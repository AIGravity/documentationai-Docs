## Overview

AIGravity/core defines a model layer for the chat interaction pipeline. The NestJS API includes DTO classes for request validation, and the AI service includes Pydantic models for request and response serialization. No ORM or database models or migration files exist in either service.

The health endpoints still return inline response shapes, but the chat interaction pipeline now defines structured models: `SendMessageDto` in the NestJS API for request validation, and `ChatRequest`, `InteractionResponse`, and `InfoJson` in the AI service for request and response serialization. These models are API contract definitions, not persisted entities.

<Callout kind="info">

This reference inventories what is present in the checked-in repository today. It does not describe planned architecture, intended schemas, or future database work.


</Callout>

- **NestJS API SendMessageDto** — DTO class for chat request validation with fields: `userId` (UUID, optional), `sessionId` (UUID, optional), `message` (string, required, max 4000), `selectedTools` (`string[]`, optional), `userPrompt` (string, optional), `submitTools` (boolean, optional)

- **AI service InteractionResponse** — Pydantic `BaseModel` for chat turn responses with fields: `session_id` (str), `reply` (str), `info_json` (`InfoJson`), `ready_to_query` (bool), `search_query` (str), `memories` (`list[str]`), `guardrail_log` (str), `redis_history` (`list[dict]`), `typesense_payload` (dict), `top_agents` (`list[dict]`), `suggested_tools` (`list[str]`), `show_tool_selection` (bool), `llm_calls` (int), `execution_id` (`str | None`)
- **AI service InfoJson** — Pydantic `BaseModel` for structured extraction with fields: `agent_type` (`list[str]`), `platforms` (`list[str]`), `tools` (`list[str]`), `selected_tools` (`list[str]`), `use_case` (`list[str]`), `constraints` (`list[str]`), `preferences` (`list[str]`), `search_query` (str), `handoff` (bool), `awaiting_tools` (bool, written as extra key via `model_config extra=allow`)

## Persistence and migration status

No ORM-based persistence layer is implemented in the analyzed codebase. The AI service uses external systems at runtime — Redis for conversation history, Typesense for agent search, and Supabase for workflow metadata — but these integrations are not modeled through ORM entities or migrations. The repository contains no Prisma schema, no TypeORM entities, no Drizzle tables, no Mongoose schemas, no SQLAlchemy models, no Sequelize models, and no Knex-based schema definitions.

Migration infrastructure is also absent. No `migrations` directory, ORM-managed migration history, or SQL migration files were found in the analyzed code.

### Repository-level signals

- The NestJS API exposes a single health controller with an inline object response.
- The FastAPI service exposes a single health endpoint with an inline object response.
- `pydantic` is present and `BaseModel` classes are defined for `ChatRequest`, `InteractionResponse`, and `InfoJson`.
- The repository README describes shared schemas and database work as planned rather than implemented.

## Gaps and implications

The current codebase exposes service health, but it does not yet define durable application data structures. That has several practical implications for anyone reading the repository as a backend reference.

- **No canonical persisted entities** — The chat models are API contracts, not database entities.
- **Validation contracts exist for the chat pipeline** — `SendMessageDto` and `ChatRequest` formalize request validation for the interaction flow, but other potential endpoints remain unspecified.
- **No persistence contract** — No model maps to a database table, collection, or record.
- **No migration history** — Schema changes cannot be tracked because no schema layer exists yet.
- **Limited reuse across services** — Shared contracts are not implemented as reusable schema packages.

<Callout kind="danger">

The chat models (`SendMessageDto`, `ChatRequest`, `InteractionResponse`, `InfoJson`) are API contract definitions for the interaction pipeline. They are not persisted entities or database models. The health endpoint shapes remain inline response objects.


</Callout>
