## Overview

AIGravity/core now includes both lightweight inline API response shapes and a persistence-backed credit billing system. The current repository defines database tables for agent run charges, user credit balance entries, creator earnings, LLM cost telemetry, and pricing configuration, alongside health and administrative response payloads exposed by the services.

What exists today spans two layers. Health endpoints still return endpoint-local inline objects, while credit billing is modeled as durable database-backed records used for charge settlement, margin tracking, and configuration-driven pricing behavior.

<Callout kind="info">

This reference inventories the current model surface in the checked-in repository, including persistence-backed billing tables as well as inline response shapes exposed by the API and AI services.


</Callout>

## Credit billing data models

The credit billing system introduces the repository's primary persistence-backed data model. These tables track what a run cost, how many credits a user was charged, what a creator earned, what the underlying LLM usage consumed, and which pricing rules were in effect when settlement happened.

### agent_run_charges

`agent_run_charges` stores settlement records for agent runs. Each record captures the quoted price, the final settled price, cost snapshots taken at charge time, and failure context when a run cannot be charged successfully.

#### Classification

- **Kind** — Persisted settlement table
- **Persistence-backed** — Yes
- **Relationships** — Referenced by `credit_ledger` through run-linked ledger entries and by `creator_earnings_ledger` through charge-linked earnings entries

#### Key fields

<ResponseField name="kind" field-type="string" required="true">

Billing surface for the charge. Observed values distinguish run contexts such as chat and marketplace.


</ResponseField>

<ResponseField name="tier_code_snapshot" field-type="string" required="true">

Pricing tier captured when the charge was computed. This snapshot preserves the pricing context even if tier definitions change later.


</ResponseField>

<ResponseField name="credits_quoted" field-type="number" required="true">

Pre-flight estimated charge in credits before the run settles. Use this value to compare projected cost against final settled cost.


</ResponseField>

<ResponseField name="credits_charged" field-type="number" required="true">

Actual settled charge in credits. This is the amount applied after the run completes and settlement logic resolves the final cost.


</ResponseField>

<ResponseField name="fail_reason" field-type="string" required="false">

Reason code recorded when a charge cannot be completed. This field distinguishes settlement failures from successful charges.


</ResponseField>

<ResponseField name="snapshot_llm_credits" field-type="number" required="false">

LLM cost captured at charge time in credit units. This snapshot supports margin analysis and preserves the cost basis used during settlement.


</ResponseField>

<ResponseField name="snapshot_infra_credits" field-type="number" required="false">

Infrastructure cost captured at charge time in credit units. This value complements the LLM snapshot when the system calculates total run cost.


</ResponseField>

<ResponseField name="input_tokens" field-type="integer" required="false">

Observed input token count captured for the run when token telemetry is available.


</ResponseField>

<ResponseField name="output_tokens" field-type="integer" required="false">

Observed output token count captured for the run when token telemetry is available.


</ResponseField>

#### Notes

This table is the billing source of truth for individual run settlements. It preserves both the commercial view of a charge, such as quoted and charged credits, and the operational view, such as token and cost snapshots used to explain how the charge was derived.

### credit_ledger

`credit_ledger` stores user credit balance entries. Each row represents a balance movement rather than a full account snapshot, which makes the table suitable for audit trails, refunds, and balance reconstruction.

#### Classification

- **Kind** — Persisted ledger table
- **Persistence-backed** — Yes
- **Relationships** — `AGENT_RUN` entries link to `agent_run_charges`, and `REFUND` entries link to the originating charge or reversal target through the reference field

#### Key fields

<ResponseField name="delta" field-type="number" required="true">

Signed balance change for the ledger entry. Positive values add credits to a user balance, and negative values debit credits from the balance.


</ResponseField>

<ResponseField name="reason" field-type="string" required="true">

Reason code for the balance movement. Observed billing reasons include `AGENT_RUN` for run charges and `REFUND` for reversals.


</ResponseField>

<ResponseField name="ref_id" field-type="string" required="false">

Reference to the originating entity for the ledger entry. The reference connects a debit or refund entry back to the billing event that produced it.


</ResponseField>

#### Notes

This table expresses balance history as immutable entries. That model makes settlement easier to audit because each debit, refund, or top-up remains visible as a distinct event instead of being collapsed into a mutable balance record.

### creator_earnings_ledger

`creator_earnings_ledger` tracks creator earnings for marketplace activity. Each entry represents a creator share derived from a marketplace run charge rather than a general-purpose revenue record.

#### Classification

- **Kind** — Persisted earnings ledger table
- **Persistence-backed** — Yes
- **Relationships** — Linked to `agent_run_charges` through `run_charge_id`; effectively one-to-one for marketplace run charges

#### Key fields

- **`run_charge_id`** — Links the earnings entry to the originating settled run charge.
- **Creator share entry** — Each row represents the creator portion of a marketplace run charge rather than the entire customer charge.

#### Notes

This table separates creator compensation from user debits. That separation allows the billing system to settle the customer side and the payout side independently while preserving a direct relationship between the two records.

### workflow_llm_calls and llm_call_logs

`workflow_llm_calls` and `llm_call_logs` store telemetry about LLM usage during agent runs. These records capture the operational detail that the billing system needs to estimate or verify model cost.

#### Classification

- **Kind** — Persisted telemetry tables
- **Persistence-backed** — Yes
- **Relationships** — Feed cost computation for agent run settlement and margin calculations

#### Key fields

- **Per-call usage telemetry** — Stores LLM usage records associated with agent execution.
- **Retry-aware usage accounting** — Supports deduplication of retry activity so repeated attempts do not inflate downstream cost totals.
- **Pre-aggregated credits-used scalar** — Provides a summarized usage value that downstream billing logic can consume directly.

#### Notes

These tables are not customer-facing billing ledgers, but they are part of the billing data model because settlement depends on them. Their role is to preserve granular usage signals while also supporting a normalized cost value that higher-level billing logic can use.

### pricing_config

`pricing_config` stores billing behavior as key-value configuration. It centralizes the settings that control pricing, settlement behavior, and environment-specific billing rules.

#### Classification

- **Kind** — Persisted configuration table
- **Persistence-backed** — Yes
- **Relationships** — Read by billing and settlement workflows as configuration input

#### Key fields

- **Configuration key** — Identifies the billing setting being stored.
- **Configuration value** — Stores the current value associated with the key.

#### Notes

This table makes pricing behavior configurable without changing application code for every adjustment. See the Configuration Reference page for the full list of keys and current values.

<Callout kind="info">

The billing service uses database-stored RPCs for charge settlement. A post-deploy verification script also checks table existence and configuration values after each deployment.


</Callout>

## Migration status

The credit billing system uses database migrations managed through SQL scripts. The repository now includes a database schema that defines billing tables for run charges, credit ledger entries, creator earnings, LLM cost tracking, and pricing configuration.

### Summary

- Billing tables are managed through SQL-based schema migrations
- The repository now includes a persistence-backed database schema
- Migration-backed tables support the credit billing system
- A post-deploy verification script checks table existence after deployment
- The same verification flow checks required configuration values after deployment

### Current implication

Database schema changes for billing are tracked through migrations, and deployment verification confirms that the expected billing tables and configuration records are present.

## Gaps and implications

The current codebase now has durable billing data structures, but its model layer is still intentionally narrow. The repository defines persistence for credit settlement and telemetry, while service-level request and response contracts remain lightweight.

- **Credit billing data models are database-backed** — Settlement and ledger records persist in tables and use RPC-based settlement logic.
- **No ORM abstraction layer** — Tables are managed through SQL migrations and accessed through stored procedures rather than a repository or entity abstraction.
- **No shared DTO or schema packages** — The NestJS API and FastAPI service do not share reusable model definitions.
- **No named validation schemas** — Request and response validation is not formalized in DTO or schema classes.

<Callout kind="info">

Credit billing tables are persistence-backed and managed through database migrations. Health endpoint response shapes still remain endpoint-local inline objects.


</Callout>
