## Overview

The AI service is the FastAPI-based AI layer for the Gravity platform, running in `apps/ai-service`. It exposes chat, agent verification, agent quality review, guardrail, embedding, and usage metering endpoints. The service orchestrates LLM calls through OpenRouter and OpenAI, manages conversation memory via Redis, persists data through Supabase, and provides agent search through Typesense.

## Current scope

The AI service provides the conversational interaction layer, agent verification gates, advisory quality review, and internal services for the Gravity platform. It handles intent classification, agent discovery, memory and session management, guardrail checks, text embeddings, Typesense agent indexing, model pricing management, and execution/usage tracking.

## Bootstrap in main.py

The application starts in `apps/ai-service/main.py`. App creation happens at module import time, and the service registers routes directly while mounting additional routers for verification, agent review, and credits.

<CodeGroup tabs="main.py,Startup responsibilities">

```python
from fastapi import FastAPI

from routes.agent_review import router as agent_review_router
from routes.credits import router as credits_router
from routes.verification import router as verification_router

app = FastAPI()

app.include_router(verification_router, prefix="/verification")
app.include_router(agent_review_router, prefix="/agent-review")
app.include_router(credits_router, prefix="/credits")
```

```text
Startup responsibilities:

- Initialize LLM clients for OpenRouter and OpenAI
- Initialize memory through Redis and Mem0
- Initialize agent search through Typesense
- Initialize guardrails through AWS Bedrock
- Initialize database connections through Supabase
- Warm verification and agent review components
- Start background tasks for execution tracking and model pricing synchronization
```

</CodeGroup>

The startup path now initializes the main service, including LLM clients, memory, search, guardrails, and database connections. It also warms verification and review components and starts background tasks for execution tracking and model pricing synchronization.

When no LLM API key is configured, `POST /chat` returns HTTP `503 Service Unavailable`.

## Endpoint surface

The service exposes endpoint families for conversational interaction, agent workflows, internal AI services, usage metering, and pricing administration.

- **Health:** `GET /health` provides service health and chat availability.
- **Chat:** `POST /chat` handles conversational interaction, intent classification, agent discovery, and response generation.
- **Agent verification:** `POST /verification/*` provides workflow verification gates streamed as Server-Sent Events, description and category generation, field generation, URL safety verdicts, and guardrail health checks.
- **Agent review:** `POST /agent-review/analyze` performs structural quality analysis, runtime and output analysis, requirement coverage analysis, and evidence-axis scoring.
- **Internal APIs:** `POST /internal/*` provides guardrail checks, text embeddings, Typesense agent indexing and deletion, and requested-agent management.
- **Credits and usage:** `GET /credits/executions/{id}/usage`, `GET /credits/executions/{id}/breakdown`, and `POST /credits/internal/workflow-llm-event` support chat execution usage and workflow LLM metering.
- **Admin pricing:** `POST /admin/pricing` manages model pricing overrides and requires an admin token.

## Health endpoint

The only custom endpoint implemented in the analyzed service code is `GET /health`. It returns a plain JSON object with one field.

<CodeGroup tabs="Route,Response">

```python
@app.get("/health")
def health():
    return {"status": "ok"}
```

```json
{
  "status": "ok"
}
```

</CodeGroup>

The endpoint does not define a response model, custom status code, tags, auth requirement, or explicit error handling. It is best understood as a basic process health check because no downstream dependencies are wired into the service.

The `/chat` endpoint is the primary user-facing route. It accepts a `ChatRequest` with `user_id`, `session_id`, `message`, `selected_tools`, `submit_tools`, and optional `agent_id`. The response includes the assistant reply, interaction mode, matching agents, suggested tools, and an `execution_id` for billing correlation. The endpoint returns `503` when no LLM API key is configured.

## Python environment and dependency management

Python and package management are consistent across local tooling, project metadata, and the lockfile. The service requires Python `>=3.14`, uses uv for dependency resolution, and pins resolved package versions in `uv.lock`.

The service dependencies have expanded beyond FastAPI, Pydantic, and Uvicorn. They now include packages for LLM orchestration such as OpenAI and HTTPX, database access through Supabase and SQLAlchemy, caching through Redis, search through Typesense, AWS integration through Boto3 for Bedrock guardrails, and embeddings through Google Generative AI. The exact dependency list is defined in `pyproject.toml`.

## Run locally

The repository does not include a substantive local guide for this service, so the usable commands are implied by the CI workflow and Docker runtime command. Run these commands from `apps/ai-service`.

<CodeGroup tabs="Install and start,Quality checks">

```bash
uv python install
uv sync
uv run uvicorn main:app --host 0.0.0.0 --port 8001
```

```bash
uv run ruff format --check .
uv run ruff check .
```

</CodeGroup>

If startup succeeds, Uvicorn listens on port `8001`. A successful request to `GET /health` returns `{"status": "ok"}`.

The service requires environment variables for LLM access through `OPENROUTER_API_KEY` or `OPENAI_API_KEY` and database access through `SUPABASE_DATABASE_URL`. Redis, Typesense, Bedrock, and Gemini configuration is optional based on the features you use. Without an LLM API key, the `/chat` endpoint returns `503`.

Tests are not part of the active CI path today. The workflow includes a commented-out pytest step, so pytest is declared as a dev dependency but is not currently enforced in automation.

## Docker packaging

The service image uses a multi-stage Docker build based on `python:3.14-slim`. The builder stage installs production dependencies with uv, and the runtime stage copies the virtual environment and application source before starting Uvicorn.

<CodeGroup tabs="Dockerfile">

```dockerfile
FROM python:3.14-slim AS builder
WORKDIR /app
COPY --from=ghcr.io/astral-sh/uv:latest /uv /uvx /bin/
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev

FROM python:3.14-slim
WORKDIR /app
COPY --from=builder /app/.venv /app/.venv
COPY . .
ENV PATH="/app/.venv/bin:$PATH"
EXPOSE 8001
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8001"]
```

</CodeGroup>

A few runtime details are explicit in the Dockerfile. The image exposes port `8001`, prepends `/app/.venv/bin` to `PATH`, and starts the app with `uvicorn main:app --host 0.0.0.0 --port 8001`.

The Dockerfile does not define a non-root user, healthcheck instruction, environment-specific configuration, or deployment-time setup. It packages and runs the current service as-is.

## CI workflow

The GitHub workflow runs when changes affect `apps/ai-service/**` or `.github/workflows/ai-service.yml` on pushes and pull requests targeting `main` or `dev`. Its build job works from `apps/ai-service`, installs uv, installs Python, syncs dependencies, and runs Ruff formatting and lint checks.

Publishing happens only on push events. On `main`, the workflow reads `apps/ai-service/VERSION`, bumps the version according to commit message rules, creates a Git tag in the format `ai-service-v<version>`, publishes `ghcr.io/<owner>/gravity-ai-service`, applies the generated version tag and `latest`, and creates a GitHub Release.

On `dev`, the workflow generates a development version using the base version, timestamp, and short SHA. It tags the repository, publishes the same image with the generated version tag and `dev-latest`, and also adds a SHA tag.
