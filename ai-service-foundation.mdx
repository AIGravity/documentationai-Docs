## Overview

The AI service is a FastAPI application that provides conversational AI, workflow quality review, publish-safety verification, usage metering, guardrail checks, and agent search indexing. It integrates with multiple LLM providers, including OpenAI, OpenRouter, and Gemini, and uses Supabase for persistence, Typesense for search, Redis for session caching, and AWS Bedrock for content guardrails.

<Callout kind="info">

The service now includes model orchestration through an LLM router, inference pipelines for chat and agent review, Supabase persistence, usage tracking, guardrail integrations, and connections to multiple external services.

</Callout>

## Current scope

The service has three primary functional surfaces: conversational runtime, agent verification, and agent review.

**Conversational runtime** supports chat with intent extraction, agent recommendations, memory, guardrails, and usage tracking. The runtime routes requests through configured LLM providers and uses supporting services for persistence, caching, and content safety.

**Agent verification** is a publish-safety pipeline. It checks whether workflows are safe and eligible to publish, including URL verdicts, description generation, and field validation. Verification is blocking: a workflow that fails required checks is not eligible to publish.

**Agent review** performs advisory quality analysis on submitted workflows. It produces findings about structural issues, dataflow problems, reliability, AI-step substance, and output quality. Review and verification serve different purposes: review recommends improvements, while verification enforces publish-safety requirements.

## Bootstrap in main.py

The application starts in `apps/ai-service/main.py`. App creation happens during module import, and the bootstrap registers multiple `APIRouter` instances for agent review, agent verification, and credits in addition to the inline `/health` and `/chat` endpoints.

<CodeGroup tabs="main.py,Notes">

```python
from fastapi import FastAPI

app = FastAPI()


@app.get("/health")
def health():
    return {"status": "ok"}
```

```text
Grounded bootstrap details:

- app = FastAPI() is defined at the top level
- /health and /chat are registered as application routes
- APIRouter instances provide agent review, agent verification, and credits routes
- middleware and dependency injection are part of the application wiring
- service wiring connects the runtime to persistence, caching, search, LLM providers, and guardrail services
```

</CodeGroup>

The startup path now combines direct application routes with router-based feature areas and shared service wiring. Middleware and dependency injection provide the infrastructure needed for request processing, authentication-related dependencies, usage tracking, external service access, and runtime policy checks.

The declared runtime dependencies provide the FastAPI application, data validation, and ASGI serving. The dev dependency group provides formatting, linting, and test tooling, while uv maintains the resolved dependency set.

Runtime integrations now span several service categories:

- **Persistence:** Supabase stores application data and workflow-related state.
- **LLM providers:** OpenAI, OpenRouter, and Gemini provide model completion capabilities through the service's LLM routing layer.
- **Search:** Typesense supports agent search indexing and retrieval.
- **Caching:** Redis provides session and runtime caching.
- **Content safety:** AWS Bedrock provides guardrail checks.
- **Application services:** Chat, review, verification, usage metering, embeddings, and administrative pricing depend on shared service and dependency wiring.

## Run locally

The repository does not include a substantive local guide for this service, so the usable commands are implied by the CI workflow and Docker runtime command. Run these commands from `apps/ai-service`.

<CodeGroup tabs="Install and start,Quality checks">

```bash
uv python install
uv sync
uv run uvicorn main:app --host 0.0.0.0 --port 8001
```

```bash
uv run ruff format --check .
uv run ruff check .
```

</CodeGroup>

If startup succeeds, Uvicorn listens on port `8001`. A successful request to `GET /health` returns `{"status": "ok"}`.

The application also requires runtime configuration for its external services. Local startup may fail or feature behavior may be unavailable when Supabase, Redis, Typesense, the configured LLM providers, or AWS Bedrock guardrails are not reachable or configured.

Tests are not part of the active CI path today. The workflow includes a commented-out pytest step, so pytest is declared as a dev dependency but is not currently enforced in automation.

## Docker packaging

The service image uses a multi-stage Docker build based on `python:3.14-slim`. The builder stage installs production dependencies with uv, and the runtime stage copies the virtual environment and application source before starting Uvicorn.

<CodeGroup tabs="Dockerfile">

```dockerfile
FROM python:3.14-slim AS builder
WORKDIR /app
COPY --from=ghcr.io/astral-sh/uv:latest /uv /uvx /bin/
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev

FROM python:3.14-slim
WORKDIR /app
COPY --from=builder /app/.venv /app/.venv
COPY . .
ENV PATH="/app/.venv/bin:$PATH"
EXPOSE 8001
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8001"]
```

</CodeGroup>

A few runtime details are explicit in the Dockerfile. The image exposes port `8001`, prepends `/app/.venv/bin` to `PATH`, and starts the app with `uvicorn main:app --host 0.0.0.0 --port 8001`.

The container now depends on external service connections at runtime. Supabase provides persistence, Redis provides session caching, Typesense provides search indexing, configured LLM providers provide model completions, and AWS Bedrock provides content guardrails. The Dockerfile does not define a non-root user, healthcheck instruction, environment-specific configuration, or deployment-time setup.

## CI workflow

The GitHub workflow runs only for pull requests targeting `main` or `dev` when changes affect `apps/ai-service/**` or `.github/workflows/ai-service.yml`. Its build job works from `apps/ai-service`, installs uv, installs Python, syncs dependencies, and runs Ruff formatting and lint checks.

Production deployment is handled by the separate unified deployment workflow. This service workflow no longer publishes production or development images, creates version tags, or creates GitHub Releases from push events.
