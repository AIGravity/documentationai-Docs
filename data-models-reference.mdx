## Overview

The AIGravity/core repository defines data models for bounty funding via Supabase-backed persistence. The bounty system uses direct SQL through a Supabase client, not an ORM, with migration-managed schema changes, a class-validator DTO for payment verification, and service-layer interfaces for order creation and verification.

Health endpoints continue to return inline response shapes that are not persisted entities. This reference inventories all model-like definitions, DTOs, persisted tables, and migration files present in the checked-in repository.

<Callout kind="info">

This reference inventories what is present in the checked-in repository. It covers bounty funding models, DTOs, and migrations that are currently implemented.


</Callout>

### Model-like definitions found

- **NestJS API health response** — inline response shape: ``{ status: "ok", service: "api" }``
- **FastAPI health response** — inline response shape: `{"status": "ok"}`
- **VerifyBountyOrderDto** — class-validator DTO with three required string fields: `razorpayOrderId`, `razorpayPaymentId`, `razorpaySignature`. Used by `POST /api/bounties/{id}/pay/verify`.
- **CreateBountyOrderResult** — service interface returned by `POST /api/bounties/{id}/pay/order`. Fields: `orderId`, `razorpayOrderId`, `razorpayKeyId`, `amountMinor`, `currency`, `bountyId`, `bountyTitle`.
- **VerifyBountyOrderResult** — service interface returned by `POST /api/bounties/{id}/pay/verify`. Fields: `status` with values `PAID` or `ALREADY_PAID`, `bountyId`, `bountyStatus`.
- **CreateBountyResult (extended)** — response shape for `POST /api/bounties`. Fields: `id`, `title`, `summary`, `expiresAt`, `paymentRequired`, `amount`, `currency`.

## Bounty funding data models

Bounty funding introduces the repository's first persisted schema. The implementation uses SQL migrations and Supabase access patterns rather than ORM entity classes.

### `bounties` table additions

| Column | Type | Default | Description |
| --- | --- | --- | --- |
| `payment_status` | TEXT | `'unpaid'` | Funding state: `'unpaid'` or `'paid'`. Existing bounties backfilled to `'paid'`. |
| `funded_at` | TIMESTAMPTZ | NULL | Timestamp when the bounty was funded via Razorpay. |

### `bounty_orders` table

| Column | Type | Description |
| --- | --- | --- |
| `id` | UUID (PK) | Auto-generated order UUID |
| `bounty_id` | UUID (FK → `bounties.id`) | Bounty this order funds, cascading delete |
| `user_id` | UUID (FK → `auth.users.id`) | User who created the order, cascading delete |
| `amount_minor` | INTEGER | Amount in minor units, CHECK >= 0 |
| `currency` | TEXT | Currency code |
| `razorpay_order_id` | TEXT (UNIQUE) | Razorpay order identifier, serves as idempotency key |
| `razorpay_payment_id` | TEXT | Razorpay payment identifier, set on success |
| `status` | TEXT | One of: `PENDING`, `PAID`, `FAILED`, `EXPIRED` with default `PENDING` |
| `fail_reason` | TEXT | Reason for failure, set when status is `FAILED` |
| `created_at` | TIMESTAMPTZ | Creation timestamp with default `now()` |
| `updated_at` | TIMESTAMPTZ | Last update timestamp, auto-updated via trigger |

<Callout kind="info">

The migration also creates three indexes for common access paths: `bounty_orders_bounty_id_idx`, `bounty_orders_user_id_idx`, and `bounty_orders_status_idx`.


</Callout>

### Bounty lifecycle statuses

| Status | Description |
| --- | --- |
| `pending_payment` | Created, awaiting Razorpay payment. Hidden from public list. |
| `open` | Live and accepting submissions. |
| `awarded` | A winner has been chosen. |
| `expired` | Past the expiry date. |

## Validation schema and DTO status

The repository now includes one named DTO for Razorpay payment verification in the NestJS API.

### NestJS API

- **VerifyBountyOrderDto** — the first DTO in the repository. Uses `class-validator` with `@IsString` and `@IsNotEmpty` decorators on three required fields: `razorpayOrderId`, `razorpayPaymentId`, `razorpaySignature`. Used to validate the request body for `POST /api/bounties/{id}/pay/verify`.
- `class-validator` is now used for request body validation on the verify endpoint.
- No `ValidationPipe` is globally configured, but the DTO is applied via NestJS body validation on the specific route.

### FastAPI service

- No Pydantic `BaseModel` classes found
- No request model annotations found
- No response model annotations found

<Callout kind="info">

The `VerifyBountyOrderDto` is the first `class-validator` DTO in the repository. It validates Razorpay Checkout verification parameters. The Pydantic dependency in the Python service remains unused for model definitions.


</Callout>

## Migration status

Bounty funding starts the repository's schema migration history with one SQL migration.

- Migration file: `017_bounty_orders.sql`
- Creates the `bounty_orders` table with UUID primary key, foreign keys to `bounties` and `auth.users`, CHECK constraints on `amount_minor` and `status`, and a UNIQUE constraint on `razorpay_order_id`.
- Adds `payment_status` and `funded_at` columns to the `bounties` table.
- Backfills all existing bounties with `payment_status = 'paid'`.
- Creates three indexes on `bounty_orders` for `bounty_id`, `user_id`, and `status`.

<CodeGroup tabs="SQL">

```sql
CREATE TABLE bounty_orders (
  id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  bounty_id           UUID NOT NULL REFERENCES bounties(id) ON DELETE CASCADE,
  user_id             UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  amount_minor        INTEGER NOT NULL CHECK (amount_minor >= 0),
  currency            TEXT NOT NULL,
  razorpay_order_id   TEXT UNIQUE,
  razorpay_payment_id TEXT,
  status              TEXT NOT NULL DEFAULT 'PENDING'
                      CHECK (status IN ('PENDING','PAID','FAILED','EXPIRED')),
  fail_reason         TEXT,
  created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at          TIMESTAMPTZ NOT NULL DEFAULT now()
);

ALTER TABLE bounties
  ADD COLUMN IF NOT EXISTS payment_status TEXT NOT NULL DEFAULT 'unpaid'
    CHECK (payment_status IN ('unpaid','paid')),
  ADD COLUMN IF NOT EXISTS funded_at TIMESTAMPTZ;
```

</CodeGroup>

## Gaps and implications

The bounty funding system introduces the repository's first persistence layer, DTO, and migration. The following gaps remain for broader domain coverage:

- **Limited domain entity coverage** — Bounty funding models exist, but other domain areas such as users, sessions, and projects do not yet have formalized models.
- **Partial validation contract** — `VerifyBountyOrderDto` validates payment verification, but other endpoints lack formal DTOs.
- **Bounty persistence implemented** — `bounty_orders` and `bounties` tables are managed via Supabase and SQL migrations. Other domain areas are not yet persisted.
- **Migration history started** — The `017_bounty_orders` migration is the first schema migration. Future schema changes should follow the same pattern.
- **Limited reuse across services** — Shared contracts are not implemented as reusable schema packages.

<Callout kind="info">

The bounty funding data models are the repository's first persisted entities. Treat other response objects, such as health endpoint shapes, as endpoint-local and not backed by a database.


</Callout>
