## Overview

The AI service is a FastAPI application that provides the platform's AI capabilities, including chat interactions, content guardrails, text embeddings, agent indexing, requested-agent management, agent verification with server-sent event streaming, agent review analysis, and credit metering. It runs on port `8001` and organizes endpoints into structured router groups.

## Current scope

The AI service provides a feature-rich set of AI platform capabilities. It supports chat interactions backed by language model providers, content safety guardrails for input and output evaluation, vector embeddings for agent indexing and retrieval, requested-agent management, structured agent verification with server-sent event streaming, agent review analysis with findings and evidence scoring, and credit metering for execution usage tracking.

The service uses Pydantic models for request validation and organizes related endpoints into structured router groups for `/verification`, `/agent-review`, and `/credits`. Internal service-to-service endpoints use the `/internal` path prefix, while the admin pricing endpoint uses the `/admin` prefix.

## Bootstrap

The application starts from the service entry point. The bootstrap creates the FastAPI application, registers the health endpoint, mounts structured router groups for `/verification`, `/agent-review`, and `/credits`, and starts serving requests on port `8001`.

The router groups are composed at application startup, making related endpoints available under their respective path prefixes. Internal service-to-service endpoints under `/internal` and the admin pricing endpoint under `/admin` are also registered during bootstrap.

Pydantic models validate request bodies for each endpoint group, providing structured request validation before route handlers process incoming data.

## Health endpoint

The `GET /health` endpoint reports the service health status, the running version, and whether chat functionality is available.

```json
{
  "status": "ok",
  "service": "ai-service",
  "version": "1.0.0",
  "chat_available": true
}
```

The `chat_available` field indicates whether the service has the required language model configuration to handle chat requests. When the LLM key is not configured, the field returns `false` and chat requests will fail with a `503 Service Unavailable` response.

<ResponseField name="status" field-type="string" required="true">

Returns `ok` when the AI service is healthy and responding.

</ResponseField>

<ResponseField name="service" field-type="string" required="true">

</ResponseField>

<ResponseField name="version" field-type="string" required="true">

</ResponseField>

<ResponseField name="chat_available" field-type="boolean" required="true">

</ResponseField>

## Python environment and dependency management

Python and package management are consistent across local tooling, project metadata, and the lockfile. The service requires Python `>=3.14`, uses uv for dependency resolution, and pins resolved package versions in `uv.lock`.

<CodeGroup tabs="pyproject.toml,uv.lock,.python-version">

```toml
[project]
name = "ai-service"
version = "0.1.0"
requires-python = ">=3.14"
dependencies = [
    "fastapi>=0.135.0",
    "pydantic>=2.12.5",
    "uvicorn>=0.41.0",
]

[dependency-groups]
dev = [
    "ruff>=0.11.0",
    "pytest>=8.0.0",
]
```


The declared runtime dependencies include FastAPI, Pydantic, and Uvicorn, along with additional packages for language model provider integrations, vector search, database connectivity, and other AI-specific libraries. The dev dependency group adds Ruff and pytest for code quality and testing.

## Run locally

The repository does not include a substantive local guide for this service, so the usable commands are implied by the CI workflow and Docker runtime command. Run these commands from `apps/ai-service`.

<CodeGroup tabs="Install and start,Quality checks">

```bash
uv python install
uv sync
uv run uvicorn main:app --host 0.0.0.0 --port 8001
```

```bash
uv run ruff format --check .
uv run ruff check .
```

</CodeGroup>

If startup succeeds, Uvicorn listens on port `8001`. A successful request to `GET /health` returns a JSON object with `status`, `service`, `version`, and `chat_available` fields.

Tests are not part of the active CI path today. The workflow includes a commented-out pytest step, so pytest is declared as a dev dependency but is not currently enforced in automation.

## Docker packaging

The service image uses a multi-stage Docker build based on `python:3.14-slim`. The builder stage installs production dependencies with uv, and the runtime stage copies the virtual environment and application source before starting Uvicorn.

<CodeGroup tabs="Dockerfile">

```dockerfile
FROM python:3.14-slim AS builder
WORKDIR /app
COPY --from=ghcr.io/astral-sh/uv:latest /uv /uvx /bin/
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev

FROM python:3.14-slim
WORKDIR /app
COPY --from=builder /app/.venv /app/.venv
COPY . .
ENV PATH="/app/.venv/bin:$PATH"
EXPOSE 8001
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8001"]
```

</CodeGroup>

A few runtime details are explicit in the Dockerfile. The image exposes port `8001`, prepends `/app/.venv/bin` to `PATH`, and starts the app with `uvicorn main:app --host 0.0.0.0 --port 8001`.

The Dockerfile does not define a non-root user, healthcheck instruction, environment-specific configuration, or deployment-time setup. It packages and runs the AI service as-is.

## CI workflow

The GitHub workflow runs when changes affect `apps/ai-service/**` or `.github/workflows/ai-service.yml` on pushes and pull requests targeting `main` or `dev`. Its build job works from `apps/ai-service`, installs uv, installs Python, syncs dependencies, and runs Ruff formatting and lint checks.

Publishing happens only on push events. On `main`, the workflow reads `apps/ai-service/VERSION`, bumps the version according to commit message rules, creates a Git tag in the format `ai-service-v<version>`, publishes `ghcr.io/<owner>/gravity-ai-service`, applies the generated version tag and `latest`, and creates a GitHub Release.

On `dev`, the workflow generates a development version using the base version, timestamp, and short SHA. It tags the repository, publishes the same image with the generated version tag and `dev-latest`, and also adds a SHA tag.
