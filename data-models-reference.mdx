## Overview

The NestJS API defines DTOs with `class-validator` decorators for request validation, and the FastAPI AI service defines Pydantic `BaseModel` classes for request and response validation. The API uses Supabase as its persistence layer, with service classes querying Supabase for domain data.

A global NestJS `ValidationPipe` applies `whitelist`, `forbidNonWhitelisted`, and `transform` behavior to all incoming requests. FastAPI validates request bodies against the Pydantic models declared by each route.

<Callout kind="info">

DTOs and Pydantic models define request and response contracts. Supabase provides persistence and authentication, while migration management is handled through Supabase rather than an in-repo ORM.

</Callout>

## NestJS API models and DTOs

The NestJS API defines DTOs across its feature modules for request validation. The global `ValidationPipe` enforces whitelist, forbid-non-whitelisted, and transform behavior, rejecting unknown body properties with `400` responses.

### DTO groups

- **Authentication:** `SignUpDto`, `LoginDto`, `SendOtpDto`, `VerifyOtpDto`, `RefreshTokenDto`, `ForgotPasswordDto`, `UpdatePasswordDto`, `CompleteProfileDto`
- **Agents:** `PublishAgentDto`, `CheckRequestAlignmentDto`, `ReviewSubmissionDto`, `VerifyAgentDto`
- **Marketplace:** `PublishPasteDto`, `RunWorkflowDto`
- **Automations:** `CreateAutomationDto`, `UpdateAutomationDto`
- **Bounties:** `CreateBountyDto`, `PreviewBountyDto`
- **Subscriptions:** `SubscriptionCheckoutRequest`
- **Credits:** `CreditOrderRequest`
- **Payouts:** `PayoutRequest`, `PayoutAccountRequest`
- **Chat:** `SendMessageDto`

These DTOs define the accepted request shapes at the feature boundary. Decorators on DTO properties provide type and constraint validation before the request reaches the service layer.

### Global validation configuration

The API configures validation globally with the following behavior:

<ParamField body="whitelist" param-type="boolean" required="true" show-location="false">

Removes properties that do not have validation decorators on the DTO.

</ParamField>

<ParamField body="forbidNonWhitelisted" param-type="boolean" required="true" show-location="false">

Rejects requests containing properties that are not allowed by the DTO. These requests return `400`.

</ParamField>

<ParamField body="transform" param-type="boolean" required="true" show-location="false">

Transforms incoming values according to the DTO property types where supported.

</ParamField>

<ParamField path="id" param-type="UUID" required="true">

Path parameters that represent UUIDs use `ParseUUIDPipe` for format validation before the controller method runs.

</ParamField>

### Health response shape

The API health endpoint returns a structured response with service status and runtime metadata.

<CodeGroup tabs="TypeScript">

```ts

export class HealthController {
  @Get()
  getHealth() {
    return {
      status: "ok",
      service: "api",
      timestamp: new Date().toISOString(),
    };
  }
}
```

</CodeGroup>

## FastAPI AI service models

The FastAPI AI service defines Pydantic `BaseModel` classes for request and response validation across its route groups. FastAPI validates request bodies against these models before invoking the route handler and returns `422` responses for validation failures.

### Pydantic model groups

- **Chat:** `ChatRequest`, `InteractionResponse`
- **Guardrails:** `GuardrailCheckRequest`, `GuardrailCheckResponse`
- **Embeddings:** `EmbedRequest`, `EmbedResponse`
- **Agent indexing:** `IndexAgentRequest`
- **Workflow review:** `ReviewWorkflowRequest`, `ReviewWorkflowResponse`
- **Requested agents:** `CreateRequestedAgentRequest`, `CreateOrMergeResponse`, `RequestedAgentView`, `InterestResponse`
- **Verification:** Request models based on `workflowJson`
- **URL evaluation:** `UrlVerdictResponse`
- **Pricing:** `PricingOverrideRequest`

Typed fields on these models establish the accepted request and response shapes for AI service routes. Field validators apply additional constraints where a type declaration alone is insufficient.

### Health response shape

The AI service health endpoint returns service status, version metadata, and chat availability.

## Validation schema and DTO status

Validation is implemented at both service boundaries with framework-native schema systems.

### NestJS API

- DTO properties use `class-validator` decorators.
- The global `ValidationPipe` uses `whitelist: true`.
- The global `ValidationPipe` uses `forbidNonWhitelisted: true`.
- The global `ValidationPipe` uses `transform: true`.
- Unknown body properties produce `400` responses.
- `ParseUUIDPipe` validates UUID path parameters.
- Feature modules use DTOs for authentication, agents, marketplace operations, automations, bounties, subscriptions, credits, payouts, and chat.

### FastAPI service

- Request and response models extend Pydantic `BaseModel`.
- Typed fields define the expected request and response data.
- Field validators enforce constraints that require more than basic type checking.
- FastAPI validates request bodies before route handlers run.
- Invalid request bodies produce `422` responses.

<Callout kind="info">

NestJS DTOs and FastAPI Pydantic models are the primary validation contracts at their respective service boundaries. Supabase data access remains service-layer logic rather than ORM entity mapping.

</Callout>

## Persistence and migration status

The API uses Supabase as its persistence layer. Service classes query Supabase for user profiles, agents, workflows, bounties, payouts, subscriptions, credits, referrals, and other domain data.

Supabase also provides the authentication infrastructure used by the application. The application models persisted domain data through service queries and returned objects rather than through Prisma, TypeORM, Drizzle, Mongoose, SQLAlchemy, Sequelize, or another in-repo ORM model layer.

### Persisted domain areas

Supabase stores data for areas including:

- User profiles and authentication-related records
- Agents and agent publication data
- Workflows and marketplace activity
- Bounties and bounty previews
- Payouts and payout accounts
- Subscriptions and credit orders
- Referrals
- Other feature-specific application data accessed by service classes

### Migration management

Migration management is handled through Supabase rather than through ORM migration files checked into the application repository. Supabase is the source of truth for the database schema and its evolution.

## Gaps and implications

The codebase now defines request and response contracts, validates inputs at both service boundaries, and persists domain data through Supabase. The remaining contract gap concerns reuse between services.

- **DTOs and Pydantic models define domain shapes:** NestJS feature DTOs and FastAPI models formalize many request and response contracts.
- **Validation is enforced at the service boundaries:** Class-validator, the global `ValidationPipe`, Pydantic, and FastAPI reject invalid input before business logic executes.
- **Supabase provides the persistence contract:** Service classes query Supabase for users, agents, workflows, bounties, payouts, subscriptions, credits, referrals, and related records.
- **Supabase manages schema evolution:** Database migrations are managed through Supabase rather than an in-repo ORM migration system.
- **Shared contracts are not yet centralized:** Cross-service schemas are not currently maintained in a shared `packages/` directory.

<Callout kind="info">

DTOs and Pydantic models define request and response shapes for each service. Cross-service contract sharing through workspace packages is not yet implemented, so equivalent concepts may remain defined separately in the NestJS API and FastAPI AI service.

</Callout>
