## Overview

Gravity is a polyglot monorepo with three independently runnable applications under `apps/`: a Remix frontend at `apps/web`, a NestJS API at `apps/api`, and a FastAPI service at `apps/ai-service`. The repository has workspace orchestration, per-service Dockerfiles, semantic version files, GitHub Actions pipelines, authentication, Supabase persistence, multiple feature modules, and cross-service communication between the API and AI service.

The practical architecture today is a maturing multi-service platform rather than a feature-complete system. Each service starts, builds, and ships independently, and the API and AI service now collaborate for chat, verification, and review operations. A shared `packages/` directory still does not exist, so shared contracts and UI primitives are not yet implemented as workspace packages.

<Callout kind="info">

`pnpm-workspace.yaml` includes `packages/*`, and the README describes planned shared packages, but no `packages/` directory exists in the current repository tree.

</Callout>

## Top-level repository structure

The repository root contains the orchestration, build, and operational layers that tie the three applications together.

- `.github/`
  - `.github/workflows/web.yml`
  - `.github/workflows/api.yml`
  - `.github/workflows/ai-service.yml`
- `apps/`
  - `apps/web`
  - `apps/api`
  - `apps/ai-service`
- `scripts/`
  - `scripts/bootstrap.sh`
  - `scripts/version-bump.sh`
- `README.md`
- `package.json`
- `pnpm-lock.yaml`
- `pnpm-workspace.yaml`
- `tsconfig.base.json`
- `turbo.json`

A few root files define the monorepo shape directly:

- `pnpm-workspace.yaml` registers `apps/*` and `packages/*` as workspaces.
- `turbo.json` configures a minimal task graph for `dev` and `build`.
- `package.json` defines root development commands that delegate into the app workspaces.
- `scripts/bootstrap.sh` installs toolchains and service dependencies across JavaScript, Bun, and Python environments.

## Monorepo orchestration layer

The repo uses `pnpm` workspaces for package coordination and Turborepo primarily as a process orchestrator. At the current maturity level, Turborepo is not modeling a deep dependency graph because there are no shared internal packages yet.

The root `package.json` defines workspace-level commands such as `dev:web`, `dev:api`, and `dev`. Those commands establish the intended local development pattern: run services independently when needed, or run them in parallel through Turbo.

<Callout kind="alert">

The root script `dev:py` points to `apps/py-service`, but the actual Python service lives at `apps/ai-service`. That script is stale relative to the repository tree.

</Callout>

## Service architecture

### `apps/web`: Remix frontend

`apps/web` is the user-facing frontend. It uses Remix with Vite and React, and the current code remains close to a starter application rather than an integrated product UI.

The main entry file is `apps/web/app/root.tsx`. That file defines the document shell, global styles, font links, an `ErrorBoundary`, and the route outlet. The exported app component returns an `Outlet`, so request handling follows standard Remix nested routing.

Current route files are minimal:

- `apps/web/app/routes/_index.tsx`
- `apps/web/app/routes/home.tsx`

Both routes render the same component from `apps/web/app/welcome/welcome.tsx`. There are no route loaders, no route actions, no session handling, no data fetching helpers, and no API client layer in the current frontend tree.

`apps/web/vite.config.ts` shows the active frontend stack:

- Remix
- Vite
- Tailwind CSS
- TypeScript path support

The relationship to the rest of the repo is mostly implicit. The API service enables CORS for `http://localhost:3000`, which indicates the frontend is expected to call the API, but no such calls are implemented in the frontend code today.

### `apps/api`: NestJS API on Bun

`apps/api` is the TypeScript backend boundary. It uses NestJS for the HTTP framework, Bun as the runtime for local development and execution, and TypeScript compilation to `dist/` for builds.

The service boots from `apps/api/src/main.ts`. That file creates the Nest application, enables CORS for `http://localhost:3000`, and listens on port `3001`.

The API has grown into a multi-module service with controllers for authentication, agents, marketplace, automations, bounties, chat, connections, credits, payouts, subscriptions, referrals, leaderboard, telemetry, and other domain areas. Protected routes use `SupabaseAuthGuard`, admin routes use `AdminGuard`, and a global `ValidationPipe` enables whitelist and transform behavior. A global exception filter provides centralized error handling.

The service now follows a controller-to-service pattern across feature modules. Domain-specific controllers delegate application logic to services, while DTOs and validation define the shapes accepted by the API. The health endpoint remains part of the service, but it is now one small part of a broader application surface.

That makes `apps/api` an active application service with domain modules, authentication, persistence access, validation, and cross-service integrations. Its primary boundaries exist both at the application level and within feature-oriented Nest modules.

### `apps/ai-service`: FastAPI Python service

`apps/ai-service` is the Python service that hosts AI-related functionality. It has grown into a multi-router application with routes for chat, guardrail checks, embeddings, agent indexing, requested agents, workflow verification, and agent review analysis.

Workflow verification includes description generation, step generation, category generation, fillable field generation, setup validation, request alignment judgment, prewarming, and streaming verification. The service uses Pydantic models for request validation and integrates with LLM providers and embedding services.

The entry point is `apps/ai-service/main.py`. It assembles the FastAPI application and its routers, while the service modules handle domain-specific operations. The Python project configuration lives in `apps/ai-service/pyproject.toml`. Dependencies include `fastapi`, `pydantic`, and `uvicorn`, with `ruff` and `pytest` declared for development.

<Callout kind="info">

The AI service integrates with LLM providers for chat and workflow verification, and with embedding providers for agent indexing. Some routes fail open when those providers are unavailable.

</Callout>

## Entry points and request handling

Each application has a clear entry point, and the backend services now expose substantial request handling beyond health checks.

### Web routes

The frontend entry point is `apps/web/app/root.tsx`, with route modules under `apps/web/app/routes/`.

Current route behavior:

- `/` is defined by `apps/web/app/routes/_index.tsx`
- `/home` is defined by `apps/web/app/routes/home.tsx`

Both route modules render the same welcome component. There are no loaders, actions, or backend requests in those routes.

### API routes

The API entry point is `apps/api/src/main.ts`, with feature controllers covering the application's domain areas.

The API exposes health routes at `GET /` and `GET /health`, plus extensive routes under `/api/*` covering authentication, agents, marketplace, automations, bounties, subscriptions, credits, payouts, chat, connections, referrals, leaderboard, and telemetry. Most routes require JWT Bearer authentication, and admin routes additionally require admin authorization.

`apps/api/src/main.ts` does not set a global prefix. The `/api/*` paths come from controller-level route prefixes within the feature modules.

### AI service routes

The AI service entry point is `apps/ai-service/main.py`.

The AI service exposes `GET /health` plus routes for chat at `POST /chat`, guardrail checks, embeddings, agent indexing, requested agents, workflow verification under `/verification/*`, and agent review under `/agent-review/*`. Routes are split across multiple `APIRouter` modules.

## Module relationships and service boundaries

The repository has strong top-level separation and increasingly defined internal layering. The clearest boundaries today are folder boundaries:

- `apps/web` for the frontend
- `apps/api` for the TypeScript backend
- `apps/ai-service` for the Python backend

The Nest app now follows a controller-to-service pattern with feature modules for each domain area. The FastAPI app splits routes into `APIRouter` modules for verification and review, with service classes handling business logic. The frontend still does not separate route modules from API clients, domain packages, or shared contracts because those layers are not implemented in the current frontend tree.

The architecture is therefore separated both by service and, increasingly, by internal feature boundaries. Shared workspace packages remain absent, so cross-application contracts are not yet centralized in a reusable package.

### Current cross-service wiring

The backend services now have implemented communication paths for AI-powered operations.

- `apps/api/src/main.ts` allows CORS from `http://localhost:3000`, implying browser calls from the web app.
- The repository README describes a future shared-contract pattern through planned packages.
- `apps/api` calls `apps/ai-service` for chat, workflow verification, and agent review operations.
- The API and AI service exchange request and response data through their service interfaces rather than through shared workspace packages.

No direct frontend wiring exists today:

- no frontend fetches to the API in `apps/web`
- no API client or SDK package
- no shared `packages/` code
- no shared schema or contract definitions

<Callout kind="alert">

Treat the current topology as three services managed in one monorepo, with backend-to-AI integrations implemented but frontend-to-API integration still limited in the current web application.

</Callout>

## Persistence, middleware, auth, and external services

### Database and persistence

The API uses Supabase as its persistence layer. Service classes query Supabase for user profiles, agents, workflows, bounties, payouts, subscriptions, and other domain data.

Persistence is accessed from feature services rather than from a single generic repository layer. Supabase also provides the authentication data and token infrastructure used by the API.

### Middleware

Middleware is configured across the services for platform-level concerns.

- In `apps/api/src/main.ts`, CORS allows browser requests from `http://localhost:3000`, and global validation and exception handling are configured for incoming requests.
- In `apps/web`, there is no evidence of session middleware, CSRF protection, cookie handling, or request interception.
- In `apps/ai-service/main.py`, FastAPI assembles multiple routers and service integrations, while route-level authorization handles protected administrative operations.

Cross-cutting concerns are now partly formalized in the API through validation, exception handling, and authentication guards. Logging, request context propagation, and broader observability remain areas for continued development.

### Authentication and authorization

The API implements authentication using Supabase JWT tokens. A `SupabaseAuthGuard` protects most user routes, and an `AdminGuard` protects admin-specific routes.

Public routes, including health routes, webhooks, the marketplace catalog, and the leaderboard, are exempted with `@Public()`. The AI service admin route uses an `x-admin-token` header for authorization.

### External services and integrations

The codebase integrates with several external systems:

- Supabase for database access and authentication
- LLM providers for chat, workflow verification, and review analysis
- Gemini embedding services for agent indexing
- Razorpay, Stripe, and PayPal for payments
- Google OAuth for external identity authentication
- ActivePieces as a workflow engine
- Composio for third-party connections
- browser-to-API CORS allowance for `http://localhost:3000`
- Google Fonts references in `apps/web/app/root.tsx`
- GitHub Container Registry publishing in `.github/workflows/web.yml`, `.github/workflows/api.yml`, and `.github/workflows/ai-service.yml`

Not present today:

- Redis or cache clients
- cloud object storage
- email or SMS providers
- observability or APM tooling
- feature flag systems

## Build, release, and deployment tooling

The operational layer is more mature than the application layer. Each app has enough tooling to build, version, containerize, and publish independently.

### Local setup

`scripts/bootstrap.sh` checks for `pnpm`, `bun`, and `uv`, then installs dependencies for the JavaScript and Python services. That script reflects the repo's polyglot design: each app uses the native tooling expected for its runtime.

### Versioning

Each app has a local `VERSION` file:

- `apps/web/VERSION`
- `apps/api/VERSION`
- `apps/ai-service/VERSION`

`scripts/version-bump.sh` updates those version files, establishing per-service version management rather than one monorepo-wide application version.

### Containers and CI/CD

Each service has its own Dockerfile:

- `apps/web/Dockerfile`
- `apps/api/Dockerfile`
- `apps/ai-service/Dockerfile`

Each service also has its own GitHub Actions workflow:

- `.github/workflows/web.yml`
- `.github/workflows/api.yml`
- `.github/workflows/ai-service.yml`

Those workflows handle build and verification steps, version generation, Docker image publishing to GitHub Container Registry, and GitHub release creation. The deployment sections are present as placeholders, which means release automation is implemented further than environment deployment.

## Notable gaps and inconsistencies

A few repo details can mislead an architectural review unless they are called out directly.

### Shared packages are planned but absent

`pnpm-workspace.yaml` includes `packages/*`, and the README describes shared packages for types, UI, and config. The actual file tree does not contain a `packages/` directory.

That gap matters because the intended contract-sharing architecture does not exist yet in code. No current module should be assumed to share types or UI primitives through a workspace package.

### Script and naming drift around the Python service

The repository uses `apps/ai-service` as the actual Python service path, but some root-level references still point to `py-service`. The most concrete example is the root `package.json` script that targets `apps/py-service`.

This inconsistency affects local development expectations and is a sign that repo documentation and scripts have not fully caught up with the current directory structure.

### Testing exists mostly as intent

The Python service declares `pytest`, and the workflows reference verification steps, but the repository does not yet show a meaningful test suite. The CI layer is prepared for broader testing, while the codebase itself remains at an early implementation stage.

<Callout kind="info">

The architecture has matured beyond a scaffold. Domain modules, Supabase persistence, authentication, and service-to-service flows are now implemented. The remaining gaps are concentrated in shared workspace packages, frontend integration depth, testing coverage, and deployment configuration.

</Callout>

## What this architecture means today

Gravity has answered most of its core application-level architecture questions. Domain logic lives in feature modules, state is stored in Supabase, users authenticate through Supabase JWT tokens, and the API and AI service collaborate for chat, verification, and review operations. The repository also has defined runtimes, service boundaries, build tools, and release mechanics.

The remaining work is primarily about extending and standardizing those patterns. Shared contracts are not yet centralized in a `packages/` directory, the frontend still has limited API integration, and deployment and testing need to catch up with the expanded application surface.
