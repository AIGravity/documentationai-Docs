## Overview

AIGravity/core now includes a substantial model layer. Supabase provides PostgreSQL persistence through more than 50 migrations, while the NestJS API defines DTO classes across domain modules including auth, agents, marketplace, payments, bounties, builder, and referrals.

The FastAI service defines Pydantic models for agent review, verification, credits, and other functional areas. Health endpoints still expose simple inline response shapes, but those responses now exist alongside structured domain models, validation schemas, and persisted entities.

<Callout kind="info">

This reference inventories the model, validation, persistence, and migration definitions present in the checked-in repository. It focuses on implemented structures rather than planned architecture or future schema work.

</Callout>

### Model-like definitions found

The repository contains extensive domain and validation models in addition to the two inline health response shapes:

- **NestJS API health response**: inline response shape: `{ status: "ok", service: "api" }`
- **FastAPI health response**: inline response shape: `{"status": "ok"}`
- **Supabase entities**: persisted structures for profiles, workflows, agents, bounties, marketplace listings, payments, subscriptions, referrals, reviews, notifications, and related records
- **NestJS DTOs**: request and response contracts across authentication, agents, marketplace, payments, bounties, builder tools, and referrals
- **FastAPI models**: Pydantic request and response models for agent review, verification, credits, and related AI service features

## Persistence and migration status

The system uses Supabase, backed by PostgreSQL, for application persistence. SQL migrations cover profiles, workflow tables, session flow states, bounties, builders, published workflows, agent verification runs, agent reviews, agent runs, referrals, referral earnings, builder reports, payments, subscriptions, payouts, notifications, and other domain data.

Migrations include both SQL schema changes and Python data migration scripts. The migration history provides the repository-level record of database structure and data changes as the application has expanded.

### Repository-level signals

- The NestJS API exposes health data alongside DTO-backed domain endpoints.
- The FastAPI service exposes health data alongside Pydantic-backed AI workflows.
- `pydantic` is used to define request and response models in the Python service.
- Supabase migrations define PostgreSQL persistence for the application’s domain entities.
- The repository includes both SQL migration files and Python data migration scripts.

## NestJS API response shape

The NestJS API currently returns one simple structured object from the health endpoint. This object is an inline response shape, not a named DTO or persisted entity, and represents only one response among the API’s broader set of DTO-backed contracts.

### Implemented shape

<CodeGroup tabs="TypeScript">

```ts
@Controller("health")
export class HealthController {
  @Get()
  getHealth() {
    return { status: "ok", service: "api" };
  }
}
```

</CodeGroup>

The API also defines DTOs across authentication, agents, marketplace, payments, bounties, builder tools, and referrals. These include contracts for signup, login, OTP, password reset, agent publishing, agent reviews, agent verification, marketplace introspection, marketplace runs, marketplace publishing, credits, subscriptions, payouts, bounty orders, and referral workflows.

### Classification

- **Kind**: Inline response shape
- **Named entity or DTO**: None for this health response; numerous named DTOs exist across the API modules
- **Persistence-backed**: No for this health response; related domain operations use Supabase persistence
- **Relationships**: None found in this health response
- **Validation rules**: None found in this health response; API DTOs use class-validator rules

### Response fields

<ResponseField name="status" field-type="string" required="true">

Health state returned by the endpoint. The implemented handler returns `ok`.

</ResponseField>

<ResponseField name="service" field-type="string" required="true">

Service identifier returned by the endpoint. The implemented handler returns `api`.

</ResponseField>

### Notes

This response shape is defined inline inside the controller method. The broader API uses named DTO classes, validation pipes, and module-specific request and response contracts for domain operations.

## FastAPI response shape

The FastAPI service currently returns one simple structured object from the health endpoint. This object is an inline response shape, not a named Pydantic model or persisted entity, and represents only one response among the AI service’s broader set of validated models.

### Implemented shape

<CodeGroup tabs="Python">

```python
@app.get("/health")
def health():
    return {"status": "ok"}
```

</CodeGroup>

The AI service now defines Pydantic models for agent review, including `ReviewWorkflowRequest`, `ReviewFinding`, `ReviewWorkflowResponse`, `RequirementVerdict`, `RequirementCoverage`, and `EvidenceAxis`. It also defines models for agent verification, credits usage, and other functional areas of the service.

### Classification

- **Kind**: Inline response shape
- **Named model**: None for this health response; numerous named Pydantic models exist across the AI service
- **Persistence-backed**: No for this health response; the service communicates with persisted application data through service APIs
- **Relationships**: None found in this health response
- **Validation rules**: None found in this health response; Pydantic models validate functional request and response payloads

### Response fields

<ResponseField name="status" field-type="string" required="true">

Health state returned by the endpoint. The implemented handler returns `ok`.

</ResponseField>

### Notes

The service uses Pydantic `BaseModel` classes for functional request and response validation. The health route does not attach a response model and returns its object directly from the route handler.

## Validation schema and DTO status

The repository implements named validation layers in both services. The NestJS API uses class-validator DTOs with validation pipes, while the FastAPI service uses Pydantic `BaseModel` classes for request and response validation.

### NestJS API

- DTO classes define request and response contracts across auth, agents, marketplace, payments, bounties, builder, and referrals
- `class-validator` decorators define field-level validation rules
- Validation pipes apply DTO validation to API requests
- Domain modules include DTOs for signup, login, OTP, password reset, publishing, reviews, verification, marketplace operations, payments, bounties, builder tools, and referrals

### FastAPI service

- Pydantic `BaseModel` classes define validated request and response payloads
- Agent review models represent review requests, findings, workflow responses, requirement verdicts, requirement coverage, and evidence axes
- Additional Pydantic models cover agent verification, credits usage, and other AI service operations

## Migration status

Supabase migrations are organized in `apps/api/supabase/migrations/` and include both SQL schema files and Python data migration scripts. Migration numbers range from `001` to `053`, with some numbers containing multiple migration subjects, such as agent share links and review run evidence under `046`.

### Summary

- Supabase migrations define the PostgreSQL persistence layer
- Migration files include SQL schema changes and Python data migration scripts
- Migration numbers range from `001` through `053`
- Some migration numbers contain multiple subjects, including agent share links and review run evidence under `046`
- Migration coverage includes profiles, workflows, session flow states, bounties, builders, published workflows, agent verification runs, agent reviews, agent runs, referrals, referral earnings, builder reports, payments, subscriptions, payouts, notifications, and related entities

### Current implication

The repository has an implemented database schema and migration history to evolve. New domain features can add or modify persisted structures through the Supabase migration workflow, while API and AI service models define the contracts used to access those features.

## Gaps and implications

The current codebase includes persistence, domain models, validation schemas, and migration history, but the model layer continues to evolve as features mature. The API and AI service expose different model sets because each service owns contracts for its own responsibilities.

- **Evolving domain models**: Entity definitions and DTOs will continue to change as workflows, agents, payments, reviews, and other features mature.
- **Distributed service contracts**: Shared contracts between the NestJS API and FastAPI service are managed through API-to-service communication rather than a shared schema package.
- **Migration coordination**: Changes to persisted entities require corresponding Supabase migrations and compatible updates to the API or AI service models.
- **Validation coverage varies by boundary**: Named DTOs and Pydantic models cover structured service operations, while simple health endpoints continue to use inline response objects.
- **Cross-service reuse remains limited**: The repository does not currently centralize all API and AI service contracts in one reusable schema package.

<Callout kind="danger">

Treat the health response objects as endpoint-local shapes. The broader DTO, Pydantic, and Supabase model layers define the application’s domain and service contracts, but individual response shapes should not be interpreted as complete representations of those models.

</Callout>
