## Overview

The AIGravity core repository defines response shapes for health endpoints, a builder profile response shape backed by database queries, and database tables for creator earnings and pricing configuration. The builder profile response shape, `BuilderView`, aggregates data from the `builders` table and the `creator_earnings_ledger` table to report lifetime earnings.

The response shapes and database tables documented here were identified through code analysis of the builder profile service, Supabase service, and charges service.

<Callout kind="info">

This reference inventories what is present in the checked-in repository today. It does not describe planned architecture, intended schemas, or future database work.


</Callout>

## Persistence and migration status

The builder profile and billing features use Supabase as their data store. The Supabase service client provides methods to read from the `builders`, `creator_earnings_ledger`, and `pricing_config` tables. No ORM-based migration system is used — table structures are managed at the database level.

Migration infrastructure is also absent. No `migrations` directory, ORM-managed migration history, or SQL migration files were found in the analyzed code.

### Repository-level signals

- The NestJS API exposes a single health controller with an inline object response.
- The FastAPI service exposes a single health endpoint with an inline object response.
- `pydantic` is present as a Python dependency, but no `BaseModel` classes are defined.
- The repository README describes shared schemas and database work as planned rather than implemented.

## Builder profile response shape (BuilderView)

The `BuilderView` interface is the serialized response body for both `GET /builders/me` and `PATCH /builders/me`. It aggregates data from the `builders` table and the `creator_earnings_ledger` table to report lifetime earnings.

### Implemented shape

<CodeGroup tabs="TypeScript">

```ts
interface BuilderView {
  userId: string;
  currency: string;
  totalEarnings: number;             // legacy, always 0
  lifetimeEarningsCredits: number;   // from creator_earnings_ledger
  lifetimeEarningsUsd: number;       // lifetimeEarningsCredits / 100
  createdAt: string;
  updatedAt: string;
}
```

</CodeGroup>

### Classification

- **Kind** — Response shape (interface)
- **Named entity or DTO** — BuilderView interface
- **Persistence-backed** — Yes, reads from `builders` and `creator_earnings_ledger` tables
- **Relationships** — Aggregates builder profile data with ledger entries
- **Validation rules** — Currency field validated through `UpdateBuilderProfileDto`

### Response fields

<ResponseField name="userId" field-type="string" required="true">

Unique identifier for the builder user.


</ResponseField>

<ResponseField name="currency" field-type="string" required="true">

Display currency code for the builder's earnings.


</ResponseField>

<ResponseField name="totalEarnings" field-type="number" required="true" deprecated="true">

Legacy earnings column. Always returns `0` because no code path writes to this field. Use `lifetimeEarningsCredits` and `lifetimeEarningsUsd` instead.


</ResponseField>

<ResponseField name="lifetimeEarningsCredits" field-type="integer" required="true">

Total credits earned by the builder, summed from the `creator_earnings_ledger` table. Includes positive earnings and negative refund reversals. One credit equals `0.01` USD.


</ResponseField>

<ResponseField name="lifetimeEarningsUsd" field-type="number" required="true">

Lifetime earnings in USD, computed as `lifetimeEarningsCredits` divided by `100`.


</ResponseField>

<ResponseField name="createdAt" field-type="string" required="true">

ISO 8601 timestamp when the builder profile was created.


</ResponseField>

<ResponseField name="updatedAt" field-type="string" required="true">

ISO 8601 timestamp when the builder profile was last updated.


</ResponseField>

### Notes

<Callout kind="info">

The `totalEarnings` field reads from the `builders.total_earnings` column, which is never written to and always returns `0`. The `lifetimeEarningsCredits` field is computed by summing all `credits_earned` rows in `creator_earnings_ledger` for the builder's user ID. If the ledger table is unavailable, the endpoint gracefully returns `0` rather than erroring.


</Callout>

## creator_earnings_ledger table

The `creator_earnings_ledger` table is the source of truth for builder earnings. Each row records the credits earned by a creator for a specific run charge.

### Table columns

<ParamField body="creator_id" param-type="UUID" required="true" show-location="false">

The builder's user ID.


</ParamField>

<ParamField body="agent_id" param-type="UUID" required="true" show-location="false">

The published workflow the run was for.


</ParamField>

<ParamField body="run_charge_id" param-type="UUID" required="true" show-location="false">

Foreign key to the run charge record.


</ParamField>

<ParamField body="credits_earned" param-type="numeric" required="true" show-location="false">

Credits earned for this run. Positive values record earnings, and negative values record refund reversals.


</ParamField>

### Constraints

<Callout kind="info">

A unique constraint prevents double-crediting: `UNIQUE(run_charge_id) WHERE credits_earned > 0`. This ensures each run charge can only produce one positive earnings entry.


</Callout>

### Read path

The `SupabaseService.getCreatorEarningsCredits` method queries this table by `creator_id` and sums all `credits_earned` values. This sum is returned as `lifetimeEarningsCredits` in the `BuilderView` response.

## pricing_config table

The `pricing_config` table stores runtime-configurable billing parameters as key-value rows. Two entries control the creator split behavior.

### Configuration entries

<ParamField body="platform_share_pct" param-type="integer via value_int" required="true" show-location="false">

Platform's share of the creator split as a percentage. The creator earns `100` minus this value. Valid range is `0` through `100`. If the row is absent, the application falls back to `80`.


</ParamField>

<ParamField body="creator_share_basis" param-type="text via value_text" required="true" show-location="false">

Determines how the creator's share is calculated. `gross` means the share is a percentage of the full run charge. `margin` means the share is a percentage of the charge minus the measured LLM cost. If the row is absent, the application falls back to `gross`.


</ParamField>

### Behavior

<Callout kind="info">

No database migration is required to change these values — they are plain `pricing_config` rows. The application reads them at charge time and falls back to defaults, `80` percent platform share and `gross` basis, when the rows are absent.


</Callout>

## Gaps and implications

The current codebase exposes service health and builder earnings data, but it still uses a narrow set of response shapes and direct database access patterns. That has several practical implications for anyone reading the repository as a backend reference.

- **Builder profile and earnings data are defined as response shapes (`BuilderView`) rather than ORM entities** — the Supabase client handles persistence directly.
- **No validation contract** — Request and response validation rules are not formalized beyond the builder profile update DTO.
- **No migration history** — Schema changes cannot be tracked in the repository because no checked-in migration layer exists.
- **Limited reuse across services** — Shared contracts are not implemented as reusable schema packages.

<Callout kind="info">

The `BuilderView` response shape and `creator_earnings_ledger` table are the current source of truth for builder earnings. The legacy `totalEarnings` field should not be used for any earnings calculations.


</Callout>
