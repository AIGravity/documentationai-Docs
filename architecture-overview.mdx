## Overview

Gravity is a polyglot monorepo for an AI-agent and workflow marketplace. Three independently runnable applications live under `apps/`: a Remix frontend at `apps/web`, a NestJS API at `apps/api`, and a FastAI service at `apps/ai-service`. The platform includes authentication, an agent marketplace, billing and subscriptions, agent quality review, ActivePieces-powered workflow execution, and cross-service integration between the API and AI service.

## Top-level repository structure

The repository root contains the orchestration, build, and operational layers that tie the three applications together.

- `.github/`
  - `.github/workflows/web.yml`
  - `.github/workflows/api.yml`
  - `.github/workflows/ai-service.yml`
- `apps/`
  - `apps/web`
  - `apps/api`
  - `apps/ai-service`
- `scripts/`
  - `scripts/bootstrap.sh`
  - `scripts/version-bump.sh`
- `README.md`
- `package.json`
- `pnpm-lock.yaml`
- `pnpm-workspace.yaml`
- `tsconfig.base.json`
- `turbo.json`

A few root files define the monorepo shape directly:

- `pnpm-workspace.yaml` registers `apps/*` and `packages/*` as workspaces.
- `turbo.json` configures a minimal task graph for `dev` and `build`.
- `package.json` defines root development commands that delegate into the app workspaces.
- `scripts/bootstrap.sh` installs toolchains and service dependencies across JavaScript, Bun, and Python environments.

## Monorepo orchestration layer

The repo uses `pnpm` workspaces for package coordination and Turborepo primarily as a process orchestrator. At the current maturity level, Turborepo is not modeling a deep dependency graph because there are no shared internal packages yet.

The root `package.json` defines workspace-level commands such as `dev:web`, `dev:api`, and `dev`. Those commands establish the intended local development pattern: run services independently when needed, or run them in parallel through Turbo.

<Callout kind="alert">

The root script `dev:py` points to `apps/py-service`, but the actual Python service lives at `apps/ai-service`. That script is stale relative to the repository tree.

</Callout>

## Service architecture

### `apps/web`: Remix frontend

The frontend provides the web interface for the Gravity platform. The root layout in `apps/web/app/root.tsx` installs providers for authentication, sessions, Stripe checkout, PostHog analytics, Sentry error tracking, support chat, and bug reporting. Routes cover authentication, onboarding, marketplace, builder tools, admin dashboards, billing, referrals, subscriptions, and settings.

### `apps/api`: NestJS API on Bun

The API is the NestJS backend running on Bun. It boots from `apps/api/src/main.ts` with environment-driven CORS, global validation, Swagger at `/api/docs`, Sentry, and PostHog.

The root module imports `ConfigModule` and many feature modules, including Auth, Chat, Agents, Marketplace, ActivePieces, Payments (credits, payouts, subscriptions, charges), Earnings, AdminBilling, Referrals, Bounties, Candidates, RequestedAgents, Leaderboard, Telemetry, Notifications, and Health. The API calls the AI service for chat, verification, and review operations.

### `apps/ai-service`: FastAPI Python service

The AI service is the FastAPI-based AI layer. It exposes `/health`, `/chat`, `/verification/*`, `/agent-review/*`, `/internal/*`, and `/credits/*` endpoints.

The service orchestrates LLM calls through OpenRouter and OpenAI, manages conversation memory via Redis, persists data through Supabase, provides agent search through Typesense, and runs guardrails through AWS Bedrock.

## Module relationships and service boundaries

The services are now well-layered. The NestJS API follows a controller-to-service-to-repository pattern with feature modules. The FastAPI service splits routes into routers for verification, agent review, and credits, with service classes for intent, agent search, memory, and sessions.

The frontend separates route modules from API clients and domain hooks. Cross-service wiring is implemented: the API calls the AI service for chat, verification, and review operations via `AI_SERVICE_URL`. The API integrates with ActivePieces via REST and direct Postgres access. The frontend calls the API via `VITE_API_URL`.

### Current cross-service wiring

The primary service relationships are implemented across the platform:

- The frontend calls the API through `VITE_API_URL`.
- The API calls the AI service through `AI_SERVICE_URL` for chat, verification, and review operations.
- The API integrates with ActivePieces through REST and direct Postgres access.

## Persistence, middleware, auth, and external services

### Database and persistence

Gravity uses multiple persistence and infrastructure systems for platform data, workflow execution, search, and caching:

- Supabase and Postgres store platform data, including identity, catalog, billing, chat, reviews, referrals, and marketplace metadata.
- ActivePieces Postgres stores flows, runs, and connections.
- Typesense provides agent search.
- Redis provides session caching.

### Middleware

Cross-cutting middleware and providers are implemented across the services:

- The API uses global validation with a whitelist, raw body handling for webhook HMAC verification, Sentry, and PostHog.
- The frontend installs authentication, session, Stripe checkout, PostHog, Sentry, support chat, and bug reporting providers.
- The AI service performs guardrail checks, execution tracking, and model pricing synchronization.

### Authentication and authorization

Authentication uses Supabase email and password authentication, Google OAuth with PKCE, JWT verification and refresh, and user-type guards for creators, business users, candidates, and admins.

### External services and integrations

Gravity integrates with the following external systems:

- OpenRouter and OpenAI for LLM operations
- AWS Bedrock for guardrails
- Typesense for search
- Redis for caching
- Gemini for embeddings
- Stripe, Razorpay, and PayPal for payments
- ActivePieces for workflow execution
- Composio for tool connections
- Sentry and PostHog for observability
- SMTP for notifications

## Build, release, and deployment tooling

The operational layer is more mature than the application layer. Each app has enough tooling to build, version, containerize, and publish independently.

### Local setup

`scripts/bootstrap.sh` checks for `pnpm`, `bun`, and `uv`, then installs dependencies for the JavaScript and Python services. That script reflects the repo's polyglot design: each app uses the native tooling expected for its runtime.

### Versioning

Each app has a local `VERSION` file:

- `apps/web/VERSION`
- `apps/api/VERSION`
- `apps/ai-service/VERSION`

`scripts/version-bump.sh` updates those version files, establishing per-service version management rather than one monorepo-wide application version.

### Containers and CI/CD

Each service has its own Dockerfile:

- `apps/web/Dockerfile`
- `apps/api/Dockerfile`
- `apps/ai-service/Dockerfile`

Each service also has its own GitHub Actions workflow:

- `.github/workflows/web.yml`
- `.github/workflows/api.yml`
- `.github/workflows/ai-service.yml`

Those workflows handle build and verification steps, version generation, Docker image publishing to GitHub Container Registry, and GitHub release creation. The deployment sections are present as placeholders, which means release automation is implemented further than environment deployment.

## Notable gaps and inconsistencies

The API Dockerfile exposes port 3000 while the application defaults to 3001. The `PORT` environment variable reconciles this in deployment.

The root `package.json` `dev:py` script may still reference the old `py-service` path. Verify that it points to `apps/ai-service`.

## What this architecture means today

Gravity is a feature-complete platform with clear service boundaries, cross-service integration, persistence, authentication, and external integrations. The API and AI service collaborate on chat, verification, and review workflows. The marketplace runs on ActivePieces with version-gated compatibility. Billing supports credits, subscriptions, payouts, and referrals. The agent review pipeline provides quality assurance with evidence-axis scoring.
