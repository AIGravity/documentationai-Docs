## Overview

The AI service is a FastAPI application that hosts the agent recommendation engine alongside a health check endpoint. It manages dependencies with uv, integrates with Gemini for query embeddings and Typesense for vector search, and packages for container deployment. The recommendation engine ranks agents based on semantic similarity and user-selected preferences including platforms, agent types, and tools.

<Callout kind="info">

The agent recommendation engine uses Gemini for query embeddings and Typesense for vector search. Ranking applies a soft-blend formula that combines semantic distance with platform, agent type, and tool-matching signals to surface the most relevant agents.










</Callout>

## Current scope

The service combines a FastAPI foundation with an agent recommendation engine. The foundation includes a direct app bootstrap, a health check route, Python 3.14 tooling, and automation for linting, versioning, tagging, and container publishing. The recommendation engine searches for agents using semantic vector search and ranks them with a soft-blend formula that considers platform, agent type, and tool overlap with the user's selections.

## Bootstrap in main.py

The application starts directly in `apps/ai-service/main.py`. App creation happens at module import time, and route registration happens inline with a decorator on the FastAPI app instance.

<CodeGroup tabs="main.py,Notes">

```python
from fastapi import FastAPI

app = FastAPI()


@app.get("/health")
def health():
    return {"status": "ok"}
```

```text
Grounded bootstrap details:

- app = FastAPI() is defined at the top level
- /health is registered with @app.get("/health")
- the handler is synchronous: def health()
- no APIRouter usage appears in the analyzed files
- no middleware, startup hooks, shutdown hooks, or dependency wiring appear
```

</CodeGroup>

The startup path is straightforward because app initialization remains lightweight. The agent recommendation engine is implemented as a separate service layer, so the entry point stays focused on bootstrap and health checking while recommendation logic lives in dedicated service modules.

<CodeGroup tabs="Route,Response">

The endpoint does not define a response model, custom status code, tags, auth requirement, or explicit error handling. It serves as a basic process health check independent of the recommendation engine.

## Agent recommendation

The AI service includes an agent recommendation engine that searches for and ranks agents based on a user's query and selected preferences. When a user submits a query along with selected platforms, agent types, and tools, the service retrieves candidate agents through semantic vector search and ranks them using a soft-blend formula.

### How ranking works

Ranking combines semantic similarity with preference matching:

1. **Semantic similarity** — The primary signal. Agents are retrieved based on how closely their descriptions match the user's query. Agents that are too dissimilar are filtered out by a distance threshold.
2. **Soft-blend signals** — Each matching preference adds a small boost to the agent's score:
   - Matching platforms
   - Matching agent types
   - Matching tools — the user's selected tools that overlap with the agent's supported tools

The blend weight is intentionally small so that semantic similarity dominates ranking. The soft-blend only breaks ties between agents that are semantically similar, ensuring that an agent using the tools a user selected ranks above an otherwise-equivalent agent that does not.

<Callout kind="info">

Tool selection now influences agent ranking. When a user selects tools from the tool picker, agents that support those tools receive a slight ranking boost. This helps surface agents that are more relevant to the user's specific tool choices.






</Callout>

### Response shape

Each recommended agent in the response includes a `matched_tools` array listing which of the user's selected tools the agent supports. This array is always present, even when empty, so consumers can inspect which tools contributed to a ranking boost.

## Python environment and dependency management

Python and package management are consistent across local tooling, project metadata, and the lockfile. The service requires Python `>=3.14`, uses uv for dependency resolution, and pins resolved package versions in `uv.lock`.

<CodeGroup tabs="pyproject.toml,uv.lock,.python-version">

```toml

name = "ai-service"
version = "0.1.0"
requires-python = ">=3.14"

    "uvicorn>=0.41.0",

    "pytest>=8.0.0",
```

The service integrates with Gemini for query embeddings and Typesense for vector search to support the agent recommendation engine. The dependency list shown above reflects the base FastAPI foundation; additional packages for these external integrations are managed through the same uv workflow.

## Run locally

The repository does not include a substantive local guide for this service, so the usable commands are implied by the CI workflow and Docker runtime command. Run these commands from `apps/ai-service`.

<CodeGroup tabs="Install and start,Quality checks">

```bash
uv python install
uv sync
uv run uvicorn main:app --host 0.0.0.0 --port 8001
```


</CodeGroup>

If startup succeeds, Uvicorn listens on port `8001`. A successful request to `GET /health` returns `{"status": "ok"}`.

Tests are not part of the active CI path today. The workflow includes a commented-out pytest step, so pytest is declared as a dev dependency but is not currently enforced in automation.

## Docker packaging

The service image uses a multi-stage Docker build based on `python:3.14-slim`. The builder stage installs production dependencies with uv, and the runtime stage copies the virtual environment and application source before starting Uvicorn.

<CodeGroup tabs="Dockerfile">

```dockerfile
FROM python:3.14-slim AS builder
WORKDIR /app
COPY --from=ghcr.io/astral-sh/uv:latest /uv /uvx /bin/
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev

FROM python:3.14-slim
WORKDIR /app
COPY --from=builder /app/.venv /app/.venv
COPY . .
ENV PATH="/app/.venv/bin:$PATH"
EXPOSE 8001
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8001"]
```

</CodeGroup>

A few runtime details are explicit in the Dockerfile. The image exposes port `8001`, prepends `/app/.venv/bin` to `PATH`, and starts the app with `uvicorn main:app --host 0.0.0.0 --port 8001`.

The Dockerfile does not define a non-root user, healthcheck instruction, environment-specific configuration, or deployment-time setup. It packages and runs the service as-is, including the agent recommendation engine and its external service integrations.

## CI workflow

The GitHub workflow runs when changes affect `apps/ai-service/**` or `.github/workflows/ai-service.yml` on pushes and pull requests targeting `main` or `dev`. Its build job works from `apps/ai-service`, installs uv, installs Python, syncs dependencies, and runs Ruff formatting and lint checks.

Publishing happens only on push events. On `main`, the workflow reads `apps/ai-service/VERSION`, bumps the version according to commit message rules, creates a Git tag in the format `ai-service-v<version>`, publishes `ghcr.io/<owner>/gravity-ai-service`, applies the generated version tag and `latest`, and creates a GitHub Release.

On `dev`, the workflow generates a development version using the base version, timestamp, and short SHA. It tags the repository, publishes the same image with the generated version tag and `dev-latest`, and also adds a SHA tag.
