## Overview

The AI service is now a full-featured FastAPI application with 30 endpoints covering verification, agent review, chat interactions, embeddings, requested agents, credits, and administration.

The service exposes the AI interaction layer through several API areas:

- **Verification:** 11 endpoints under `/verification`
- **Agent review:** 1 endpoint under `/agent-review`
- **Credits:** 6 endpoints under `/credits`
- **Internal operations:** Guardrail checks, requested agents, embeddings, and agent lookup
- **Administration:** Pricing updates through `/admin/pricing`
- **Chat:** Model-backed interactions through `POST /chat`

The service continues to run on port `8001`.

## Current scope

The service coordinates AI interactions and supporting workflows through a FastAPI application. Its endpoint surface includes chat requests, verification flows, agent review, credit management, embeddings, requested-agent discovery, agent lookup, guardrail checks, and administrative pricing updates.

The service also reports whether chat is available based on LLM configuration. Requests without an available LLM API key receive a `503` response, while invalid request payloads receive FastAPI's standard `422` validation response.

The full endpoint and schema details are available on the [AI Service API reference](/api-reference/ai-service).

## Bootstrap in main.py

The application starts directly in `apps/ai-service/main.py`. App creation happens at module import time, and the application registers the feature routers for verification, agent review, and credits alongside the service-level endpoints.

<CodeGroup tabs="main.py,Notes">

```python
from fastapi import FastAPI

app = FastAPI()

app.include_router(verification_router, prefix="/verification")
app.include_router(agent_review_router, prefix="/agent-review")
app.include_router(credits_router, prefix="/credits")


@app.get("/health")
def health():
    return {
        "status": "healthy",
        "service": "Gravity AI Interaction Layer",
        "version": "1.0.0",
        "chat_available": chat_available,
    }
```

```text
Bootstrap details:

- app = FastAPI() is defined at the top level
- the verification router is mounted at /verification
- the agent review router is mounted at /agent-review
- the credits router is mounted at /credits
- service-level endpoints include /health and /chat
- internal endpoints support guardrails, requested agents, embeddings, and agent lookup
- the admin pricing endpoint is mounted at /admin/pricing
```

</CodeGroup>

The application now separates major feature areas into three routers while retaining service-level, internal, and administrative endpoints in the application surface. The router structure keeps verification, review, and credit workflows grouped independently from chat and internal AI operations.

## Health endpoint

`GET /health` reports the service status, identity, version, and whether chat requests can reach an LLM provider.

<CodeGroup tabs="Route,Response">

```python
@app.get("/health")
def health():
    return {
        "status": "healthy",
        "service": "Gravity AI Interaction Layer",
        "version": "1.0.0",
        "chat_available": True,
    }
```

```json
{
  "status": "healthy",
  "service": "Gravity AI Interaction Layer",
  "version": "1.0.0",
  "chat_available": true
}
```

</CodeGroup>

The `chat_available` field is a boolean. It indicates whether the service has the configuration required to process chat requests through an LLM provider.

## Chat endpoint

`POST /chat` accepts a user message and session context, then returns an interaction response containing an execution identifier. The request can optionally select an agent and tools.

<CodeGroup tabs="Request,Response">

```json
{
  "user_id": "usr_a1b2c3d4",
  "session_id": "sess_7f8e9d0a",
  "message": "Summarize the latest account activity.",
  "agent_id": "agent_account_assistant",
  "selected_tools": [
    "account_activity"
  ],
  "submit_tools": true
}
```

```json
{
  "execution_id": "exec_4c7d8e9f",
  "status": "completed"
}
```

</CodeGroup>

The request requires `user_id`, `session_id`, and `message`. `agent_id`, `selected_tools`, and `submit_tools` are optional fields used to control agent and tool selection.

If the service does not have an LLM API key, the endpoint returns `503 Service Unavailable` instead of attempting to process the request. FastAPI returns `422 Unprocessable Entity` when the request body fails `ChatRequest` validation.

## Feature routers and internal endpoints

The service groups its primary workflows into three routers:

- **`/verification`:** 11 endpoints for verification workflows
- **`/agent-review`:** 1 endpoint for agent review
- **`/credits`:** 6 endpoints for credit operations

Internal endpoints support the AI interaction flow without exposing those operations as public feature routers:

- **`/internal/guardrail/check`:** Evaluates a request against guardrail rules.
- **`/internal/requested-agents`:** Provides six endpoints for requested-agent workflows.
- **`/internal/embed`:** Generates embeddings.
- **`/internal/agents/index`:** Indexes agent data.
- **`/internal/agents/{agent_id}`:** Provides three agent-specific operations.

The administrative endpoint `POST /admin/pricing` updates pricing data and requires an `x-admin-token` header.

For request fields, response schemas, authentication details, and status codes, use the [AI Service API reference](/api-reference/ai-service).

## Run locally

The repository does not include a substantive local guide for this service, so the usable commands are implied by the CI workflow and Docker runtime command. Run these commands from `apps/ai-service`.

<CodeGroup tabs="Install and start,Quality checks">

```bash
uv python install
uv sync
uv run uvicorn main:app --host 0.0.0.0 --port 8001
```

```bash
uv run ruff format --check .
uv run ruff check .
```

</CodeGroup>

If startup succeeds, Uvicorn listens on port `8001`. A successful request to `GET /health` returns a response with `"status": "healthy"` and a boolean `chat_available` field.

Tests are not part of the active CI path today. The workflow includes a commented-out pytest step, so pytest is declared as a dev dependency but is not currently enforced in automation.

## Docker packaging

The service image uses a multi-stage Docker build based on `python:3.14-slim`. The builder stage installs production dependencies with uv, and the runtime stage copies the virtual environment and application source before starting Uvicorn.

<CodeGroup tabs="Dockerfile">

```dockerfile
FROM python:3.14-slim AS builder
WORKDIR /app
COPY --from=ghcr.io/astral-sh/uv:latest /uv /uvx /bin/
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev

FROM python:3.14-slim
WORKDIR /app
COPY --from=builder /app/.venv /app/.venv
COPY . .
ENV PATH="/app/.venv/bin:$PATH"
EXPOSE 8001
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8001"]
```

</CodeGroup>

A few runtime details are explicit in the Dockerfile. The image exposes port `8001`, prepends `/app/.venv/bin` to `PATH`, and starts the app with `uvicorn main:app --host 0.0.0.0 --port 8001`.

The Dockerfile does not define a non-root user, healthcheck instruction, environment-specific configuration, or deployment-time setup. It packages and runs the current minimal service as-is.

## CI workflow

The GitHub workflow runs when changes affect `apps/ai-service/**` or `.github/workflows/ai-service.yml` on pushes and pull requests targeting `main` or `dev`. Its build job works from `apps/ai-service`, installs uv, installs Python, syncs dependencies, and runs Ruff formatting and lint checks.

Publishing happens only on push events. On `main`, the workflow reads `apps/ai-service/VERSION`, bumps the version according to commit message rules, creates a Git tag in the format `ai-service-v<version>`, publishes `ghcr.io/<owner>/gravity-ai-service`, applies the generated version tag and `latest`, and creates a GitHub Release.

On `dev`, the workflow generates a development version using the base version, timestamp, and short SHA. It tags the repository, publishes the same image with the generated version tag and `dev-latest`, and also adds a SHA tag.
