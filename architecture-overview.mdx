## Overview

Gravity is a polyglot monorepo with three independently runnable applications: a Remix frontend, a NestJS API, and a FastAPI AI service. The repository provides workspace orchestration, per-service containerization, semantic versioning, and GitHub Actions pipelines.

The platform has matured beyond its original scaffold. The API now provides Supabase bearer-token authentication, Supabase-backed persistence, cross-service calls to the AI service, and domain endpoints across the product. The AI service provides feature-complete AI platform capabilities, while the frontend remains close to a starter application rather than an integrated product UI.

<Callout kind="info">

The workspace configuration includes a location for shared packages, and the README describes planned shared packages, but shared package usage is not yet a central part of the current architecture.

</Callout>

## Top-level repository structure

The repository root contains the orchestration, build, and operational layers that tie the three applications together.

- GitHub Actions workflows for the web, API, and AI services
- Three application workspaces:
  - Remix frontend
  - NestJS API
  - FastAPI AI service
- Bootstrap and version-management scripts
- Root workspace, TypeScript, lockfile, and Turbo configuration

The root configuration defines the monorepo shape directly:

- The workspace configuration registers the application workspaces and the intended shared-package workspace.
- Turbo configures the task graph for development and builds.
- Root commands delegate development tasks into the application workspaces.
- Bootstrap tooling installs dependencies across JavaScript, Bun, and Python environments.

## Monorepo orchestration layer

The repo uses `pnpm` workspaces for package coordination and Turborepo primarily as a process orchestrator. Shared internal packages are planned, but the current dependency graph is driven mostly by the independently runnable applications.

Root commands define workspace-level development flows such as `dev:web`, `dev:api`, and `dev`. These commands establish the intended local development pattern: run services independently when needed, or run them in parallel through Turbo.

<Callout kind="alert">

The root Python development command still targets the older `py-service` name, while the active Python application is named `ai-service`. Update the command before relying on it for local development.

</Callout>

## Service architecture

### Web frontend

The web application is the user-facing frontend. It uses Remix with Vite and React, and the current code remains close to a starter application rather than an integrated product UI.

The frontend provides the document shell, global styles, font links, error handling, and nested route rendering. Its current routes render the same welcome experience and do not yet provide the product's full application workflow.

There are no implemented route loaders, route actions, session handling, data-fetching helpers, or API client abstractions in the current frontend architecture. The frontend is configured to communicate with the API, but the feature-level request flows remain largely unimplemented.

The active frontend stack includes:

- Remix
- Vite
- Tailwind CSS
- React
- TypeScript path support

The API allows browser requests from the local frontend origin, establishing the expected browser-to-API relationship. The frontend has not yet implemented the corresponding product integrations at the same depth as the backend services.

### NestJS API

The NestJS API is the primary application backend. It uses NestJS for the HTTP framework, Bun as the runtime for local development and execution, and TypeScript compilation for production builds.

The API uses a global `/api` prefix for application routes. Its domain modules cover authentication, chat, agents, marketplace, apps, automations, builder workflows, bounties, candidates, payments, referrals, leaderboards, telemetry, administrative billing, and webhooks.

Authentication is handled through `SupabaseAuthGuard`, with `AdminGuard` protecting administrative routes. A global `ValidationPipe` enforces whitelisted properties, rejects unknown properties, and transforms incoming values before they reach application logic.

The API exposes Swagger documentation at `/api/docs`. Health endpoints remain outside the application prefix at `/health` and `/`.

The API now follows a controller-to-service structure organized around domain modules. It is an application backend with authentication, persistence, billing, workflows, and integrations rather than a health-check-only shell.

### FastAPI AI service

The AI service provides the platform's AI capabilities through a FastAPI application. It supports chat interactions, content guardrails, text embeddings, agent indexing, requested-agent management, agent verification with server-sent event streaming, agent review analysis, and credit metering.

The service organizes related behavior into structured router groups for `/verification`, `/agent-review`, and `/credits`. Pydantic models provide request validation, while separate service logic handles AI operations, indexing, verification, review analysis, and usage tracking.

The Python service uses FastAPI, Pydantic, and Uvicorn, along with integrations for AI model providers and supporting data services. Its runtime surface includes both public-facing AI interactions and internal endpoints used by the NestJS API.

<Callout kind="info">

The AI service integrates with language model providers and applies content guardrails to evaluate safety before supported AI operations proceed.

</Callout>

## Entry points and request handling

Each application has a clear entry point, and request handling now extends beyond health checks across the API and AI service.

### Web routes

The frontend exposes the root route and a home route through its Remix route modules. Both routes currently render the same welcome component.

The frontend does not yet provide the complete product route structure, session handling, or backend request flows expected from the mature API and AI services.

### API routes

The API uses a global `/api` prefix for application routes. Major route groups include:

- `/api/auth` for authentication
- `/api/chat` for chat sessions
- `/api/agents` for agent publishing and verification
- `/api/marketplace` for workflow discovery and execution
- `/api/credits` for credit billing
- `/api/subscriptions` for subscription billing
- `/api/payments` for payment operations
- `/api/bounties` for bounty workflows
- `/api/apps` for app connections
- `/api/automations` for automation workflows
- `/api/webhooks` for payment webhooks

Health endpoints remain at the root:

- `GET /health`
- `GET /`

### AI service routes

The AI service exposes health, interaction, internal processing, and structured router endpoints.

- `GET /health`: Service health and chat availability
- `POST /chat`: AI chat interactions
- `POST /internal/guardrail/check`: Content safety evaluation
- `POST /internal/embed`: Text embedding generation
- `POST /internal/agents/index`: Agent indexing
- `/verification`: Agent verification with SSE streaming
- `/agent-review`: Workflow submission review
- `/credits`: Execution usage and metering

## Module relationships and service boundaries

The repository maintains clear top-level separation between the frontend, NestJS API, and FastAPI AI service. The API follows a controller-to-service pattern organized into domain modules, while the AI service splits related endpoints into routers with separate business logic.

The frontend remains less layered than the backend services. It has route modules and shared presentation code, but its API client, session, domain, and data-fetching layers are not yet implemented at the same depth.

The architecture is therefore both macro-separated and increasingly layered. The API and AI service contain explicit domain responsibilities, while the frontend remains the least mature part of the application structure.

### Current cross-service wiring

The API and AI service are integrated through explicit backend-to-backend flows.

- The NestJS API calls the AI service for chat interactions, content guardrail checks, and verification streaming.
- Both services use a shared Supabase database for persistence.
- The API proxies AI functionality through `/api/chat` and `/api/agents` endpoints.
- The API exposes product-facing routes while the AI service handles model interaction, indexing, verification, review, and metering concerns.

<Callout kind="alert">

Treat the current topology as three integrated services managed in one monorepo. The API and AI service have active cross-service flows, while the frontend remains only partially connected to the platform capabilities.

</Callout>

## Persistence, middleware, auth, and external services

### Database and persistence

Supabase is the primary database and authentication platform. It stores authentication records, user profiles, agents, marketplace workflows, bounties, credits, and other domain data used by the API.

The AI service uses Redis for conversation history and Typesense for agent search and retrieval. It also maintains database connections for credit metering and requested-agent persistence.

Persistence is therefore distributed by responsibility: Supabase holds core product and identity data, Redis supports conversational state, and Typesense supports search-oriented retrieval.

### Middleware

The NestJS API uses a global `ValidationPipe` to whitelist accepted properties, reject unknown properties, and transform incoming values. This establishes consistent request validation across the API's domain modules.

A global exception filter masks internal error details before responses reach clients. The filter preserves useful client-facing error information while preventing implementation details from leaking through API responses.

The AI service also validates request payloads through Pydantic models. Cross-service request handling includes the API's authentication, validation, exception handling, and provider-specific webhook verification flows.

### Authentication and authorization

The NestJS API uses `SupabaseAuthGuard` to authenticate bearer tokens issued through Supabase. `AdminGuard` protects routes that require administrative access, and the `@Public()` decorator marks routes that intentionally skip authentication.

Authentication endpoints support:

- Signup
- Login
- One-time password delivery and verification
- Google OAuth
- Password reset
- Session refresh

Webhook endpoints use provider signatures instead of bearer authentication. Stripe, PayPal, and Razorpay webhooks each rely on their provider-specific signature verification mechanisms.

### External services and integrations

Current external integrations include:

- Language model providers for chat, verification, and review
- Supabase for the database and authentication
- Redis for conversation history
- Typesense for agent search and retrieval
- ActivePieces for workflow automation
- Stripe, PayPal, and Razorpay for payments
- Google OAuth for authentication
- GitHub Container Registry for CI/CD image publishing

## Build, release, and deployment tooling

The operational layer is more mature than the frontend application layer. Each app has enough tooling to build, version, containerize, and publish independently.

### Local setup

Bootstrap tooling checks for `pnpm`, `bun`, and `uv`, then installs dependencies for the JavaScript and Python services. The setup reflects the repo's polyglot design: each app uses the native tooling expected for its runtime.

### Versioning

Each app has its own version file, and version-management tooling updates those files independently. The repository therefore uses per-service version management rather than one monorepo-wide application version.

### Containers and CI/CD

Each service has its own Dockerfile and GitHub Actions workflow. The workflows handle build and verification steps, version generation, Docker image publishing to GitHub Container Registry, and GitHub release creation.

The deployment sections remain placeholders, which means release automation is implemented further than environment deployment.

## Notable gaps and inconsistencies

A few repo details can mislead an architectural review unless they are called out directly.

### Shared packages are planned but absent

The workspace configuration includes a location for shared packages, and the README describes shared packages for types, UI, and configuration. Shared package usage is not yet a central part of the current codebase.

This gap matters because the intended contract-sharing architecture is not yet fully realized. API and AI integration exists through service endpoints and shared persistence, but shared workspace packages should not be assumed to provide the current source of truth for contracts or UI primitives.

### Script and naming drift around the Python service

The repository uses `ai-service` as the active Python service name, but some root-level development references still use the older `py-service` name. This inconsistency affects local development expectations and indicates that some repository tooling has not fully caught up with the current service naming.

### Testing exists mostly as intent

The Python service declares testing tooling, and the workflows include verification steps, but the repository does not yet show a test suite that matches the breadth of the API and AI service capabilities. The CI layer is prepared for broader testing, while coverage of the implemented application surface remains an area for continued development.

<Callout kind="info">

The strongest parts of the current architecture are its service boundaries, runtime separation, domain modules, authentication, persistence, cross-service integration, containerization, and release automation. The frontend remains the least mature component and is still close to a starter application.

</Callout>

## What this architecture means today

Gravity now has feature-complete platform services in its API and AI layers. The API provides authentication, persistence, domain modules, billing, workflows, and integrations, while the AI service provides chat, guardrails, indexing, verification, review, and metering capabilities with structured routers and model-provider integrations.

The frontend remains close to a starter application and has not yet caught up with the backend platform depth. The main architectural work ahead is to connect the frontend to the existing service capabilities and continue strengthening shared contracts, test coverage, and deployment environments.
