## Overview

AIGravity/core now includes a working data layer across both services. The NestJS API defines DTO classes with `class-validator` decorators for agent publishing, review submission, and AI-assisted previews, while the AI service defines Pydantic models for request and response validation.

Persistence is implemented through Supabase on PostgreSQL, with schema changes tracked in SQL migrations. Inline health responses still exist, but they now sit alongside named DTOs, validated service schemas, and persisted tables for published agents, reviews, leaderboard snapshots, and bounties.

<Callout kind="info">

The repository has evolved from endpoint-local response objects to a structured data layer with validated DTOs, Pydantic schemas, SQL migrations, and Supabase-backed persistence.


</Callout>

## Current model inventory summary

The repository now has an application data layer rather than only service scaffolding.

| Area | Current status |
| --- | --- |
| Named domain models | DTOs for agents, leaderboard, and bounties |
| ORM or database models | Supabase PostgreSQL schema managed through SQL migrations |
| DTO classes | `PublishAgentDto`, `ReviewSubmissionDto`, `PreviewCategoriesDto`, `VerifyAgentDto`, and related DTOs |
| Named validation schemas | Pydantic models in the AI service such as `GenerateCategoriesRequest` and `GenerateDescriptionResponse` |
| Migration files | SQL migrations including 027 through 033 and earlier |
| Inline response shapes | Health endpoints remain in both services |
| Persisted entities | `published_workflow_meta`, `pending_agent_reviews`, `rejected_agent_reviews`, `leaderboard_result`, `bounties` |

### Model-like definitions found

- **NestJS API DTOs** — request validation for publishing, review submission, previews, verification, leaderboard, and bounty-related flows
- **FastAPI Pydantic models** — request and response schemas for category generation, description generation, and verification workflows
- **Supabase persistence schema** — PostgreSQL tables managed through checked-in SQL migrations
- **Health endpoint responses** — inline response shapes still returned by the API and AI service health checks

## Persistence and migration status

The API service now uses Supabase as its primary database layer. PostgreSQL schema changes are stored as SQL migration files under `apps/api/supabase/migrations/` and applied through a TypeScript migration runner.

The AI service also works against persisted tables for features such as bounties and manages its own database interactions where needed. The repository no longer reflects a migration-free scaffold; it includes active schema evolution, persistence-backed workflows, and stored review and leaderboard records.

### Repository-level signals

- The NestJS API validates request payloads with DTO classes and `class-validator` decorators.
- Supabase migrations define and evolve the PostgreSQL schema used by the API.
- The AI service uses Pydantic `BaseModel` classes for request and response validation.
- Persisted records now exist for published agents, pending reviews, rejected reviews, frozen leaderboard results, and bounties.

## AI edit tracking

AI-assisted authoring now feeds directly into the persistence layer. When a builder uses Improve with AI on the customize-agent page, the generated text becomes the baseline that later publish and review-submission requests send in the `aiGenerated` field.

The server stores that baseline in dedicated database columns and computes an `ai_edited_fields` array. That array records which fields the builder changed before submitting, which makes the signal queryable without recomputing diffs at read time.

### Comparison rules

- **Text fields** are compared after whitespace normalization, so reflow alone does not count as an edit.
- **Array fields** are compared in order, so reordering workflow steps counts as an edit.
- **Missing AI baseline** means the field is never marked as edited.
- **Stored diff output** is a list of field names such as `["description", "workflow_steps"]`.

<Callout kind="info">

`NULL` in an AI baseline column is meaningful. It indicates the builder never used Improve with AI for that field, not that the value was later cleared.


</Callout>

## Database migrations

The migration system now tracks schema evolution for AI-assisted publishing, moderation, leaderboard freezes, and bounties.

### Migration 027 — AI Generated Content

Migration 027 adds five AI baseline columns to both `published_workflow_meta` and `pending_agent_reviews`. These columns preserve the original AI suggestion for each supported field.

<ResponseField name="ai_generated_name" field-type="text" required="false">

Nullable baseline for the AI-generated name.


</ResponseField>

<ResponseField name="ai_generated_description" field-type="text" required="false">

Nullable baseline for the AI-generated description.


</ResponseField>

<ResponseField name="ai_generated_problem_solved" field-type="text" required="false">

Nullable baseline for the AI-generated problem statement.


</ResponseField>

<ResponseField name="ai_generated_workflow_steps" field-type="jsonb" required="true">

Stored array of AI-generated workflow steps. Defaults to an empty array.


</ResponseField>

<ResponseField name="ai_generated_categories" field-type="jsonb" required="true">

Stored array of AI-generated categories. Defaults to an empty array.


</ResponseField>

### Migration 028 — AI Edited Fields

Migration 028 adds `ai_edited_fields` to both `published_workflow_meta` and `pending_agent_reviews`. The column stores a precomputed JSON array of field names changed by the builder relative to the stored AI baseline.

<ResponseField name="ai_edited_fields" field-type="jsonb" required="true">

Array of edited field names such as `["description", "workflow_steps"]`. Defaults to an empty array.


</ResponseField>

### Migration 032 — Leaderboard Results Table

Migration 032 creates the `leaderboard_result` table for frozen final standings after a competition season closes. The table stores season-level snapshots rather than recalculating rankings from mutable live data.

It includes columns for season, rank, workflow ID, workflow name, builder user ID, builder name, avatar URL, score, builder workflows, and prize. A unique constraint on `(season, workflow_id)` makes the freeze operation idempotent, and row-level security is enabled.

### Migration 033 — Rejected AI Generated

Migration 033 extends `rejected_agent_reviews` with the same six AI baseline and diff columns already used by published and pending review records. Auto-rejected and admin-rejected submissions therefore keep the same edit tracking signal as approved or in-review submissions.

### Bounties — Difficulty column

The `bounties` table now includes a `difficulty` text column. The accepted values are `easy`, `medium`, or `difficult`, and the field is returned by the bounty API response.

## NestJS API health response

The NestJS API still returns one inline response shape from the health endpoint. That response is now one of many shapes in the system rather than the only structured object in the codebase.

### Implemented shape

<CodeGroup tabs="TypeScript">

```ts
@Controller("health")
export class HealthController {
  @Get()
  getHealth() {
    return { status: "ok", service: "api" };
  }
}
```

</CodeGroup>

### Classification

- **Kind** — Inline response shape
- **Named entity or DTO** — Endpoint-local response, separate from the API DTO layer
- **Persistence-backed** — No
- **Relationships** — None
- **Validation rules** — None on the response object itself

### Response fields

<ResponseField name="status" field-type="string" required="true">

Health state returned by the endpoint. The implemented handler returns `ok`.


</ResponseField>

<ResponseField name="service" field-type="string" required="true">

Service identifier returned by the endpoint. The implemented handler returns `api`.


</ResponseField>

### Notes

This response shape is still defined inline inside the controller method. Unlike the earlier repository state, it now exists alongside validated DTO classes and persisted domain records.

## Validation schema and DTO status

Validation is now implemented in both services rather than deferred.

### NestJS API

- DTO classes validate request payloads with `class-validator` decorators.
- Publish, review submission, preview, verification, and related flows use named request DTOs.
- Optional and required fields are enforced before application logic writes to Supabase.
- The `aiGenerated` payload is validated as a structured object rather than passed through as an untyped inline shape.

### FastAPI service

- Pydantic `BaseModel` classes validate request and response payloads.
- Category and description generation routes use named schemas.
- Defaults and constrained literal values are encoded directly in the schema layer.

<Callout kind="info">

The repository now has two distinct validation patterns by service: DTO classes with decorators in the NestJS API and Pydantic models in the AI service.


</Callout>

## Migration status

The migration system is now part of the checked-in application architecture. SQL migrations live under `apps/api/supabase/migrations/` and are applied through a TypeScript migration runner.

The API service uses those migrations to evolve the Supabase PostgreSQL schema over time. The AI service manages its own schema changes for tables and features under its control.

### Summary

- SQL migrations are present and versioned in the repository.
- Migration numbers include recent changes such as 027, 028, 032, and 033.
- Supabase provides the primary persistence layer for the API service.
- Persisted tables now back publishing, moderation, leaderboard snapshots, and bounties.

## Gaps and implications

The current codebase now exposes a production-oriented data layer rather than only endpoint-local response objects. DTOs enforce request structure, migrations track schema evolution, and Supabase provides durable persistence for agent publishing and review workflows.

The `aiGenerated` baseline columns and `ai_edited_fields` diff column add a second layer of value beyond validation and storage. They make it possible to analyze how builders use AI-suggested content, which fields they keep, and where they tend to rewrite the generated baseline.

<Callout kind="info">

The repository now has a persistent contract across validation, storage, and moderation flows. AI edit-tracking columns add audit and analytics value without requiring runtime diffing on every read.


</Callout>
