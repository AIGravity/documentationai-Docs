## Overview

The platform persists data in a Supabase-hosted PostgreSQL database. The persistence layer is schema-first and SQL-first: database tables, constraints, triggers, and stored procedures are defined in raw SQL migrations. The NestJS API accesses the database through the Supabase client and the `pg` library, using parameterized queries and RPC calls. No ORM entity layer such as TypeORM, Prisma, Drizzle, or Knex is used on the Gravity side.

The AI service uses Pydantic models for request and response validation and contains its own database helpers, but its domain persistence is also SQL-first rather than ORM-mapped.

<Callout kind="info">

A separate Activepieces PostgreSQL database stores workflow execution state, including flows, runs, and connections. Activepieces manages that schema separately from the Gravity application database.

</Callout>

## Database table inventory

### Billing and credits

| Table | Purpose |
| --- | --- |
| `credit_ledger` | Append-only ledger of credit deltas. The authoritative balance is `SUM(delta)`. |
| `credit_orders` | Credit purchase orders and payment session state. |
| `agent_run_charges` | Per-run charge records with pricing snapshots and creator-split attribution. |
| `pricing_config` | Key-value configuration for pricing, feature flags, and rates. |
| `billing_plans` | Versioned subscription plan catalog with pricing, included credits, and budget percentages. |
| `user_subscriptions` | User subscription lifecycle and status. |
| `subscription_cycles` | Per-cycle budget tracking, grants, and renewal state. |
| `usage_grants` | Entitlement grants linked to subscription cycles. |
| `usage_reservations` | Soft holds on credits for active or scheduled runs. |
| `billing_webhook_inbox` | Idempotent webhook event processing queue. |

<Callout kind="info">

Subscription cycles and reservations store metadata about entitlements and active holds. The authoritative balance remains the credit ledger. Immutability triggers protect finalized plans, cycles, grants, and ledger-derived totals from mutation.

</Callout>

### Earnings and payouts

| Table | Purpose |
| --- | --- |

Payout creation uses a database-level advisory lock and guarded database operation to prevent double withdrawal. The operation checks available balance, including pending, processing, and paid payouts, detects duplicate requests, and inserts the payout atomically.

</Callout>

## Migration system

The database schema is managed through hand-written SQL migrations in two migration directories maintained by the API service. The migrations cover the full lifecycle of the application:

1. Identity and profiles, including user profiles, builders, and admin profiles
2. Marketplace and workflows, including published workflows, consumer copies, and discovery
3. Agent review and verification, including pending reviews, quality reviews, builder reports, and feedback
4. Billing and credits, including the credit ledger, orders, charges, and pricing
5. Subscriptions, including plans, subscriptions, cycles, grants, reservations, and webhooks
6. Earnings and payouts, including creator earnings, payout accounts, payouts, and events
7. Referrals, including clicks, attributions, earnings, partners, and signups
8. Bounty and candidate systems, including submissions, pools, assignments, and scoring
9. Notifications and telemetry

Migrations use PostgreSQL features including:

- Advisory transaction locks for concurrency-safe payouts
- Immutability triggers for billing integrity
- Stored procedures for atomic charge and refund operations with creator splits
- Idempotency constraints on referral earnings and refund operations

<Callout kind="info">

Migration numbering is not globally unique across the two directories. Both directories contain sequences that overlap in numbering. For example, two separate migrations use the `007` prefix, one for creator earnings and one for payouts.

</Callout>

## Data transfer objects

The NestJS API defines DTOs for request validation. These DTOs use `class-validator` decorators and are processed by a global validation pipe that strips unknown properties and transforms input types.

### Agent DTOs

- **Publish agent:** Name, summary, platforms, tools, use cases, categories, problem solved, workflow steps, builder questions, AI-generated status, workflow JSON, and optional requested-agent and test-run identifiers.
- **Review submission:** Source, title, workflow, and review payload.
- **URL verdict:** Workflow and agent setup fields restricted to designated reviewers.
- **Verify agent:** Workflow and agent setup fields for server-sent events verification.
- **Check request alignment:** Workflow and requested-agent context.
- **Check duplicate:** Workflow JSON and an optional source identifier.

### Marketplace DTOs

- **Introspect template:** Pasted Activepieces template JSON.
- **Publish paste:** Template plus name, tagging, and publishing metadata.
- **Run workflow:** Published workflow identifier, input, optional field values, and session identifier.
- **Run scratchpad:** Full template and input.
- **Builder connections:** Template used for connection introspection.

### Subscription DTOs

- **Payment checkout:** Plan identifier and optional country override.
- **Subscription activation:** Plan identifier supplied as a path parameter.

### Credit DTOs

- **Create credit order:** Package, currency, and optional country override.
- **Create custom credit order:** Amount in USD minor units, currency, and optional country override.
- **Verify credit order:** Razorpay or Stripe verification fields.

### Payout DTOs

- **Create payout:** Amount in minor units, currency, note, and optional payout account identifier.
- **Create payout account:** Account kind, bank, UPI, or PayPal fields, country, and optional default flag.
- **Connect Stripe:** Optional country code.

### Referral DTOs

- **Create share link:** Published workflow identifier and optional campaign.
- **Attribute referral:** Referral code and optional ISO 8601 link-seen timestamp.

## TypeScript type contracts

The API defines TypeScript type contracts beyond DTOs for internal service-level data:

- **Subscription types:** Subscription lifecycle, status, and plan bindings
- **Grant types:** Entitlement grant allocation and consumption
- **Reservation types:** Soft-hold lifecycle and release state
- **Entitlement types:** Spendable credits, outstanding holds, safety net, and budget tracking
- **Webhook inbox types:** Idempotent event processing state
- **Referral earnings types:** Monthly summary, settlement period, and rate

## AI service models

The Python AI service uses Pydantic models for request and response validation. Key model groups include:

### Interaction and search

- Chat request and interaction response models for conversational AI
- Guardrail check request and response models for content safety evaluation
- Embedding and indexing request and response models for agent search

### Requested agents

- Create-requested-agent and requested-agent view models
- Interest and mark-built models for community-driven agent requests

### Agent verification

- Verify-agent request with workflow and setup fields
- Prewarm-agent request for verification warm-up
- Description, workflow step, category, and fillable-field generation models
- Setup-field check request with per-field verdicts
- Request-alignment judgment request and response models
- URL verdict request and response models

### Agent review

- Workflow review request and response models with evidence and findings
- Review finding models with severity and evidence-axis scoring
- Requirement coverage and verdict models

### Static analysis

- Risk level, finding, extracted endpoint, and trajectory models
- Guardrail violation and guardrail result models
- AI review result models that combine analysis outputs
