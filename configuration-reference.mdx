## Overview

The platform uses environment-driven configuration across all three services. Each service reads from `.env` files locally and from deployment environment variables in production. The API and web apps read environment variables through `process.env` and `import.meta.env` respectively, and the AI service uses `os.getenv`. Feature flags are database-backed, allowing runtime toggling of billing and enforcement behavior without redeployment.

This page covers environment variables, feature flags, runtime settings, config files, Docker configuration, and workflow settings across the web, API, and AI services.

<Callout kind="info">

This page reflects the current implementation. Environment variables are documented by category. Some variables are required only when specific features are enabled, for example, payment provider keys are needed only when that provider is active.

</Callout>

Use this page to answer three practical questions:

- Which environment variables and feature flags affect local runtime, builds, and deployment
- Where each setting is defined
- Which mismatches in the current configuration can affect development or container runtime

## Configuration surface summary

Configuration is distributed across several layers:

- **Environment variables** drive ports, CORS origins, database connections, provider credentials, and service URLs across all three apps.
- **Database-backed feature flags** control billing and enforcement behavior at runtime.
- **Package scripts** define dev and build commands for the monorepo and individual apps.
- **Static config files** define TypeScript, workspace, Turbo, Nest, and Python tool settings.
- **Dockerfiles** define container base images, exposed ports, and commands.
- **GitHub Actions workflows** define service names, image names, branch filters, concurrency behavior, and release gating logic.

<Callout kind="info">

Some settings such as package manager version and TypeScript targets are pinned in static config files. Runtime behavior, including ports, CORS, database connections, and provider credentials, is driven by environment variables.

</Callout>

## Environment variables

Environment variables provide local and deployment-time configuration for the API, web, and AI services. Local development loads values from `.env` files, while production deployments provide the same settings through the deployment environment.

### Core application

| Variable | Type | Default | Purpose | Required |
| --- | --- | --- | --- | --- |
| `PORT` | number | `3001` | API listening port | No |
| `CORS_ORIGINS` | comma-separated string | `http://localhost:3000,http://localhost:5173,http://localhost:5174` | Allowed CORS origins | No |
| `FRONTEND_URL` | URL string | `http://localhost:5173` | Public web origin for OAuth callbacks | No, but required for production OAuth |
| `AI_SERVICE_URL` | URL string | `http://localhost:8001` | Base URL for the Python AI service | Yes for AI-powered features |
| `AI_SERVICE_TIMEOUT_MS` | integer | `10000` | Timeout for AI service requests in milliseconds | No |

## Application runtime settings

Application runtime behavior combines environment-driven values with fixed service behavior such as health routes and credential handling.

### API service runtime settings

The API reads its listening port and allowed origins from environment variables, with local-development defaults.

<CodeGroup tabs="Behavior summary">

```ts
// API runtime behavior:
// - CORS origins configured via CORS_ORIGINS env var
// - Default origins: localhost:3000, localhost:5173, localhost:5174
// - Credentialed requests enabled
// - API port configured via PORT env var (default: 3001)
```

</CodeGroup>

<ParamField body="origin" param-type="string[]" required="true" show-location="false">

**Purpose:** Define which frontend origins may access the API through CORS.

**Type:** array of strings.

**Explicit value:** Environment-driven through `CORS_ORIGINS`.

**Default:** `http://localhost:3000`, `http://localhost:5173`, and `http://localhost:5174`.

**Required:** No. The default origins apply when `CORS_ORIGINS` is not set.

</ParamField>

<ParamField body="credentials" param-type="boolean" required="true" show-location="false">

**Purpose:** Allow credentialed cross-origin requests.

**Type:** boolean.

**Explicit value:** `true`.

**Required:** Yes. Credentialed requests remain enabled.

</ParamField>

<ParamField body="port" param-type="number" required="true" show-location="false">

**Purpose:** Define the API listening port.

**Type:** number.

**Explicit value:** Environment-driven through `PORT`.

**Default:** `3001`.

**Required:** No. The service uses port `3001` when `PORT` is not set.

</ParamField>

## Feature flags

The platform uses database-backed feature flags stored in the `pricing_config` table. These flags are read at runtime and cached for 60 seconds. They default to off when the database row is missing, zero, `NULL`, or when a query error occurs.

### Subscription flags

| Flag | Default | Behavior |
| --- | --- | --- |
| `subscription_billing_enabled` | Off | Enables subscription billing and entitlement computation. When off, subscription endpoints return 404. |
| `subscription_enforcement_enabled` | Off | Blocks or admits workflow runs based on subscription entitlement. Fail-safe: errors default to off so transient issues cannot block users. |

<Callout kind="info">

The two flags are intentionally independent. Billing on with enforcement off creates a shadow mode that computes entitlements without blocking runs. Enforcement is fail-safe: database or configuration errors default to off.

</Callout>

### Presence-based toggles

Several features activate based on the presence of environment variables rather than explicit boolean flags:

- Stripe enables when `STRIPE_SECRET_KEY` is set.
- Razorpay enables when `RAZORPAY_KEY_ID` and `RAZORPAY_KEY_SECRET` are both set.
- RazorpayX payouts enable when all three RazorpayX keys are set.
- PayPal payouts enable when `PAYPAL_CLIENT_ID` and `PAYPAL_CLIENT_SECRET` are set.
- Agent rank scoring enables when `AGENT_RANKER_API_URL` is set.
- Composio verification enables when `COMPOSIO_API_KEY` is set.
- Crisp support chat enables when `VITE_CRISP_WEBSITE_ID` is set.
- Analytics sending enables only when `POSTHOG_ENVIRONMENT` is `production`.

### Notification safety toggles

- `NOTIFICATIONS_ENABLED`: Kill switch for outbound email while retaining queued rows.
- `NOTIFICATIONS_REDIRECT_TO`: Redirects all notification recipients in staging.
