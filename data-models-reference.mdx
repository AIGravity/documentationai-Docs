## Overview

The NestJS API service uses a Supabase-backed Postgres database with SQL migration files for schema management. The repository does not use an ORM framework, formalized DTO classes, or named validation schemas. Admin billing endpoints return ad-hoc TypeScript interfaces rather than class-backed DTOs.

What exists today is still limited in terms of formal model definitions. The repository includes two inline response shapes returned by health endpoints. Those shapes are API responses, not persisted entities, and they do not declare relationships, validation rules, or storage mappings. Admin billing endpoints also return structured response shapes defined as TypeScript interfaces.

<Callout kind="info">

This reference inventories what is present in the checked-in repository today. It does not describe planned architecture, intended schemas, or future database work.


</Callout>

## Persistence and migration status

The NestJS API service persists data in a Supabase-managed Postgres database. Schema changes are managed through SQL migration files that are applied manually.

SQL migration files are present and manage database schema changes including the profiles table, credit ordering, run charge tracking, and creator earnings. Migrations are applied manually via the Supabase SQL editor rather than through an automated migration runner.

### Repository-level signals

- The NestJS API exposes a health controller and a set of admin billing endpoints with structured TypeScript interface responses.
- The FastAPI service exposes a single health endpoint with an inline object response.
- `pydantic` is present as a Python dependency, but no `BaseModel` classes are defined.
- The repository README describes shared schemas and database work as planned rather than implemented.

## NestJS API response shape

The NestJS API currently returns one structured object from the health endpoint and also returns structured response shapes from admin billing endpoints. Those admin billing shapes are defined as TypeScript interfaces rather than class-backed DTOs. The health response object remains an inline response shape rather than a named DTO or persisted entity.

## Migration status

SQL migration files manage the Postgres database schema for the NestJS API service.

- Migrations are applied manually through the Supabase SQL editor.
- Recent migrations include a test-account flag on user profiles and a minimum creator payout rule for marketplace billing.
- No automated migration runner is configured; migrations are tracked as SQL files in the repository.

### Current implication

The database schema evolves through SQL migration files. Each migration is a standalone SQL script that modifies tables or Postgres functions.

## Gaps and implications

The current codebase exposes service health and persists billing-related data, but it does not yet define durable application data structures as a formal model layer. That has several practical implications for anyone reading the repository as a backend reference.

- **No canonical domain entities** — There is no checked-in source of truth for business objects.
- **No validation contract** — Request and response validation rules are not formalized in DTOs or schema classes.
- **Persistence via raw SQL, not ORM** — Database tables exist and are managed through SQL migrations, but no ORM model layer provides typed entity definitions or relationship mappings.
- **Manual migration tracking** — Migrations are SQL files without an automated runner or version tracking table.
- **Limited reuse across services** — Shared contracts are not implemented as reusable schema packages.

<Callout kind="info">

Admin billing response shapes are defined as TypeScript interfaces for API responses. They are not backed by ORM models or formalized DTO classes, but they do reflect persisted database entities in the Postgres schema.


</Callout>
