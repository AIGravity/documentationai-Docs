## Overview

AIGravity/core defines validation DTOs in the NestJS API and Pydantic schemas in the FastAI AI service for agent verification, marketplace feedback, and agent publishing flows. A SQL migration handles the transition from single-value to array-based feedback reasons.

In addition to the DTOs and schemas, two inline response shapes are returned by health endpoints. The agent feedback DTO is backed by a database table with a SQL migration.

<Callout kind="info">

This reference inventories what is present in the checked-in repository today. It does not describe planned architecture, intended schemas, or future database work.


</Callout>

## Persistence and migration status

A persistence layer is partially implemented for marketplace agent feedback. The NestJS API uses a Supabase service to insert feedback records, backed by a SQL migration.

The repository still contains no Prisma schema, no TypeORM entities, no Drizzle tables, no Mongoose schemas, no SQLAlchemy models, no Sequelize models, and no Knex-based schema definitions.

A SQL migration file handles the schema change from a single `reason` text column to a `reasons` text array column in the agent feedback table.

### Repository-level signals

- The NestJS API exposes health, agent verification, agent submission, and marketplace feedback endpoints with DTO validation.
- The FastAPI service exposes a single health endpoint with an inline object response.
- `pydantic` is present as a Python dependency, and `BaseModel` classes are defined for agent verification requests and responses.
- The repository README describes shared schemas and database work as planned rather than implemented.

## Validation schema and DTO status

The NestJS API uses `class-validator` decorators on DTO classes for request body validation. The FastAPI service uses Pydantic `BaseModel` classes for request and response schemas on the verification endpoints.

### NestJS API DTOs

Three DTO classes with `class-validator` decorators are defined:

**PrewarmAgentDto** — used by `POST /agents/verify-prewarm`

<ResponseField name="workflowJson" field-type="object" required="true">

The agent workflow JSON object. Validated with `@IsObject()`.


</ResponseField>

**AgentFeedbackDto** — used by `POST /marketplace/feedback`

<ResponseField name="agentId" field-type="string" required="true">

Identifier of the agent being reviewed.


</ResponseField>

<ResponseField name="reasons" field-type="array" required="true">

One or more feedback categories. Validated with `@IsArray()`, `@ArrayNotEmpty()`, and `@IsIn(..., { each: true })`. Allowed values: `output_quality`, `looking_elsewhere`, `try_alternate`, `other`. This field replaces the previous single `reason` string.


</ResponseField>

**PublishAgentDto** — used by `POST /agents/verify` and `POST /agents/{id}/submit`

<ResponseField name="problemSolved" field-type="string" required="false">

Description of the problem the agent solves. Validated with `@MinLength()` and `@MaxLength()` to enforce server-side character length constraints.


</ResponseField>

### FastAPI service Pydantic schemas

Three `BaseModel` classes are defined for agent verification:

**VerifyAgentRequest** — request body for `POST /verification/verify-ap-stream`

<ResponseField name="workflow_json" field-type="object" required="true">

The agent workflow JSON object to verify.


</ResponseField>

<ResponseField name="workflow_content_hash" field-type="string" required="false">

Content hash of the workflow JSON. Enables Gate 4 result reuse from the prewarm cache. Defaults to an empty string.


</ResponseField>

<ResponseField name="allowed_hosts" field-type="array" required="false">

List of allowed hostnames for URL safety checks.


</ResponseField>

**PrewarmAgentRequest** — request body for `POST /verification/prewarm`

<ResponseField name="workflow_json" field-type="object" required="true">

The agent workflow JSON object to evaluate.


</ResponseField>

<ResponseField name="workflow_content_hash" field-type="string" required="false">

Cache key for the prewarmed Gate 4 result. Defaults to an empty string.


</ResponseField>

<ResponseField name="allowed_hosts" field-type="array" required="false">

List of allowed hostnames. Defaults to an empty array.


</ResponseField>

**PrewarmAgentResponse** — response from `POST /verification/prewarm`

<ResponseField name="cached" field-type="boolean" required="true">

`true` when the Gate 4 result was cached. `false` on failure.


</ResponseField>

<ResponseField name="status" field-type="string" required="false">

Gate 4 outcome: `pass`, `warn`, or `fail`. Empty on failure.


</ResponseField>

<ResponseField name="reason" field-type="string" required="false">

Empty on success. Contains the exception type name on failure.


</ResponseField>

## Migration status

One SQL migration file handles a schema change for the agent feedback table.

### Summary

- 1 SQL migration file found for the agent feedback reasons column change
- No ORM-managed migration framework is present; the migration is a standalone SQL file
- The migration converts the `reason` text column to a `reasons` text array column

### Agent feedback reasons migration

The migration performs these steps:

1. Adds a `reasons` column of type `text[]` if it does not exist
2. Adds a constraint restricting `reasons` values to the allowed set: `output_quality`, `looking_elsewhere`, `try_alternate`, `other`
3. Backfills `reasons` from the old `reason` column where `reasons` is null
4. Drops the `reason` column
5. Sets `reasons` to `NOT NULL`

<Callout kind="info">

This is a breaking schema change. Clients still sending the old single `reason` string format will receive a `400 Bad Request` from the API.


</Callout>

## Gaps and implications

The current codebase exposes service health, but it does not yet define durable application data structures. That has several practical implications for anyone reading the repository as a backend reference.

- **No canonical domain entities** — There is no checked-in source of truth for business objects.
- **Partial validation contract** — DTOs and Pydantic schemas now formalize request validation for agent verification, marketplace feedback, and agent publishing. Health endpoints remain unvalidated inline shapes.
- **Partial persistence contract** — The agent feedback DTO maps to a database table via a SQL migration. Other shapes remain request/response contracts only.
- **Single migration** — One SQL migration exists for the feedback reasons schema change. No broader migration framework is in place.
- **Limited reuse across services** — Shared contracts are not implemented as reusable schema packages.

<Callout kind="danger">

Treat the health response shapes as endpoint-local only. The DTOs and Pydantic schemas are stable API contracts for their respective endpoints.


</Callout>
