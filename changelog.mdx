## Frontend tooling

- The web frontend uses Remix v2 through the Vite build path, with `remix vite:build` configured in `apps/web/package.json`.
- Vite 6 is configured for the web app, and `apps/web/vite.config.ts` wires the Tailwind, Remix, and TypeScript path plugins together.
- Tailwind CSS v4 is installed through `tailwindcss` and `@tailwindcss/vite`, with the CSS entrypoint using the v4 `@import "tailwindcss";` pattern in `apps/web/app/app.css`.

## Service versioning and image tags

- Each deployable service keeps its base semantic version in a service-local `VERSION` file: `apps/web/VERSION`, `apps/api/VERSION`, and `apps/ai-service/VERSION`.
- The CI workflows derive service tags from each service version and branch context. Main branch builds create service tags such as `web-v<version>`, `api-v<version>`, and `ai-service-v<version>`, while dev branch builds use prerelease tags with the base version, timestamp, and short commit SHA.
- The manual version bump script, `scripts/version-bump.sh`, supports major, minor, and patch increments for `web`, `api`, and `ai-service`.

## Docker publishing

Gravity publishes Docker images for all three services to GitHub Container Registry:

| Service | Image name |
| --- | --- |
| Web frontend | `ghcr.io/<owner>/gravity-web` |
| NestJS API | `ghcr.io/<owner>/gravity-api` |
| AI service | `ghcr.io/<owner>/gravity-ai-service` |

The workflows also publish branch-aware convenience tags: `latest` for main builds, `dev-latest` for dev builds, and a bare commit SHA tag for traceability.

## Health endpoints

- The NestJS API exposes `GET /health` and returns `{"status":"ok","service":"api"}` from `apps/api/src/health/health.controller.ts`.
- The AI service exposes `GET /health` and returns `{"status":"ok"}` from `apps/ai-service/main.py`.
- The Remix web frontend does not define a health route in the current `apps/web/app/routes` surface.

<Callout kind="alert">

The API service currently listens on port `3001` in `apps/api/src/main.ts`, while its Dockerfile declares `EXPOSE 3000`. Treat that as a deployment detail to verify before relying on container metadata for health checks.

</Callout>
