## Overview

AIGravity/core now includes a Supabase-backed persistence layer for bounty funding, a validated DTO for bounty payment verification, and SQL migrations that evolve the bounty schema.

What exists today includes two persisted bounty-related entities, one DTO-backed validation contract for payment verification, and several inline response shapes returned by API endpoints. The FastAPI service still exposes only a health response shape and does not define persisted models in the analyzed code.

<Callout kind="info">

This reference inventories what is present in the checked-in repository today. It does not describe planned architecture, intended schemas, or future database work.


</Callout>

## Persistence and migration status

The repository now uses Supabase as its persistence layer for bounty funding. The implemented persistence surface covers the existing `bounties` table and a new `bounty_orders` table that records payment orders created during checkout.

The `bounties` table now carries funding-specific state in addition to the bounty lifecycle state. It includes `payment_status`, which stores either `unpaid` or `paid` and defaults to `unpaid`, plus `funded_at`, which stores the verification timestamp when payment succeeds.

Bounty lifecycle state also expanded to support `pending_payment`. That status marks a bounty that has been created but not yet funded. After payment verification succeeds, the bounty transitions to `open`.

Migration infrastructure now exists for this slice of the schema. The repository includes `017_bounty_orders.sql`, which creates the `bounty_orders` table and adds the new bounty funding columns to `bounties`.

### Repository-level signals

- The NestJS API exposes a health controller with an inline object response.
- The FastAPI service exposes a health endpoint with an inline object response.
- The repository persists bounty funding state in Supabase tables.
- Bounty payment verification uses a DTO with `class-validator` decorators.
- SQL migrations now evolve the bounty schema directly in the repository.
- `pydantic` is present as a Python dependency, but no `BaseModel` classes are defined.

## Bounty funding data models

Bounty funding now introduces durable data structures for checkout state and payment confirmation. The persistence model separates the payment order record from the bounty itself so the system can track order lifecycle without overloading the bounty row.

### bounty_orders table

The `bounty_orders` table tracks Razorpay payment orders created for bounty funding.

| Column | Type | Constraints | Description |
| --- | --- | --- | --- |
| `id` | UUID | PK, auto-generated | Order record identifier |
| `bounty_id` | UUID | FK to `bounties(id)`, NOT NULL | The bounty being funded |
| `user_id` | UUID | FK to `auth.users(id)`, NOT NULL | The bounty creator |
| `amount_minor` | integer | NOT NULL, `>= 0` | Amount in smallest currency unit such as paise or cents |
| `currency` | text | NOT NULL | ISO 4217 currency code |
| `razorpay_order_id` | text | UNIQUE | Razorpay order ID |
| `razorpay_payment_id` | text | nullable | Razorpay payment ID set after payment |
| `status` | text | default `PENDING`, check IN `PENDING`, `PAID`, `FAILED`, `EXPIRED` | Order lifecycle |
| `fail_reason` | text | nullable | Failure description if payment failed |
| `created_at` | timestamptz | default `now()` | Creation timestamp |
| `updated_at` | timestamptz | default `now()` | Last update timestamp |

Indexes exist on `bounty_id`, `user_id`, and `status` to support common lookup paths during order creation, payment verification, and operational review.

### bounties table additions

The existing `bounties` table now stores funding state directly on the bounty record.

| Column | Type | Default | Constraints | Description |
| --- | --- | --- | --- | --- |
| `payment_status` | text | `unpaid` | check IN `unpaid`, `paid` | Durable funding flag stored separately from lifecycle status |
| `funded_at` | timestamptz | `NULL` | — | Timestamp when payment was confirmed |

The `status` column also supports `pending_payment`. A bounty in that state has been created but not yet funded, so it is not visible in the public bounty list. After payment verification succeeds, the bounty status changes to `open`.

<Callout kind="info">

All pre-existing bounties were backfilled with `payment_status = 'paid'` during the migration. Legacy bounties remain visible and are treated as already funded.


</Callout>

## Bounty payment DTO

Bounty payment verification now uses a DTO-backed validation contract. The DTO validates the Razorpay checkout callback payload before the API attempts to confirm payment and update bounty state.

If any required field is missing or empty, the request fails with a `400` error. That prevents partial or malformed verification payloads from reaching the payment confirmation flow.

### Fields

<ParamField body="razorpayOrderId" param-type="string" required="true" show-location="false">

Razorpay order identifier returned when the funding order is created. The value must be present and non-empty.


</ParamField>

<ParamField body="razorpayPaymentId" param-type="string" required="true" show-location="false">

Razorpay payment identifier returned by the checkout flow. The value must be present and non-empty.


</ParamField>

<ParamField body="razorpaySignature" param-type="string" required="true" show-location="false">

Signature returned by Razorpay for callback verification. The value must be present and non-empty.


</ParamField>

### Validation behavior

- Uses `class-validator` decorators on all three fields.
- Rejects missing values.
- Rejects empty-string values.
- Returns `400` for invalid payloads before payment verification runs.

## Gaps and implications

The current codebase now defines durable data structures and validation for the bounty funding domain, but that coverage is still narrow relative to the full repository.

- **Partial domain coverage** — Canonical persisted entities exist for bounty funding, but other business areas still do not expose the same level of checked-in model coverage.
- **Validation is flow-specific** — DTO validation exists for bounty payment verification, but the documented response shapes are still mostly inline contracts rather than broadly reused schema classes.
- **Mixed contract styles** — The repository now combines database-backed entities, DTO validation, and endpoint-local response objects instead of one uniform modeling approach across services.
- **Python service remains schema-light** — The FastAPI service still exposes only an inline health response and does not define Pydantic models in the analyzed code.
- **Migration history is limited in scope** — Checked-in migration coverage now exists for bounty funding, but not yet for every potential domain area.
