## Overview

The frontend is a Remix application running in `apps/web`. It provides the web interface for the Gravity platform, including authentication, onboarding, agent marketplace, builder tools, admin dashboards, billing, referrals, subscriptions, and settings. The root layout installs providers for authentication, sessions, Stripe checkout, PostHog analytics, Sentry error tracking, support chat, and bug reporting.

## App purpose and current scope

The frontend serves as the primary web interface for the Gravity platform. It includes routes for authentication and onboarding, agent marketplace browsing and customization, agent publishing, builder dashboards, admin review tools, billing and subscriptions, referral programs, and user settings. The root layout wraps all routes with authentication, session management, analytics, error tracking, and support widget providers.

The implemented files that define the shell include:

- `apps/web/app/root.tsx`
- `apps/web/app/app.css`
- Authentication and onboarding route modules
- Marketplace route modules
- Builder route modules
- Admin route modules
- Billing and subscription route modules
- Referral route modules
- User settings route modules
- `apps/web/vite.config.ts`
- `apps/web/package.json`
- `apps/web/Dockerfile`
- `apps/web/VERSION`

## Route map

The frontend route map is organized around the primary workflows of the Gravity platform.

### Authentication and onboarding

Authentication routes handle sign-in flows, callback processing, and onboarding for new users.

- **Auth callback:** Completes authentication redirects and establishes the signed-in session.
- **Onboarding:** Guides new users through the initial account and platform setup.

### Marketplace

Marketplace routes support agent discovery, browsing, customization, and detail views.

- **Marketplace index:** Displays the main agent marketplace.
- **Agent detail:** Shows information and available actions for an individual agent.
- **Explore agents:** Provides additional agent discovery and browsing flows.

### Builder

Builder routes support agent creation, customization, publishing, and dashboard management.

- **Publish agent:** Publishes an agent to the marketplace.
- **Customize agent:** Configures an agent before publication or continued development.
- **Builder dashboard:** Provides an overview of the user's builder activity and agents.

### Admin

Admin routes provide operational dashboards and review tools.

- **Admin dashboard:** Provides the main administrative overview.
- **Review tools:** Support agent and marketplace review workflows.
- **Billing analytics:** Exposes billing and revenue-related administrative data.
- **Candidate management:** Supports management of signed-in candidates and assignment-related workflows.

### Billing

Billing routes manage subscription plans, checkout, and credit purchases.

- **Subscription plans:** Displays available subscription options.
- **Checkout:** Starts and completes Stripe checkout flows.
- **Credit packages:** Provides access to available credit purchase options.

### Referrals

Referral routes support referral link management and earnings visibility.

- **Referral links:** Creates or displays links used for referrals.
- **Earnings:** Shows referral-related earnings and activity.

### User settings

Settings routes allow users to manage their account and preferences.

- **Profile:** Updates profile information.
- **Password:** Manages password settings.
- **Preferences:** Configures user preferences.

The root layout provides shared authentication, session, Stripe checkout, PostHog, Sentry, support chat, and bug reporting providers to these routes.

## Root layout

The root layout in `apps/web/app/root.tsx` installs multiple providers around the route outlet. These include authentication and session providers, Stripe checkout, PostHog analytics, Sentry error tracking, support chat, and bug reporting.

The root also loads the global stylesheet before first paint, restricts signed-in candidates to assignment routes, and renders global help, support, and error UI. Route modules therefore receive the shared application context without needing to initialize these services independently.

### Provider nesting pattern

The provider hierarchy places authentication and session context around the route outlet, then adds global payment, analytics, error tracking, support, and bug reporting behavior around the application shell.

```tsx
export default function App() {
  return (
    <AuthProvider>
      <SessionProvider>
        <StripeCheckoutProvider>
          <PostHogProvider>
            <SentryProvider>
              <SupportChatProvider>
                <BugReportingProvider>
                  <Outlet />
                  <GlobalHelp />
                  <GlobalSupport />
                  <GlobalErrorUI />
                </BugReportingProvider>
              </SupportChatProvider>
            </SentryProvider>
          </PostHogProvider>
        </StripeCheckoutProvider>
      </SessionProvider>
    </AuthProvider>
  );
}
```

This shared structure keeps authentication, session state, payment flows, telemetry, error reporting, and support tools available throughout the application. The root layout also applies route restrictions for signed-in candidates so that assignment routes remain the permitted destination for that user state.

## Error handling

The root file defines the application error boundary. It distinguishes route error responses from runtime errors and exposes more detail during development.

The error boundary is now part of a richer application shell that includes global error and support UI. Route-level failures still use the boundary for fallback rendering, while the surrounding shell provides the shared support and reporting behavior available across the application.

### Error boundary logic

The implementation starts with fallback values, then refines the message based on the error type.

<CodeGroup tabs="Boundary logic,Fallback UI">

```tsx
export function ErrorBoundary() {
  const error = useRouteError();
  let message = "Oops!";
  let details = "An unexpected error occurred.";
  let stack: string | undefined;

  if (isRouteErrorResponse(error)) {
    message = error.status === 404 ? "404" : "Error";
    details =
      error.status === 404
        ? "The requested page could not be found."
        : error.statusText || details;
  } else if (import.meta.env.DEV && error && error instanceof Error) {
    details = error.message;
    stack = error.stack;
  }
```

```tsx
  return (
    <main className="pt-16 p-4 container mx-auto">
      <h1>{message}</h1>
      <p>{details}</p>
      {stack && (
        <pre className="w-full p-4 overflow-x-auto">
          <code>{stack}</code>
        </pre>
      )}
    </main>
  );
}
```

</CodeGroup>

### Current behavior

The boundary currently behaves as follows:

- **404 route errors** render `404` with the message `The requested page could not be found.`
- **Other route error responses** render `Error` and use `error.statusText` when present
- **Development runtime errors** render the thrown error message and stack trace
- **Fallback cases** render `Oops!` and `An unexpected error occurred.`

The boundary works alongside the global error and support UI provided by the root layout. This gives route failures a local fallback while preserving access to the application's shared reporting and support tooling.

## Styling pipeline

The styling stack is intentionally small. Global styles live in `app.css`, and Vite is configured with only the plugins required for Tailwind, Remix, and TypeScript path resolution.

### Global CSS in `app.css`

The stylesheet imports Tailwind, defines the sans font theme variable, and sets the document background for light and dark mode.

<CodeGroup tabs="app.css">

```css
@import "tailwindcss";

@theme {
    --font-sans:
        "Inter", ui-sans-serif, system-ui, sans-serif, "Apple Color Emoji",
        "Segoe UI Emoji", "Segoe UI Symbol", "Noto Color Emoji";
}

html,
body {
    background-color: var(--color-white);

    @media (prefers-color-scheme: dark) {
        background-color: var(--color-gray-950);
        color-scheme: dark;
    }
}
```

</CodeGroup>

From this file alone, the shell currently guarantees:

- Tailwind CSS is loaded globally
- Inter is first in the sans font stack
- `html` and `body` default to a white background
- dark mode switches the background to `var(--color-gray-950)` and enables `color-scheme: dark`

### Vite and Remix configuration

The build configuration is defined in `apps/web/vite.config.ts`.

<CodeGroup tabs="vite.config.ts">

```ts
import { vitePlugin as remix } from "@remix-run/dev";
import tailwindcss from "@tailwindcss/vite";
import { defineConfig } from "vite";
import tsconfigPaths from "vite-tsconfig-paths";

export default defineConfig({
  plugins: [tailwindcss(), remix(), tsconfigPaths()],
});
```

</CodeGroup>

No additional server settings, proxy behavior, environment-specific overrides, or custom build options are configured here. The shell uses the default behavior provided by these plugins.

## Local run and build

`apps/web/package.json` defines the complete local script surface for the frontend shell.

<Callout kind="tip">

Run these commands from `apps/web` so `package.json` and the local build output resolve as expected.

</Callout>

<CodeGroup tabs="package.json scripts,Command usage">

```json
"scripts": {
  "build": "remix vite:build",
  "dev": "remix vite:dev",
  "start": "remix-serve ./build/server/index.js",
  "typecheck": "tsc"
}
```

```bash
npm run dev
npm run build
npm run start
npm run typecheck
```

</CodeGroup>

These commands map directly to the current shell lifecycle:

- `npm run dev` starts the Remix Vite development server
- `npm run build` creates the production build
- `npm run start` serves the built app from `./build/server/index.js`
- `npm run typecheck` runs TypeScript without a separate lint or test command in this package

Other relevant package facts currently visible in `package.json`:

- package name is `@repo/web`
- module type is `module`

## Container packaging

The frontend can also be built and run as a container. The Dockerfile uses a two-stage Node 20 Alpine build and serves the production Remix bundle on port `3000`.

### Docker build and runtime flow

<CodeGroup tabs="Dockerfile,Version file">

```dockerfile
FROM node:20-alpine AS build
WORKDIR /app
COPY package.json ./
RUN npm install --include=dev
COPY . .
# tsconfig.json extends ../../tsconfig.base.json — place it at the expected path
COPY tsconfig.base.json /tsconfig.base.json
RUN npm run build

FROM node:20-alpine
WORKDIR /app
COPY package.json ./
RUN npm install --omit=dev
COPY --from=build /app/build ./build
EXPOSE 3000
CMD ["npm", "run", "start"]
```

```text
0.1.0
```

</CodeGroup>

A few implementation details matter:

- the build stage installs development dependencies and runs `npm run build`
- the runtime stage installs production dependencies only
- the built `./build` output is copied into the final image
- the container exposes port `3000`
- the startup command is `npm run start`, which resolves to `remix-serve ./build/server/index.js`
- `apps/web/VERSION` is currently `0.1.0`
