## Overview

The AI service is now a FastAPI application with health, chat, and agent verification endpoints. It integrates LLM-based content generation through OpenRouter for category suggestion, description polishing, and workflow step generation, while the verification stack adds streaming agent verification, setup field scoring, and request alignment checks.

<Callout kind="info">

The current service uses LLM providers, Pydantic schemas, and a startup warmup sequence to reduce cold-start latency for verification workflows.


</Callout>

## Current scope

This service has evolved from a minimal scaffold into a feature-rich AI system with a verification router, LLM integration, and Pydantic-based request and response schemas. The verification stack is pre-warmed on startup so higher-cost checks are ready before the first verification request arrives.

Key capabilities now include:

- AI-powered category generation from a fixed taxonomy
- Description and name generation with deterministic post-processing
- Workflow step generation from workflow definitions
- Fillable field detection for user-provided inputs
- Setup field scoring for agent metadata quality
- Request alignment judging against requested-agent or bounty specifications
- Prewarming and cached verification results by workflow hash
- Streaming agent verification through Server-Sent Events

## Bootstrap in main.py

The application still starts in `apps/ai-service/main.py`, but startup now does more than instantiate a single FastAPI app. The main module registers multiple routers, including a verification router mounted at `/verification` and a credits router, and it uses a lifespan handler to pre-warm the verification stack during startup.

<CodeGroup tabs="main.py,Notes">

```python
from contextlib import asynccontextmanager
from fastapi import FastAPI

from routers.verification import router as verification_router
from routers.credits import router as credits_router
from services.verification import prewarm_verification_stack


@asynccontextmanager
async def lifespan(app: FastAPI):
    await prewarm_verification_stack()
    yield


app = FastAPI(lifespan=lifespan)

app.include_router(verification_router, prefix="/verification")
app.include_router(credits_router)


@app.get("/health")
def health():
    return {
        "status": "ok",
        "service": "ai-service",
        "version": "0.1.0",
    }
```

```text
Grounded bootstrap details:

- FastAPI app creation now includes a lifespan startup handler
- startup prewarms the verification stack before serving requests
- /verification routes are registered through an APIRouter
- a credits router is also mounted on the main app
- the main module also defines direct routes for chat, requested agents, embedding, agent indexing, and admin pricing
```

</CodeGroup>

That broader bootstrap path changes what this service is responsible for at runtime. The application now coordinates router composition, verification readiness, and direct AI-facing endpoints rather than serving only a single liveness route.

## Agent verification capabilities

The verification router now exposes 11 endpoints under the `/verification` prefix. Together, those endpoints support classification, content generation, workflow analysis, advisory scoring, and streamed multi-phase verification.

### Category generation

Category generation uses an LLM with temperature `0.0` to keep classification deterministic. The model classifies agents into a fixed taxonomy of 10 marketplace categories and returns between 1 and 3 categories from this set:

- Everyday
- Customer service
- Sales
- Engineering
- Finance
- HR
- IT
- Legal
- Marketing
- Operations

If category generation fails, the service fails open and returns an empty array rather than blocking the broader verification flow.

### Description and name generation

Description generation can create or polish an agent name, description, and problem statement. It uses different temperature settings by field, with `0.2` for names and `0.5` for descriptions, so short labels stay more stable while descriptive text has more room to improve.

The service then applies deterministic post-processing before returning the result. That post-processing removes hyphenated phrasing where needed, clamps content to character limits, and enforces style constraints such as avoiding first-person pronouns and unnecessary technical jargon.

### Workflow step generation and field analysis

Workflow step generation converts workflow JSON into natural-language step-by-step descriptions. That output gives reviewers and downstream systems a readable summary of what the workflow actually does.

The same verification stack also detects fillable fields by identifying workflow inputs that still need user-provided values. This helps separate complete automations from flows that require setup-time or run-time input.

### Scoring and alignment checks

Setup field scoring evaluates the name, description, and problem statement against the workflow definition. The scores are advisory only and do not reject an agent on their own.

Request alignment judging evaluates whether a workflow matches a requested-agent or bounty specification. This check helps determine whether the uploaded workflow satisfies the intent of the request, not merely whether the workflow is syntactically valid.

### Prewarming and streaming verification

Prewarming runs behavioral checks at upload time and caches results by workflow hash. That cache reduces repeated work when the same workflow is verified multiple times.

Streaming verification delivers multi-phase verification over Server-Sent Events. Clients receive per-phase status updates and issue reporting as the verification progresses, which is more useful than waiting for a single final response after every check completes.

<Callout kind="info">

The verification stack is pre-warmed on startup so the first verification request does not pay the full cold-start cost for model-backed checks.


</Callout>

## LLM provider integration

The service uses OpenRouter as its LLM provider. Model-backed generation and verification requests flow through that provider rather than through a local model runtime.

<CodeGroup tabs="Environment,Defaults">

```bash
OPENROUTER_API_KEY=or_example_9xmk7q2r
OPENROUTER_BASE_URL=https://openrouter.ai/api/v1
VERIFICATION_REQUEST_TIMEOUT_SECS=10
```

```text
Provider behavior:

- OPENROUTER_API_KEY authenticates requests to the provider
- OPENROUTER_BASE_URL defaults to https://openrouter.ai/api/v1
- VERIFICATION_REQUEST_TIMEOUT_SECS defaults to 10 seconds
- workflow JSON is truncated before LLM submission to control token usage
```

</CodeGroup>

Those controls keep provider integration predictable at runtime. The timeout bounds slow verification calls, and workflow truncation limits prompt size before structured workflow data is sent to the model.

## Run locally

The repository does not include a substantive local guide for this service, so the usable commands are implied by the CI workflow and Docker runtime command. Run these commands from `apps/ai-service`.

<CodeGroup tabs="Install and start,Quality checks">

```bash
uv python install
uv sync
uv run uvicorn main:app --host 0.0.0.0 --port 8001
```

```bash
uv run ruff format --check .
uv run ruff check .
```

</CodeGroup>

If startup succeeds, Uvicorn listens on port `8001`. A successful request to `GET /health` returns `{"status": "ok"}`.

Tests are not part of the active CI path today. The workflow includes a commented-out pytest step, so pytest is declared as a dev dependency but is not currently enforced in automation.

## Docker packaging

The service image uses a multi-stage Docker build based on `python:3.14-slim`. The builder stage installs production dependencies with uv, and the runtime stage copies the virtual environment and application source before starting Uvicorn.

<CodeGroup tabs="Dockerfile">

```dockerfile
FROM python:3.14-slim AS builder
WORKDIR /app
COPY --from=ghcr.io/astral-sh/uv:latest /uv /uvx /bin/
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev

FROM python:3.14-slim
WORKDIR /app
COPY --from=builder /app/.venv /app/.venv
COPY . .
ENV PATH="/app/.venv/bin:$PATH"
EXPOSE 8001
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8001"]
```

</CodeGroup>

A few runtime details are explicit in the Dockerfile. The image exposes port `8001`, prepends `/app/.venv/bin` to `PATH`, and starts the app with `uvicorn main:app --host 0.0.0.0 --port 8001`.

The Dockerfile does not define a non-root user, healthcheck instruction, environment-specific configuration, or deployment-time setup. It packages and runs the current minimal service as-is.

## CI workflow

The GitHub workflow runs when changes affect `apps/ai-service/**` or `.github/workflows/ai-service.yml` on pushes and pull requests targeting `main` or `dev`. Its build job works from `apps/ai-service`, installs uv, installs Python, syncs dependencies, and runs Ruff formatting and lint checks.

Publishing happens only on push events. On `main`, the workflow reads `apps/ai-service/VERSION`, bumps the version according to commit message rules, creates a Git tag in the format `ai-service-v<version>`, publishes `ghcr.io/<owner>/gravity-ai-service`, applies the generated version tag and `latest`, and creates a GitHub Release.

On `dev`, the workflow generates a development version using the base version, timestamp, and short SHA. It tags the repository, publishes the same image with the generated version tag and `dev-latest`, and also adds a SHA tag.
