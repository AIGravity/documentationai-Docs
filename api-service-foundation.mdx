## Overview

The API service is a multi-module NestJS application in `apps/api`. It boots a single Nest application, enables CORS, applies global validation and exception handling, configures Swagger/OpenAPI, and connects feature modules for authentication, agents, marketplace, automations, bounties, chat, connections, credits, payouts, subscriptions, referrals, leaderboard, telemetry, and other domain areas. The service uses DTOs for request contracts and Supabase for persistence.

<Callout kind="info">

The health endpoint is one of many routes exposed by the API. The application graph includes feature modules for each domain area, with module-specific controllers, services, DTOs, persistence logic, and supporting providers.

</Callout>

## Bootstrap flow

`apps/api/src/main.ts` creates the Nest application from `AppModule`, enables CORS, configures global request validation and exception handling, sets up Swagger/OpenAPI, and starts the HTTP server. The entrypoint also reads the runtime port from `PORT`, defaulting to `3001`.

<CodeGroup tabs="main.ts,Behavior summary">

```ts
const app = await NestFactory.create(AppModule);

app.enableCors({
  origin: ["http://localhost:3000"],
  credentials: true,
});

app.useGlobalPipes(
  new ValidationPipe({
    whitelist: true,
    forbidNonWhitelisted: true,
    transform: true,
  }),
);

app.useGlobalFilters(new GlobalExceptionFilter());

const config = new DocumentBuilder()
  .setTitle("API")
  .setDescription("API service reference")
  .setVersion("1.0")
  .build();

const document = SwaggerModule.createDocument(app, config);
SwaggerModule.setup("api", app, document);

await app.listen(process.env.PORT || 3001);
```

```ts
// Application behavior:
//
// - Creates the app with NestFactory.create(AppModule)
// - Enables CORS
// - Allows exactly http://localhost:3000
// - Enables credentials
// - Applies a global ValidationPipe
// - Whitelists declared DTO properties
// - Rejects non-whitelisted properties
// - Transforms request values to declared DTO types
// - Applies a global exception filter
// - Generates and serves Swagger/OpenAPI documentation
// - Listens on PORT, defaulting to 3001
// - Logs: 🚀 API running on http://localhost:3001
```

</CodeGroup>

### Application creation

The service starts by calling `NestFactory.create(AppModule)`. `AppModule` is the root of the application graph and makes the imported feature modules, controllers, providers, and persistence integrations available at runtime.

Bootstrap applies cross-cutting behavior before the server starts. Global validation standardizes request handling across modules, while the exception filter provides a consistent error response path.

### CORS configuration

CORS is enabled with `app.enableCors(...)` and allows exactly one origin: `http://localhost:3000`. The configuration also sets `credentials: true`, so browsers can include credentials on cross-origin requests from that origin.

That setup supports local frontend-to-API development. The allowed origin remains defined in the bootstrap configuration rather than being loaded from an environment-based configuration provider.

### Global validation

The global `ValidationPipe` applies DTO validation to incoming requests throughout the application. `whitelist: true` removes properties that are not declared by the target DTO, `forbidNonWhitelisted: true` rejects requests that contain undeclared properties, and `transform: true` converts values to the types declared by DTO metadata where supported.

Feature modules therefore share the same request-validation behavior without registering a separate pipe on each controller.

### Exception handling

A global exception filter handles uncaught application errors at the HTTP boundary. This keeps error formatting consistent across health, authentication, domain, persistence, and other feature routes.

### Swagger and OpenAPI

The bootstrap file builds an OpenAPI document from the application metadata and registers the Swagger UI under the API documentation route. Use the [NestJS API reference](/api-reference/nestjs-api) for the complete endpoint catalog and request and response contracts.

### Port binding

The service listens on the port supplied through `PORT`, with `3001` as the default. Container and deployment configuration must provide a matching port value when the runtime environment uses a different binding.

<Callout kind="alert">

The runtime port is not aligned across the implementation. `main.ts` listens on `PORT` with a default of `3001`, while the Dockerfile exposes `3000`. A container built from the current files advertises one port and may bind another unless the runtime environment supplies a matching `PORT` value.

</Callout>

## Module wiring

`AppModule` imports feature modules for authentication, agents, marketplace, automations, bounties, chat, connections, credits, payouts, subscriptions, referrals, leaderboard, telemetry, and other domain areas. Each feature module declares the controllers, services, DTOs, and persistence providers required for its domain.

### Application module graph

The application graph is organized around domain modules rather than a single controller:

```text
AppModule
├── AuthModule
├── AgentsModule
├── MarketplaceModule
├── AutomationsModule
├── BountiesModule
├── ChatModule
├── ConnectionsModule
├── CreditsModule
├── PayoutsModule
├── SubscriptionsModule
├── ReferralsModule
├── LeaderboardModule
├── TelemetryModule
└── Other domain modules
```

Each module owns its HTTP entrypoints and application logic. DTOs define request and response contracts, services coordinate domain behavior, and Supabase-backed providers handle persistence where the feature requires stored data.

### Cross-cutting module behavior

Authentication, validation, persistence, and API documentation are integrated into the broader application rather than isolated as future extensions. Global bootstrap configuration applies validation and exception handling to every feature module, while Swagger/OpenAPI metadata exposes the available routes and schemas.

## Health endpoint

`GET /health` provides a lightweight service availability check alongside the API's other feature routes. It returns a static JSON object and does not query downstream dependencies.

<CodeGroup tabs="health.controller.ts,Response example">

```ts
@Controller("health")
export class HealthController {
  @Get()
  getHealth() {
    return { status: "ok", service: "api" };
  }
}
```

```json
{
  "status": "ok",
  "service": "api"
}
```

</CodeGroup>

### Route behavior

The route path is `/health` because the controller is decorated with `@Controller("health")` and no global route prefix changes that path. The method is `GET`, and the handler returns a literal object directly from the controller method.

Clients call the endpoint at `/health`, not `/api/health` or `/v1/health`, unless a deployment layer adds an external prefix. For the complete list of routes, schemas, and operations, see the [NestJS API reference](/api-reference/nestjs-api).

### Response shape

The response is a small JSON object with two fields.

<ResponseField name="status" field-type="string" required="true">
Returns `ok` from the health handler.
</ResponseField>

<ResponseField name="service" field-type="string" required="true">
Returns `api` from the health handler.
</ResponseField>

### Health check scope

The health endpoint reports API process availability by returning a static object from the controller. It does not check downstream dependencies or map the result through a separate response DTO.

## Runtime and build

Local development and runtime execution are defined in `apps/api/package.json`, while Nest and TypeScript build behavior is split across `nest-cli.json`, `tsconfig.json`, and `tsconfig.build.json`. The setup is workable as a foundation, but several paths and module settings do not line up cleanly.

<CodeGroup tabs="package.json scripts,package metadata">

```json
{
  "scripts": {
    "dev": "bun --watch src/main.ts",
    "build": "tsc -p tsconfig.build.json",
    "start": "bun dist/main.js",
    "start:prod": "bun ."
  }
}
```

```json
{
  "main": "dist/src/main",
  "type": "commonjs"
}
```

</CodeGroup>

### Runtime scripts

The service defines four runtime and build scripts:

- **`dev`**: Runs `bun --watch src/main.ts`
- **`build`**: Runs `tsc -p tsconfig.build.json`
- **`start`**: Runs `bun dist/main.js`
- **`start:prod`**: Runs `bun .`

The `dev` command runs the TypeScript entrypoint directly in Bun watch mode. The `build` command compiles with TypeScript rather than `nest build`.

### Likely dist path mismatch

The package metadata and runtime scripts point to different built entrypoints. `package.json` declares `main` as `dist/src/main`, while the `start` script runs `dist/main.js`.

<Callout kind="alert">

The compiled output path is likely inconsistent with the `start` script. With `rootDir` set to `./` and the source entrypoint at `src/main.ts`, emitted files likely land under `dist/src/`, which makes `bun dist/main.js` a probable mismatch.

</Callout>

The module settings are also worth noting. TypeScript emits `module: "ESNext"` while `package.json` declares `type: "commonjs"`, which creates a potentially inconsistent runtime model unless Bun is intentionally smoothing over the difference.

## Docker and runtime packaging

The Dockerfile builds the service in one Bun-based stage and runs it in a second Bun-based stage. It copies the built `dist/` directory into the runtime image and starts the service with the production script.

<CodeGroup tabs="Dockerfile build stage,Dockerfile runtime stage">

```dockerfile
FROM oven/bun:1-alpine AS build
WORKDIR /app
COPY package.json bun.lock ./
RUN bun install --frozen-lockfile
COPY . .
RUN bun run build
```

```dockerfile
FROM oven/bun:1-alpine
WORKDIR /app
COPY package.json bun.lock ./
RUN bun install --frozen-lockfile --production
COPY --from=build /app/dist ./dist
EXPOSE 3000
CMD ["bun", "run", "start:prod"]
```

</CodeGroup>

### Build flow inside the image

The build stage installs dependencies from `package.json` and `bun.lock`, copies the application files, and runs `bun run build`. The runtime stage installs production dependencies only, copies `dist/` from the build stage, and starts the container with `bun run start:prod`.

That keeps the final image smaller than a single-stage build and matches the Bun-based local runtime approach used in the package scripts.

### Runtime behavior in the container

The runtime image exposes port `3000` and starts the service with `bun run start:prod`. That command resolves to `bun .`, so the container depends on package metadata to find the entrypoint rather than using an explicit file path.

This is one more place where the current packaging is functional but indirect. Between the `main` value, the `start` script path, and the runtime port configuration, the implementation has multiple assumptions that do not fully agree.

## CI integration

The API workflow in `.github/workflows/api.yml` already covers build, versioning, image publishing, release creation, and a placeholder deploy job. It is more complete than the service implementation itself, but several parts are still scaffolding.

### Trigger and build behavior

The workflow runs on pushes to `main` and `dev` for changes under selected paths, and on pull requests targeting those branches. The build section installs dependencies with `pnpm install --frozen-lockfile` and builds the API with `pnpm --filter @repo/api build`.

The workflow path filters include `apps/api/**`, `packages/**`, `pnpm-lock.yaml`, `tsconfig.base.json`, and the workflow file itself. The inspected tree does not show a `packages/` directory, so that filter currently looks anticipatory or stale.

<CodeGroup tabs="Workflow trigger,Build step">

```yaml
on:
  push:
    branches: [main, dev]
    paths:
      - "apps/api/**"
      - "packages/**"
      - "pnpm-lock.yaml"
      - "tsconfig.base.json"
      - ".github/workflows/api.yml"
  pull_request:
    branches: [main, dev]
```

```yaml
- name: Install dependencies
  run: pnpm install --frozen-lockfile

- name: Build
  run: pnpm --filter @repo/api build
```

</CodeGroup>

### Versioning and tagging

The workflow reads the base version from `apps/api/VERSION`, which currently contains `0.1.0`. On `main`, it bumps major, minor, or patch based on commit message rules. On `dev`, it creates a prerelease version in the form `base-dev.timestamp.shortsha`.

It then tags releases as `api-v<version>`. On `main`, the workflow also writes the bumped version back to `apps/api/VERSION`, commits it, and pushes the change.

### Docker publishing and releases

The workflow publishes a container image to `ghcr.io/<owner>/gravity-api`. Tags include the exact version, `latest` on `main`, `dev-latest` on `dev`, and a SHA-based tag.

On `main`, the workflow also creates a GitHub Release named `API v<version>`. The release body includes the published image reference.

### Deploy step status

The deploy job exists, but it does not perform a real deployment yet. The inspected workflow only writes a deployment summary, and the actual deploy commands are commented placeholders.

<Callout kind="alert">

The CI pipeline includes release and deployment scaffolding, but deployment is not implemented. The deploy job is placeholder-only in the current workflow.

</Callout>

## Current limitations

<Callout kind="info">

The API includes DTOs, authentication, Supabase persistence, domain modules, Swagger/OpenAPI documentation, and global request validation. CI still has no active test step, and the workflow job labeled Build and Lint does not include a lint step.

</Callout>

The service now provides a multi-module NestJS foundation with shared bootstrap behavior, domain-specific application modules, validated request contracts, Supabase-backed persistence, and generated API documentation. The remaining foundation work is concentrated in infrastructure alignment and delivery quality, especially the runtime port configuration, the likely built-entry path mismatch, and active test and lint steps in CI.
