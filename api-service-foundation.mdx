## Overview

The API service is a full NestJS application in `apps/api`. It boots a multi-module API with authentication, Supabase persistence, domain modules, DTOs, validation, and external service integrations. The surrounding build and delivery setup includes Bun scripts, a Dockerfile, and GitHub Actions workflows for building, publishing, and deploying the service.

<Callout kind="info">

The current module graph spans authentication, marketplace, agent management, payments, Activepieces integration, Supabase persistence, bounties, builder tools, chat, referrals, notifications, and supporting infrastructure. The `GET /health` endpoint remains available, but it is no longer the only application endpoint.

</Callout>

## Bootstrap flow

`apps/api/src/main.ts` creates the Nest application from `AppModule`, enables CORS, and starts the HTTP server. The inspected bootstrap behavior still keeps the allowed origin and listening port in the entrypoint rather than driving them from environment-based configuration.

<CodeGroup tabs="main.ts,Behavior summary">

```ts
const app = await NestFactory.create(AppModule);

app.enableCors({
  origin: ["http://localhost:3000"],
  credentials: true,
});

await app.listen(3001);
```

```ts
// Grounded behavior from the inspected file:
//
// - Creates the app with NestFactory.create(AppModule)
// - Enables CORS
// - Allows exactly http://localhost:3000
// - Enables credentials
// - Listens on port 3001
// - Logs: 🚀 API running on http://localhost:3001
```

</CodeGroup>

### Application creation

The service starts by calling `NestFactory.create(AppModule)`. That makes `AppModule` the root of the application graph and defines the controllers, providers, guards, strategies, integrations, and feature modules available at runtime.

`AppModule` now imports the service's domain and infrastructure modules. Bootstrap still does not configure global pipes, interceptors, filters, or prefixes in the inspected entrypoint, while validation and request shaping are handled within the application's DTO and module implementations.

### CORS configuration

CORS is enabled with `app.enableCors(...)` and allows exactly one origin: `http://localhost:3000`. The configuration also sets `credentials: true`, so browsers can include credentials on cross-origin requests from that origin.

That setup supports local frontend-to-API development, but it is not dynamic. The service does not read allowed origins from environment variables or a configuration module in the inspected bootstrap file.

### Port binding

The service binds to port `3001` with `app.listen(3001)`. There is no `process.env.PORT` handling in the inspected source, so the listening port remains fixed in code.

<Callout kind="alert">

The runtime port is not aligned across the implementation. `main.ts` listens on `3001`, while the Dockerfile exposes `3000`. A container built from the current files advertises one port and binds another.

</Callout>

### Current module graph

The application graph is organized around feature areas and shared infrastructure:

- **Authentication** provides JWT guards and strategies for protected routes and authenticated request handling.
- **Marketplace** covers catalog access, publishing, workflow runs, consumer connections, and file proxy behavior.
- **Agent management** covers agent CRUD, builder fields, administrative review, and agent ranking.
- **Payments** handles credits, subscriptions, payouts, and payin routing through Stripe and Razorpay.
- **Activepieces integration** handles sessions, user provisioning, flow management, and capability detection.
- **Supabase** provides persistence for application data and is backed by more than 50 migrations.
- **Platform features** include bounties, builder tools, chat, notifications, referrals, and related supporting infrastructure.

The feature modules contain their own controllers and services, while shared authentication and persistence concerns support multiple areas of the application. The current graph therefore extends well beyond the original health controller foundation.

### What is wired

The inspected application now includes the primary concerns expected from a multi-module API:

- authentication modules with JWT guards and strategies
- DTO classes with request validation
- Supabase persistence with more than 50 migrations
- domain modules and services across marketplace, agent management, and payments
- Stripe and Razorpay payment integrations
- Activepieces session, provisioning, flow, and capability integrations
- supporting modules for bounties, builder tools, chat, notifications, and referrals

## Health endpoint

The health endpoint remains the simplest route in the service. It returns a plain inline object and does not use a DTO, schema, or health-check integration package.

<CodeGroup tabs="health.controller.ts,Response example">

```ts
@Controller("health")
export class HealthController {
  @Get()
  getHealth() {
    return { status: "ok", service: "api" };
  }
}
```

```json
{
  "status": "ok",
  "service": "api"
}
```

</CodeGroup>

### Route behavior

The route path is `/health` because the controller is decorated with `@Controller("health")` and there is no global prefix configured in `main.ts`. The method is `GET`, and the handler returns a literal object directly from the controller method.

Because there is no API versioning or prefix configuration in the bootstrap file, clients call the endpoint at `/health`, not `/api/health` or `/v1/health`.

### Response shape

The response is a small JSON object with two fields.

<ResponseField name="status" field-type="string" required="true">
Returns `ok` in the current implementation.
</ResponseField>

<ResponseField name="service" field-type="string" required="true">
Returns `api` in the current implementation.
</ResponseField>

### What the endpoint does not include

The health endpoint is intentionally bare. It does not check downstream dependencies, validate output through a schema, or map through a response DTO.

There is also no health library integration in the inspected files. The endpoint reports service availability by returning a static object from the controller.

## Runtime and build

Local development and runtime execution are defined in `apps/api/package.json`, while Nest and TypeScript build behavior is split across `nest-cli.json`, `tsconfig.json`, and `tsconfig.build.json`. The setup supports the expanded application, but several paths and module settings do not line up cleanly.

<CodeGroup tabs="package.json scripts,package metadata">

```json
{
  "scripts": {
    "dev": "bun --watch src/main.ts",
    "build": "tsc -p tsconfig.build.json",
    "start": "bun dist/main.js",
    "start:prod": "bun ."
  }
}
```

```json
{
  "main": "dist/src/main",
  "type": "commonjs"
}
```

</CodeGroup>

### Runtime scripts

The service defines four runtime and build scripts:

- **`dev`**: runs `bun --watch src/main.ts`
- **`build`**: runs `tsc -p tsconfig.build.json`
- **`start`**: runs `bun dist/main.js`
- **`start:prod`**: runs `bun .`

The `dev` command runs the TypeScript entrypoint directly in Bun watch mode. The `build` command compiles with TypeScript rather than `nest build`.

### Likely dist path mismatch

The package metadata and runtime scripts point to different built entrypoints. `package.json` declares `main` as `dist/src/main`, while the `start` script runs `dist/main.js`.

<Callout kind="alert">

The compiled output path is likely inconsistent with the `start` script. With `rootDir` set to `./` and the source entrypoint at `src/main.ts`, emitted files likely land under `dist/src/`, which makes `bun dist/main.js` a probable mismatch.

</Callout>

The module settings are also worth noting. TypeScript emits `module: "ESNext"` while `package.json` declares `type: "commonjs"`, which creates a potentially inconsistent runtime model unless Bun is intentionally smoothing over the difference.

## Docker and runtime packaging

The Dockerfile builds the service in one Bun-based stage and runs it in a second Bun-based stage. It copies the built `dist/` directory into the runtime image and starts the service with the production script.

<CodeGroup tabs="Dockerfile build stage,Dockerfile runtime stage">

```dockerfile
FROM oven/bun:1-alpine AS build
WORKDIR /app
COPY package.json bun.lock ./
RUN bun install --frozen-lockfile
COPY . .
RUN bun run build
```

```dockerfile
FROM oven/bun:1-alpine
WORKDIR /app
COPY package.json bun.lock ./
RUN bun install --frozen-lockfile --production
COPY --from=build /app/dist ./dist
EXPOSE 3000
CMD ["bun", "run", "start:prod"]
```

</CodeGroup>

### Build flow inside the image

The build stage installs dependencies from `package.json` and `bun.lock`, copies the application files, and runs `bun run build`. The runtime stage installs production dependencies only, copies `dist/` from the build stage, and starts the container with `bun run start:prod`.

That keeps the final image smaller than a single-stage build and matches the Bun-based local runtime approach used in the package scripts.

### Runtime behavior in the container

The runtime image exposes port `3000` and starts the service with `bun run start:prod`. That command resolves to `bun .`, so the container depends on package metadata to find the entrypoint rather than using an explicit file path.

This is one more place where the current packaging is functional but indirect. Between the `main` value, the `start` script path, and the hardcoded port in `main.ts`, the implementation has multiple runtime assumptions that do not fully agree.

## CI integration

The API workflow in `.github/workflows/api.yml` covers pull request validation, versioning, image publishing, and release-related automation. Production deployment is handled separately by the unified deployment workflow at `.github/workflows/deploy-new-account.yml`.

### Trigger and build behavior

The API workflow runs on pull requests targeting `main` and `dev`. The build section installs dependencies with `pnpm install --frozen-lockfile` and builds the API with `pnpm --filter @repo/api build`.

The workflow path filters include `apps/api/**`, `packages/**`, `pnpm-lock.yaml`, `tsconfig.base.json`, and the workflow file itself. The inspected tree does not show a `packages/` directory, so that filter currently looks anticipatory or stale.

<CodeGroup tabs="Workflow trigger,Build step">

```yaml
on:
  pull_request:
    branches: [main, dev]
```

```yaml
- name: Install dependencies
  run: pnpm install --frozen-lockfile

- name: Build
  run: pnpm --filter @repo/api build
```

</CodeGroup>

### Versioning and tagging

The workflow reads the base version from `apps/api/VERSION`, which currently contains `0.1.0`. On `main`, it bumps major, minor, or patch based on commit message rules. On `dev`, it creates a prerelease version in the form `base-dev.timestamp.shortsha`.

It then tags releases as `api-v<version>`. On `main`, the workflow also writes the bumped version back to `apps/api/VERSION`, commits it, and pushes the change.

### Docker publishing and releases

The workflow publishes a container image to `ghcr.io/<owner>/gravity-api`. Tags include the exact version, `latest` on `main`, `dev-latest` on `dev`, and a SHA-based tag.

On `main`, the workflow also creates a GitHub Release named `API v<version>`. The release body includes the published image reference.

### Deployment workflow

Production deployment is handled by `.github/workflows/deploy-new-account.yml`, rather than by the API workflow's build and release steps. The unified deployment workflow builds images, pushes them to Amazon ECR, and updates the corresponding ECS services.

This separates API image creation and release metadata from the deployment process that promotes container images into the production runtime.

## Current limitations

<Callout kind="danger">

The API service is now a multi-module backend, but several operational concerns remain:

- `main.ts` listens on `3001` while the Dockerfile exposes `3000`
- the compiled output path may not match the `start` script
- the API workflow has no active test step
- the API workflow has no lint step, even though the workflow job is labeled Build and Lint

</Callout>

The implementation now supports authentication, DTO validation, Supabase persistence, domain services, external integrations, and multiple product areas. The next layer of operational work should resolve the runtime mismatches and add explicit test and lint execution to CI.
