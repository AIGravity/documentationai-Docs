## Overview

This page documents the FastAPI AI service routes currently implemented in the AIGravity core repository. Based on code analysis of `apps/ai-service/main.py`, the service exposes two endpoints today: `GET /health` and `POST /chat`.

### Dual-LLM interaction architecture

The chat endpoint uses a guide-and-responder architecture. The guide LLM, or LLM1, analyzes the conversation, chooses an operating mode, and derives the structured spec for the turn. The responder LLM, or LLM2, writes the user-facing reply from that state.

The guide runs at temperature `0.0` to produce deterministic JSON output. The responder runs at temperature `0.3` to keep replies natural while still following the guide's state and constraints.

The guide supports six modes:

- `clarify`
- `about_gravity`
- `general_help`
- `list_agents`
- `off_topic`
- `handoff`

On `handoff`, the service performs an agent search. If agents are found, the service returns the tools-selection prompt, sets `show_tool_selection` to `true`, and writes `awaiting_tools` in `info_json` for the next turn. If no agents are found, the service sets `ready_to_query` to `true` and returns the no-agent handoff phrase.

The guide re-derives the spec on every turn. That spec is authoritative for the turn, so previously collected fields can be dropped if the new guide output no longer includes them. The service does not union-merge old and new extracted fields.

<Callout kind="info">

Platform selection is no longer required for handoff. A single concrete use case is sufficient to move the conversation into agent search.




</Callout>

### Vector search threshold

Agent matching now uses a stricter default vector distance threshold. The default changed from `0.30` to `0.22`, which reduces weaker matches and favors fewer, higher-quality results.

<Callout kind="info">

Configure the threshold with the `SEARCH_VECTOR_DIST_THRESHOLD` environment variable.




</Callout>

## Implementation notes

The FastAPI file defines the application with `app = FastAPI()` and registers the `GET /health` and `POST /chat` handlers directly. No response model is defined for the health route, and chat behavior is driven by the dual-LLM interaction flow and supporting search, memory, and guardrail logic in the service layer.

## Likely error responses

The current implementation combines framework-default errors with application-level degraded and blocked responses.

- **`404 Not Found`** — Returned when you request a path that is not defined.
- **`404 Not Found`** — Returned when you use a path or method combination that does not match an implemented route.
- **`503 Service Unavailable`** — Returned by the chat flow when no LLM API key is configured.
- **`500 Internal Server Error`** — Returned when the service encounters an unhandled exception.
- **`200 OK` with guardrail block** — Returned when the guardrail rejects the message. The response includes `reply` set to `I cannot process this request. Reason: reason`, `ready_to_query` set to `false`, `show_tool_selection` set to `false`, `top_agents` set to an empty array, `suggested_tools` set to an empty array, and `llm_calls` set to `0`.
- **`200 OK` with degraded response** — Returned when part of the chat pipeline fails but the service still produces a response. If the guide LLM fails, mode falls back to `clarify`, `llm_calls` is `0`, and the responder still produces a reply. If the responder fails, the service returns a fallback message.
