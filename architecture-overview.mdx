## Overview

Gravity is a multi-service monorepo with three independently runnable applications under `apps/`: a Remix frontend at `apps/web`, a NestJS API at `apps/api`, and a FastAPI service at `apps/ai-service`. The applications now support persistent data through Supabase, JWT-based authentication, multiple domain modules, external integrations, and implemented cross-service request flows.

The current architecture combines product-facing applications with distributed backend services. The API coordinates authentication, marketplace features, agents, payments, builder tools, workflows, and other domain capabilities. It also calls the AI service for chat, verification, and agent review, and calls Activepieces for workflow management. The AI service integrates with LLM providers, persistence, caching, search, and content-safety systems.

<Callout kind="info">

`pnpm-workspace.yaml` includes `packages/*`, and the README describes shared packages. The current repository may still contain fewer shared packages than the broader architecture anticipates, but the primary application capabilities now live inside the service modules.

</Callout>

A few root files define the monorepo shape directly:

- `package.json` defines root development commands that delegate into the app workspaces.
- `scripts/bootstrap.sh` installs toolchains and service dependencies across JavaScript, Bun, and Python environments.

## Monorepo orchestration layer

The repo uses `pnpm` workspaces for package coordination and Turborepo for task orchestration. The workspace now contains substantial application modules, domain logic, persistence integrations, and service boundaries in addition to the shared operational tooling.

The root `package.json` defines workspace-level commands such as `dev:web`, `dev:api`, and `dev`. Those commands establish the local development pattern: run services independently when needed, or run them in parallel through Turbo.

<Callout kind="alert">

The root script `dev:py` points to `apps/py-service`, but the actual Python service lives at `apps/ai-service`. That script is stale relative to the repository tree.

</Callout>

## Service architecture

### `apps/web`: Remix frontend

`apps/web` is the user-facing frontend for Gravity's product workflows. It uses Remix with Vite and React and now includes builder dashboards, admin dashboards, agent customization flows, marketplace experiences, and API-backed application interfaces.

The main entry file is `apps/web/app/root.tsx`. That file defines the document shell, global styles, font links, an `ErrorBoundary`, and the route outlet. Route modules under `apps/web/app/routes/` compose the user-facing flows and connect them to the API through client utilities and shared components.

The frontend contains multiple route modules rather than only the initial starter routes. Current areas include:

- Builder interfaces for creating and configuring agents and workflows.
- Admin dashboards for operational and marketplace management.
- Agent customization and review flows.
- Marketplace and payment-related user interfaces.
- API-integrated routes that load and mutate application data.
- Shared components and frontend utilities used across route modules.

`apps/web/vite.config.ts` shows the active frontend stack:

- Remix
- Vite
- Tailwind CSS
- TypeScript path support

The frontend calls the API for application data and domain operations. The API remains the primary backend boundary for authentication, marketplace features, agents, payments, workflows, and related product capabilities.

### `apps/api`: NestJS API on Bun

`apps/api` is the TypeScript backend boundary. It uses NestJS for the HTTP framework, Bun as the runtime for local development and execution, and TypeScript compilation to `dist/` for builds.

The service boots from `apps/api/src/main.ts`. That file creates the Nest application, configures CORS, applies request validation, and starts the API listener.

The root module composes a multi-module NestJS application. Modules cover authentication, marketplace functionality, agent management, payments, Activepieces integration, Supabase persistence, builder tools, bounties, chat, and other supporting domain areas.

The health controller remains available as an operational endpoint, but it is one controller among many. The API now follows a controller-to-service architecture with DTOs, guards, persistence adapters, and domain-specific modules behind the HTTP boundary.

`apps/api` coordinates requests across the frontend, AI service, external workflow systems, payment providers, and persistence layer. It is the primary application integration point rather than a thin health-check service.

### `apps/ai-service`: FastAPI Python service

`apps/ai-service` hosts AI-related functionality behind a dedicated Python service boundary. It uses FastAPI with composed routers, service classes, Pydantic models, dependency injection, and integrations for model inference, agent evaluation, search, caching, and content safety.

The service includes functionality for:

- Chat and conversational requests.
- Agent verification and agent review.
- Credits and usage tracking.
- Guardrails and content-safety checks.
- Search indexing and retrieval.
- LLM provider integrations through OpenAI, OpenRouter, and Gemini.
- Supabase persistence for service data.
- Redis caching for runtime and session-related data.
- Typesense search integration.
- AWS Bedrock content-safety support.

The Python project configuration lives in `apps/ai-service/pyproject.toml`. Dependencies include FastAPI, Pydantic, and Uvicorn, with Ruff and Pytest declared for development. The service now uses that foundation for multiple application routes and supporting service layers rather than only a health endpoint.

## Entry points and request handling

Each application has a clear entry point and now exposes a broader request surface across product, operational, and integration workflows.

### Web routes

The frontend entry point is `apps/web/app/root.tsx`, with route modules under `apps/web/app/routes/`.

The current route tree includes:

- `/`, defined by `apps/web/app/routes/_index.tsx`
- `/home`, defined by `apps/web/app/routes/home.tsx`
- Builder and agent customization routes.
- Admin dashboard routes.
- Marketplace and payment-related routes.
- API-integrated routes for loading and updating application state.

Routes use Remix modules and shared frontend components to present product workflows. API client integration connects route loaders and actions to the NestJS backend.

### API routes

The API entry point is `apps/api/src/main.ts`. Its route surface spans multiple NestJS modules, including:

- Authentication, signup, login, OTP, password reset, OAuth, and session refresh.
- Agent creation, configuration, verification, and review.
- Marketplace listings and related commerce workflows.
- Payments, subscriptions, referrals, and payouts.
- Bounties and builder tools.
- Chat and AI-backed application flows.
- Activepieces workflow import, execution, and provisioning.
- Health and operational endpoints.

The repository README reportedly references `/api/health`, but `apps/api/src/main.ts` does not set a global prefix. Based on the code, the implemented health route is `/health`, not `/api/health`.

### AI service routes

The AI service entry point is `apps/ai-service/main.py`. It composes multiple `APIRouter` instances for chat, agent review, agent verification, credits and usage, search, and supporting service operations.

Requests pass through dependency injection, usage tracking, guardrail checks, and provider-specific service layers. The service can persist data through Supabase, cache runtime state through Redis, index or query content through Typesense, and call supported LLM and safety providers.

## Module relationships and service boundaries

The repository has clear top-level service separation and implemented internal layering:

- `apps/web` for the frontend and user-facing route modules.
- `apps/api` for the TypeScript backend and application orchestration.
- `apps/ai-service` for AI-specific processing and provider integrations.

Inside those boundaries, the API follows a module-based NestJS architecture with controllers, services, DTOs, guards, and persistence integrations. Authentication, marketplace, agents, payments, workflows, bounties, builder tools, and chat have distinct domain areas while sharing the API application's infrastructure.

The AI service uses `APIRouter` composition with service classes and Pydantic models. The frontend separates route modules, API client integration, shared components, and user-facing feature areas.

### Current cross-service wiring

The services communicate through implemented application flows rather than only through naming and configuration.

- `apps/web` calls `apps/api` for authentication, application data, agent workflows, marketplace operations, payments, and other product actions.
- `apps/api` calls `apps/ai-service` for chat, agent verification, and agent review.
- `apps/api` calls Activepieces for workflow import, execution, and provisioning.
- `apps/ai-service` connects to OpenAI, OpenRouter, and Gemini for LLM capabilities.
- `apps/ai-service` uses Supabase for persistence, Redis for caching, Typesense for search, and AWS Bedrock for content-safety checks.
- The backend services also integrate with payment, analytics, error tracking, email, and tool-integration providers.

The architecture therefore has both browser-to-API and backend-to-backend request flows. Each service retains a focused boundary while participating in broader product workflows.

## Persistence, middleware, auth, and external services

### Database and persistence

The system uses Supabase, backed by PostgreSQL, as its primary persistence layer. More than 50 SQL migrations cover profiles, workflows, agents, bounties, marketplace data, payments, subscriptions, referrals, reviews, notifications, and related application state.

Supabase provides the database and user identity foundation used by the API and supporting services. Redis provides session caching and runtime caching for workflows that need fast access to temporary or frequently accessed data.

### Middleware

Middleware and request-level infrastructure now cover cross-cutting application concerns across the services.

- In `apps/api`, JWT guards and authentication strategies enforce protected routes.
- The API configures CORS for browser clients and applies request validation for incoming payloads.
- In `apps/ai-service`, middleware and dependencies support dependency injection, usage tracking, and guardrail checks.
- Shared service infrastructure propagates authenticated identity and request context into domain operations where required.

These layers allow individual domain modules to focus on application behavior while authentication, validation, usage limits, and safety checks remain consistent across requests.

### Authentication and authorization

The API implements JWT-based authentication with guards, strategies, and Supabase-backed user identity. Auth modules handle login, signup, OTP verification, password reset, Google OAuth, and session refresh.

Protected API routes use guards and authenticated request context to enforce access to user-specific resources. The frontend integrates with these flows through its API client and route modules.

### External services and integrations

Gravity integrates with external systems across workflows, persistence, payments, search, AI, observability, and communication.

Present today:

- Activepieces for workflow import, execution, and provisioning.
- Supabase for PostgreSQL persistence and user identity.
- Stripe and Razorpay for payments.
- PayPal for payouts.
- Typesense for search.
- Redis for caching.
- OpenAI, OpenRouter, and Gemini for LLM providers.
- AWS Bedrock for guardrails and content safety.
- Composio for tool integration.
- PostHog for analytics.
- Sentry for error tracking.
- SMTP for email delivery.
- Google Fonts references in `apps/web/app/root.tsx`.
- GitHub Container Registry publishing through the service workflows.

## Build, release, and deployment tooling

The operational layer supports independent service builds alongside coordinated production deployment. Each app has tooling to build, version, containerize, test, and publish independently.

### Local setup

`scripts/bootstrap.sh` checks for `pnpm`, `bun`, and `uv`, then installs dependencies for the JavaScript and Python services. That script reflects the repo's polyglot design: each app uses the native tooling expected for its runtime.

### Versioning

Each app has a local `VERSION` file:

- `apps/web/VERSION`
- `apps/api/VERSION`
- `apps/ai-service/VERSION`

`scripts/version-bump.sh` updates those version files, establishing per-service version management rather than one monorepo-wide application version.

### Containers and CI/CD

Each service has its own Dockerfile:

- `apps/web/Dockerfile`
- `apps/api/Dockerfile`
- `apps/ai-service/Dockerfile`

Each service also has its own GitHub Actions workflow:

- `.github/workflows/web.yml`
- `.github/workflows/api.yml`
- `.github/workflows/ai-service.yml`

The service workflows run PR-focused build and verification checks. Pushes to `main` trigger the production deployment flow. The unified `deploy-new-account.yml` workflow performs real AWS ECS deployments rather than stopping at placeholder deployment sections.

The CI/CD layer supports version generation, testing, Docker image publishing to GitHub Container Registry, GitHub release creation, and deployment of the services to AWS ECS.

## Notable gaps and inconsistencies

A few repo details can still mislead an architectural review unless they are called out directly.

### Shared packages may not cover the full intended architecture

`pnpm-workspace.yaml` includes `packages/*`, and the README describes shared packages for types, UI, and config. The current architecture has substantial service-local modules, but the shared package layer may still be smaller than the full contract-sharing design anticipates.

That distinction matters when evaluating where shared types, UI primitives, and configuration are maintained. Service-local implementations should not automatically be assumed to come from a shared workspace package.

### Script and naming drift around the Python service

The repository uses `apps/ai-service` as the actual Python service path, but some root-level references still point to `py-service`. The most concrete example is the root `package.json` script that targets `apps/py-service`.

This inconsistency affects local development expectations and is a sign that repo documentation and scripts have not fully caught up with the current directory structure.

### API route documentation mismatch

The README references `/api/health`, but the implemented Nest app does not set a global prefix in `apps/api/src/main.ts`. The existing controller path in `apps/api/src/health/health.controller.ts` therefore resolves to `/health`.

When evaluating the system, trust the source files over the README for the current health route shape.

### Testing spans multiple suites

Testing is no longer only an intended capability. The repository contains multiple test suites across the services, and CI workflows include verification steps. Coverage and depth can continue to expand as additional domain modules and integrations mature.

<Callout kind="info">

The strongest parts of the current architecture are its explicit service boundaries, Supabase-backed persistence, JWT authentication, domain-module structure, cross-service integrations, and production deployment automation. The main areas of evolution are broader shared package adoption, continued test coverage, and further refinement of distributed workflows and operational observability.

</Callout>

## What this architecture means today

Gravity has chosen and implemented its primary service boundaries, runtimes, persistence model, authentication approach, domain modules, and cross-service integration patterns. The web application calls the API for product workflows, the API coordinates domain and external services, and the AI service provides specialized processing backed by multiple providers and infrastructure systems.

The repository now represents an implemented distributed system with active product capabilities rather than only an application scaffold. Remaining work focuses on expanding feature depth, consolidating shared contracts where useful, increasing test coverage, refining deployment and observability practices, and evolving service-to-service workflows as the product grows.
