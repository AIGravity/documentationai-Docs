## Overview

Gravity currently provides an early-stage monorepo foundation with a thin frontend shell, two service health endpoints, per-service version files, and CI workflows that build and publish containers. The implemented surface is operational scaffolding, not a complete product workflow.

<Callout kind="info">

This page separates verified capabilities from planned or missing product behavior. The current repository does not yet include authentication, persistence, business workflow UI, or AI model integration.

</Callout>

## Implemented capabilities

### Frontend shell

The frontend in `apps/web` is a Remix application built through Vite. It imports Tailwind CSS through the Tailwind v4 package and Vite plugin, loads global styling from `app.css`, and defines a basic document shell in `root.tsx`.

The implemented routes are still scaffold routes. Both `/` and `/home` render the shared welcome screen, so the frontend proves that routing, styling, metadata, error handling, local scripts, and container packaging are wired, but it does not yet represent a Gravity-specific user workflow.

### API service health

The API service in `apps/api` is a minimal NestJS app. `AppModule` registers only `HealthController`, and the service exposes one application endpoint at `GET /health`.

```json
{
  "status": "ok",
  "service": "api"
}
```

That response confirms the API process is reachable. The endpoint does not check downstream dependencies because no database, queue, auth provider, or external integration is currently wired into the service.

### AI service health

The AI service in `apps/ai-service` is a minimal FastAPI app with one custom route at `GET /health`.

```json
{
  "status": "ok"
}
```

The service currently provides a runtime foundation for future AI behavior. The inspected implementation does not include model providers, prompts, inference routes, background jobs, vector storage, or orchestration code.

### Versioning and releases

Gravity tracks service versions independently. The web, API, and AI service each have a `VERSION` file currently set to `0.1.0`, and repository automation can bump those values by service.

The CI workflows use those versions to create service-specific tags and releases, such as `web-v0.1.0`, `api-v0.1.0`, and `ai-service-v0.1.0`. That structure lets each service move at its own release pace instead of forcing every repository change into one global product version.

### Container publishing

Each service includes container packaging and workflow support for publishing images to GitHub Container Registry. The workflows publish service-specific images for the web app, API service, and AI service, with tags for exact versions, branch aliases, and commit SHAs.

This is the most complete part of the current operational surface. Deployment jobs exist as scaffolding, but the workflows do not yet perform a real environment deployment.

## Current limitations

<Callout kind="alert">

Gravity is not yet a feature-complete application. The repository currently implements service scaffolding, health checks, versioning, and container publishing, but the product layer is still missing.

</Callout>

The following capabilities are not implemented in the verified repository state:

- **Authentication and sessions** — no login routes, auth guards, JWT handling, or session UI are wired into the web or API services.
- **Persistence** — no database driver, ORM, migration system, repositories, or persisted domain models are present.
- **Business workflow UI** — the frontend still renders starter welcome routes rather than dashboards, forms, project workflows, or domain-specific screens.
- **AI model integration** — the AI service has no model SDKs, inference endpoints, prompt orchestration, vector storage, or provider configuration.
- **Production deployment logic** — CI includes deployment placeholders, but the current workflows stop short of deploying a running environment.

## How to read the current state

Gravity is best understood as a service foundation with release infrastructure already taking shape. The repository can boot a frontend shell, answer health checks from the API and AI services, build service artifacts, version services independently, and publish containers.

The next product milestone would need to add domain behavior on top of that foundation: application screens, authenticated API flows, persisted data models, and real AI service capabilities. Until those pieces exist, the health endpoints and release pipelines are the clearest signals of what works today.
