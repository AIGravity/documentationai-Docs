## Overview

AIGravity/core currently does not define a model layer. The analyzed codebase contains no ORM or database models, no migration files, no DTO classes, and no named validation schemas in either the NestJS API or the FastAPI service.

What exists today is limited to two inline response shapes returned by health endpoints. Those shapes are API responses, not persisted entities, and they do not declare relationships, validation rules, or storage mappings.

<Callout kind="info">

This reference inventories what is present in the checked-in repository today. It does not describe planned architecture, intended schemas, or future database work.


</Callout>

## Persistence and migration status

No persistence layer is implemented in the analyzed codebase. The repository contains no Prisma schema, no TypeORM entities, no Drizzle tables, no Mongoose schemas, no SQLAlchemy models, no Sequelize models, and no Knex-based schema definitions.

Migration infrastructure is also absent. No `migrations` directory, ORM-managed migration history, or SQL migration files were found in the analyzed code.

### Repository-level signals

- The NestJS API exposes a single health controller with an inline object response.
- The FastAPI service exposes a single health endpoint with an inline object response.
- `pydantic` is present as a Python dependency, but no `BaseModel` classes are defined.
- The repository README describes shared schemas and database work as planned rather than implemented.

## Consumer input model

Published agents now define a consumer input model that controls what a consumer sees and fills in before running a workflow. Each input maps a form field in the run experience to one or more workflow parameters.

### ConsumerInput

The `ConsumerInput` object represents one field in the published agent form. The platform uses this shape when publishing agents and when rendering the consumer run form.

<ResponseField name="label" field-type="string" required="true">

Display name shown to the consumer in the run form.


</ResponseField>

<ResponseField name="paramPath" field-type="string" required="true">

Workflow parameter path that this input writes to.


</ResponseField>

<ResponseField name="type" field-type="ConsumerInputType" required="true">

Input field type. Supported values are `text`, `dropdown`, `multi-dropdown`, `dynamic-dropdown`, `dynamic-multi-dropdown`, `dynamic-cascade`, `date`, `file`, and `array`.


</ResponseField>

<ResponseField name="refreshers" field-type="string[]" required="false">

List of other input `paramPath` values whose answers trigger this input to refresh its available options. Use this for dependent fields such as a Worksheet selector that depends on the selected Spreadsheet.


</ResponseField>

<ResponseField name="targets" field-type="string[]" required="false">

Additional workflow parameter paths that receive the same value as `paramPath`. When a consumer answers this field, the platform writes that answer to the primary path and to every path in `targets`.


</ResponseField>

<ResponseField name="required" field-type="boolean" required="false">

Controls whether the consumer must provide a value before running the agent.


</ResponseField>

<ResponseField name="defaultValue" field-type="string" required="false">

Pre-filled default value shown in the run form.


</ResponseField>

<ResponseField name="options" field-type="array" required="false">

Static options used by dropdown-style inputs.


</ResponseField>

<Callout kind="info">

The `array` type and `targets` field were introduced in the latest platform update. `dynamic-cascade` is now fully supported on the agent publish path.


</Callout>

### ConsumerInputType

The `ConsumerInputType` union defines how the run form renders a field and how the platform interprets the submitted value.

- `text` — Free-text input
- `dropdown` — Single-select dropdown with static options
- `multi-dropdown` — Multi-select dropdown with static options
- `dynamic-dropdown` — Single-select dropdown whose options are fetched at runtime
- `dynamic-multi-dropdown` — Multi-select dropdown whose options are fetched at runtime
- `dynamic-cascade` — Cascading select whose options depend on the value of another field and is now supported on all publish paths
- `date` — Date picker
- `file` — File upload
- `array` — Array input; scalar string values are auto-split on commas or newlines

### Published workflow metadata

Agent publish now records additional workflow metadata that affects how a published agent is displayed and run.

<ResponseField name="deploymentMode" field-type="string" required="true">

How the agent runs. Supported values are `on-demand` for manually triggered runs and `scheduled` for cron-based runs. The selected mode determines which consumer UI card the platform shows.


</ResponseField>

<ResponseField name="triggerMetadata" field-type="object" required="false">

Scheduling metadata for `scheduled` agents, such as the cron expression and related trigger details.


</ResponseField>

<ResponseField name="creditCost" field-type="number" required="true">

Estimated credit cost per run. The platform calculates this value at publish time from the workflow's AI and agent node count.


</ResponseField>

## Gaps and implications

The current codebase exposes service health, but it does not yet define durable application data structures. That has several practical implications for anyone reading the repository as a backend reference.

- **No canonical domain entities** — There is no checked-in source of truth for business objects.
- **No validation contract** — Request and response validation rules are not formalized in DTOs or schema classes.
- **No persistence contract** — No model maps to a database table, collection, or record.
- **No migration history** — Schema changes cannot be tracked because no schema layer exists yet.
- **Limited reuse across services** — Shared contracts are not implemented as reusable schema packages.

<Callout kind="danger">

Treat the current response objects as endpoint-local shapes only. They should not be interpreted as stable domain models, database entities, or cross-service contracts.


</Callout>
