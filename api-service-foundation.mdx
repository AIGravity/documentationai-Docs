## Overview

The API service is the NestJS backend for the Gravity platform, running in `apps/api` on Bun. It boots a NestJS application with environment-driven CORS, global validation, Swagger API documentation, Sentry error tracking, and PostHog analytics. The application registers modules for authentication, chat, agent marketplace, billing, subscriptions, credits, payouts, referrals, bounties, candidates, leaderboards, telemetry, and health checks.

## Bootstrap flow

`apps/api/src/main.ts` creates the Nest application from `AppModule`, loads environment-driven configuration, enables CORS, configures request validation and observability, registers Swagger, and starts the HTTP server. The bootstrap also preserves raw request bodies for webhook HMAC verification.

<CodeGroup tabs="main.ts,Behavior summary">

```ts
const corsOrigins = process.env.CORS_ORIGINS
  ?.split(",")
  .map((origin) => origin.trim())
  .filter(Boolean) ?? [
    "http://localhost:3000",
    "http://localhost:5173",
    "http://localhost:5174",
  ];

const app = await NestFactory.create(AppModule, {
  rawBody: true,
});

app.enableCors({
  origin: corsOrigins,
  methods: ["GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS"],
  allowedHeaders: [
    "Content-Type",
    "Authorization",
    "Accept",
    "sentry-trace",
    "baggage",
  ],
  credentials: true,
});

app.useGlobalPipes(
  new ValidationPipe({
    whitelist: true,
    forbidNonWhitelisted: true,
  }),
);

const port = process.env.PORT || 3001;

await app.listen(port);
```

### Application creation

The service starts by calling `NestFactory.create(AppModule, { rawBody: true })`. That makes `AppModule` the root of the application graph and defines the full set of controllers, providers, and imported modules available at runtime.

The raw body option preserves the unparsed request body for webhook handlers that need to verify HMAC signatures. Bootstrap also applies global validation, registers Swagger documentation at `/api/docs`, and configures Sentry and PostHog integrations.

### CORS configuration

CORS origins are read from the comma-separated `CORS_ORIGINS` environment variable. When the variable is not set, the service allows `http://localhost:3000`, `http://localhost:5173`, and `http://localhost:5174`.

The configuration allows `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, and `OPTIONS` requests. It also allows the `Content-Type`, `Authorization`, `Accept`, `sentry-trace`, and `baggage` headers, with `credentials: true` enabled for credentialed cross-origin requests.

### Port binding

The service reads its listening port from the `PORT` environment variable and defaults to `3001` when the variable is not set. Deployment environments can set `PORT` to match the port exposed or routed by the runtime, so the environment variable reconciles local and containerized execution.

### Current module graph

The module graph includes shared infrastructure and feature modules for the Gravity platform:

- `ConfigModule` loads `.env` and exposes configuration globally
- `SupabaseModule` provides Supabase and Postgres integration
- `AuthModule` handles authentication, sessions, JWT verification, and user-type guards
- `ChatModule` provides chat capabilities
- `AgentsModule` and `MarketplaceModule` manage agents and marketplace workflows
- `ActivePiecesModule` integrates ActivePieces workflows
- `PaymentsModule`, `CreditsModule`, `PayoutsModule`, `SubscriptionsModule`, and `ChargesModule` provide billing functionality
- `EarningsModule` and `AdminBillingModule` support earnings and administrative billing operations
- `ReferralsModule`, `BountiesModule`, `CandidatesModule`, and `RequestedAgentsModule` support platform-specific workflows
- `LeaderboardModule` provides leaderboard functionality
- `TelemetryModule` and `NotificationsModule` provide observability and notification capabilities
- `HealthModule` exposes service health checks

Each feature module can define its own controllers, providers, repositories, DTOs, guards, and supporting services. The application root composes these modules into the runtime graph while shared configuration remains available through the global `ConfigModule`.

## Health endpoint

The only implemented endpoint is `GET /health`. It returns a plain inline object and does not use a DTO, schema, or health-check integration package.

<CodeGroup tabs="health.controller.ts,Response example">

```ts
@Controller("health")
export class HealthController {
  @Get()
  getHealth() {
    return { status: "ok", service: "api" };
  }
}
```

```json
{
  "status": "ok",
  "service": "api"
}
```

</CodeGroup>

### Route behavior

The route path is `/health` because the controller is decorated with `@Controller("health")` and there is no global prefix configured in `main.ts`. The method is `GET`, and the handler returns a literal object directly from the controller method.

Because there is no API versioning or prefix configuration in the bootstrap file, clients call the endpoint at `/health`, not `/api/health` or `/v1/health`.

### Response shape

The response is a small JSON object with two fields.

<ResponseField name="status" field-type="string" required="true">
Returns `ok` in the current implementation.
</ResponseField>

<ResponseField name="service" field-type="string" required="true">
Returns `api` in the current implementation.
</ResponseField>

### What the endpoint does not include

The health endpoint is intentionally bare. It does not check downstream dependencies, validate output through a schema, or map through a response DTO.

There is also no health library integration in the inspected files. The endpoint reports service availability by returning a static object from the controller.

## Runtime and build

Local development and runtime execution are defined in `apps/api/package.json`, while Nest and TypeScript build behavior is split across `nest-cli.json`, `tsconfig.json`, and `tsconfig.build.json`. The setup is workable as a foundation, but several paths and module settings do not line up cleanly.

<CodeGroup tabs="package.json scripts,package metadata">

```json
{
  "scripts": {
    "dev": "bun --watch src/main.ts",
    "build": "tsc -p tsconfig.build.json",
    "start": "bun dist/main.js",
    "start:prod": "bun ."
  }
}
```

```json
{
  "main": "dist/src/main",
  "type": "commonjs"
}
```

</CodeGroup>

### Runtime scripts

The service defines four runtime and build scripts:

- **`dev`**: runs `bun --watch src/main.ts`
- **`build`**: runs `tsc -p tsconfig.build.json`
- **`start`**: runs `bun dist/main.js`
- **`start:prod`**: runs `bun .`

The `dev` command runs the TypeScript entrypoint directly in Bun watch mode. The `build` command compiles with TypeScript rather than `nest build`.

### Likely dist path mismatch

The package metadata and runtime scripts point to different built entrypoints. `package.json` declares `main` as `dist/src/main`, while the `start` script runs `dist/main.js`.

<Callout kind="alert">

The compiled output path is likely inconsistent with the `start` script. With `rootDir` set to `./` and the source entrypoint at `src/main.ts`, emitted files likely land under `dist/src/`, which makes `bun dist/main.js` a probable mismatch.

</Callout>

## Docker and runtime packaging

The Dockerfile builds the service in one Bun-based stage and runs it in a second Bun-based stage. It copies the built `dist/` directory into the runtime image and starts the service with the production script.

<CodeGroup tabs="Dockerfile build stage,Dockerfile runtime stage">

```dockerfile
FROM oven/bun:1-alpine AS build
WORKDIR /app
COPY package.json bun.lock ./
RUN bun install --frozen-lockfile
COPY . .
RUN bun run build
```

```dockerfile
FROM oven/bun:1-alpine
WORKDIR /app
COPY package.json bun.lock ./
RUN bun install --frozen-lockfile --production
COPY --from=build /app/dist ./dist
EXPOSE 3000
CMD ["bun", "run", "start:prod"]
```

</CodeGroup>

### Build flow inside the image

The build stage installs dependencies from `package.json` and `bun.lock`, copies the application files, and runs `bun run build`. The runtime stage installs production dependencies only, copies `dist/` from the build stage, and starts the container with `bun run start:prod`.

That keeps the final image smaller than a single-stage build and matches the Bun-based local runtime approach used in the package scripts.

### Runtime behavior in the container

The runtime image exposes port `3000` and starts the service with `bun run start:prod`. That command resolves to `bun .`, so the container depends on package metadata to find the entrypoint rather than using an explicit file path.

This is one more place where the current packaging is functional but indirect. Between the `main` value, the `start` script path, and the environment-driven port in `main.ts`, the implementation has multiple runtime assumptions that should remain aligned across local and deployed environments.

## CI integration

The API workflow in `.github/workflows/api.yml` already covers build, versioning, image publishing, release creation, and a placeholder deploy job. It is more complete than the service implementation itself, but several parts are still scaffolding.

### Trigger and build behavior

The workflow runs on pushes to `main` and `dev` for changes under selected paths, and on pull requests targeting those branches. The build section installs dependencies with `pnpm install --frozen-lockfile` and builds the API with `pnpm --filter @repo/api build`.

The workflow path filters include `apps/api/**`, `packages/**`, `pnpm-lock.yaml`, `tsconfig.base.json`, and the workflow file itself. The inspected tree does not show a `packages/` directory, so that filter currently looks anticipatory or stale.

<CodeGroup tabs="Workflow trigger,Build step">

```yaml
on:
  push:
    branches: [main, dev]
    paths:
      - "apps/api/**"
      - "packages/**"
      - "pnpm-lock.yaml"
      - "tsconfig.base.json"
      - ".github/workflows/api.yml"
  pull_request:
    branches: [main, dev]
```

```yaml
- name: Install dependencies
  run: pnpm install --frozen-lockfile

- name: Build
  run: pnpm --filter @repo/api build
```

</CodeGroup>

### Versioning and tagging

The workflow reads the base version from `apps/api/VERSION`, which currently contains `0.1.0`. On `main`, it bumps major, minor, or patch based on commit message rules. On `dev`, it creates a prerelease version in the form `base-dev.timestamp.shortsha`.

It then tags releases as `api-v<version>`. On `main`, the workflow also writes the bumped version back to `apps/api/VERSION`, commits it, and pushes the change.

### Docker publishing and releases

The workflow publishes a container image to `ghcr.io/<owner>/gravity-api`. Tags include the exact version, `latest` on `main`, `dev-latest` on `dev`, and a SHA-based tag.

On `main`, the workflow also creates a GitHub Release named `API v<version>`. The release body includes the published image reference.

### Deploy step status

The deploy job exists, but it does not perform a real deployment yet. The inspected workflow only writes a deployment summary, and the actual deploy commands are commented placeholders.

<Callout kind="alert">

The CI pipeline includes release and deployment scaffolding, but deployment is not implemented. The deploy job is placeholder-only in the current workflow.

</Callout>

## Current limitations

The API now includes the core backend foundations required by the Gravity platform:

- DTOs with validation
- authentication with Supabase JWT and Google OAuth
- persistence through Supabase and Postgres
- domain modules and services
- environment-based configuration through `ConfigModule`
- Swagger and OpenAPI documentation at `/api/docs`

The API uses a global validation pipe with whitelist mode. Non-whitelisted properties are rejected, so request DTOs define the fields that controllers accept.

Authentication is handled through Supabase sessions and JWT verification. User-type guards provide authorization boundaries for creators, business users, candidates, and admins.

The implementation provides a feature-module foundation for the platform, including chat, agents, marketplace, billing, subscriptions, credits, payouts, referrals, bounties, candidates, leaderboards, telemetry, notifications, and health checks. The next layer of work should continue aligning the build entrypoint, package metadata, Docker runtime command, and deployment configuration so every execution environment uses the same compiled output and startup assumptions.
