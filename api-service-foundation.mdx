## Overview

The NestJS API is a feature-complete backend with a global `/api` prefix, SupabaseAuthGuard authentication, AdminGuard protection for administrative routes, and a global validation pipeline. The validation pipeline whitelists accepted properties, rejects unknown properties, and transforms incoming values.

Swagger documentation is available at `/api/docs`. The application includes domain modules for authentication, chat, agents, marketplace, apps, automations, builder, bounties, candidates, payments, referrals, leaderboard, telemetry, administration, Composio integrations, webhooks, and related features.

Health endpoints remain outside the `/api` prefix. Clients can check service availability at `/health` and `/`.

## Bootstrap flow

Application bootstrap creates the Nest application, enables CORS for the frontend origin, applies the global `/api` prefix, registers the global `ValidationPipe`, configures Swagger at `/api/docs`, and starts the HTTP server on port `3001`.

### Application creation

The bootstrap process creates the Nest application from the root application module. The root module assembles the domain modules, controllers, providers, guards, persistence integrations, and shared infrastructure available at runtime.

### CORS configuration

CORS is enabled for the frontend origin and allows credentials. Browser clients can make authenticated cross-origin requests from the configured frontend application.

### Global API prefix

The application applies `/api` as the global route prefix. Domain endpoints therefore use paths such as `/api/auth`, `/api/chat`, and `/api/agents`.

Health routes are explicitly available at the root level, so `/health` and `/` do not include the `/api` prefix.

### Validation pipeline

A global `ValidationPipe` validates incoming request data before it reaches route handlers. The configuration:

- **Whitelists properties** by removing fields that are not declared by the request DTO.
- **Forbids unknown properties** by rejecting requests that contain undeclared fields.
- **Transforms values** so validated input can use the expected DTO and parameter types.

### Authentication and authorization

Authenticated routes use `SupabaseAuthGuard` to validate the request identity through Supabase authentication. Administrative routes add `AdminGuard` to restrict access to users with the required administrative privileges.

### Swagger documentation

Swagger is configured at `/api/docs`. The documentation describes the API routes and their request and response contracts for consumers exploring or integrating with the backend.

### Port binding

The API listens on port `3001`. The port remains defined by the current application runtime configuration rather than being read dynamically from an environment variable.

<Callout kind="alert">

The runtime port is not aligned across the implementation. The Nest application listens on `3001`, while the Docker image exposes `3000`. A container built from the current files advertises one port and binds another.

</Callout>

## Module wiring

The root application module assembles the API's domain and infrastructure modules. The module graph now covers authentication, product functionality, payments, integrations, administration, and operational features rather than a single health controller.

### Domain module structure

The API includes modules for:

- **Authentication**: User authentication and authorization flows.
- **Chat and agents**: Conversational features and agent execution.
- **Marketplace**: Marketplace resources and related workflows.
- **Apps, automations, and builder**: Application creation, automation, and builder functionality.
- **Bounties and candidates**: Bounty workflows and candidate management.
- **Payments**: Credits, payouts, and subscriptions.
- **Referrals and leaderboard**: Referral tracking and ranking features.
- **Telemetry**: Application and product usage data.
- **Admin billing**: Administrative billing operations.
- **Composio and webhooks**: External integrations and event delivery.

The root module also wires the authentication guards, DTO validation, persistence services, Swagger metadata, and shared providers required by these domains.

### Authentication and protected routes

Supabase authentication establishes the request identity for protected endpoints. `SupabaseAuthGuard` runs before route handlers that require an authenticated user.

Routes that require administrative access use `AdminGuard` in addition to authentication. This separates user authentication from authorization for administrative operations.

### Persistence and application services

The domain modules include persistence and application logic for their respective features. Controllers no longer represent the entire application behavior: they coordinate validated requests with domain services and data access components.

## Health endpoint

The API exposes root-level health endpoints at `GET /health` and `GET /`. The NestJS health response is a static service-availability object containing the current service name and a timestamp.

### Route behavior

The health routes remain outside the global `/api` prefix. Clients call `/health` or `/` directly rather than `/api/health` or `/api/`.

The NestJS health response reports the API service as available. The AI service health check separately verifies chat availability before reporting its result.

### Response shape

The response contains three fields.

<ResponseField name="status" field-type="string" required="true">
Returns `ok` when the API health endpoint responds successfully.
</ResponseField>

<ResponseField name="service" field-type="string" required="true">
Returns `api` to identify the service.
</ResponseField>

<ResponseField name="timestamp" field-type="string" required="true">
Returns the time at which the health response was generated.
</ResponseField>

The response has the following shape:

```json
{
  "status": "ok",
  "service": "api",
  "timestamp": "2025-01-15T12:34:56.000Z"
}
```

### Health checks and dependencies

The NestJS health endpoint returns a static response and does not perform downstream dependency checks. The AI service health check has separate behavior and checks chat availability before returning its result.

## Runtime and build

Local development and production execution use Bun-based scripts, while the application build uses TypeScript. Nest CLI settings support the project configuration, but the primary build command invokes TypeScript directly.

### Runtime scripts

The service provides scripts for:

- **Development**: Runs the TypeScript entrypoint in Bun watch mode.
- **Build**: Compiles the application with the TypeScript project build configuration.
- **Start**: Runs the compiled application from the distribution directory.
- **Production start**: Starts the application using the package's production entrypoint metadata.

The development command supports automatic restarts while the application is being changed. The build command compiles the API independently of the Nest CLI command.

### Likely dist path mismatch

The package metadata and runtime scripts point to different built entrypoints. The package metadata refers to an entrypoint under the distribution directory's source path, while the direct start script refers to a top-level file in the distribution directory.

<Callout kind="alert">

The compiled output path is likely inconsistent with the direct start script. With the current root directory and source layout, emitted files likely land under a nested source directory, which makes the top-level start path a probable mismatch.

</Callout>

### Nest CLI configuration

Nest CLI configuration defines the source root, entry file, build TypeScript configuration, manual restart behavior, and output cleanup behavior. The package build script uses TypeScript directly, so the CLI configuration does not appear to drive the primary build path.

### TypeScript build setup

The TypeScript configuration enables decorators and metadata emission required by Nest, targets ES2024, writes compiled output to the distribution directory, and uses incremental compilation.

The module settings require attention during runtime troubleshooting. TypeScript emits ES modules while the package metadata declares CommonJS, which creates a potentially inconsistent module model unless the Bun runtime resolves the difference as intended.

### Dependencies present in the API package

The API package includes Nest core and HTTP platform dependencies, reflection metadata, the TypeScript compiler, Nest CLI tooling, Nest schematics, and Node.js type definitions. The application also includes the dependencies required by its authentication, persistence, domain, integration, and documentation modules.

## Docker and runtime packaging

The Docker build uses separate Bun-based build and runtime stages. The build stage installs dependencies and compiles the service. The runtime stage installs production dependencies, copies the compiled distribution directory, exposes the configured container port, and starts the application through the production runtime command.

### Build flow inside the image

The build stage installs dependencies from the lockfile, copies the application source, and runs the API build. The runtime stage installs production dependencies only and copies the compiled output from the build stage.

This keeps development tooling out of the final image and preserves the Bun-based runtime used by local scripts.

### Runtime behavior in the container

The runtime image exposes port `3000` and starts the production command. The production command resolves the application entrypoint through package metadata rather than using an explicit compiled file path.

The container therefore depends on several runtime assumptions: the package main entrypoint, the direct start path, the compiled output layout, and the port configured by the Nest application. These assumptions should be aligned before relying on the image in deployment environments.

## CI integration

The API workflow covers dependency installation, compilation, versioning, container publishing, release creation, and a placeholder deployment job. The workflow is more complete than the deployment implementation, which still requires a real target and deployment command.

### Trigger and build behavior

The workflow runs for pushes to the primary and development branches when API, shared package, lockfile, TypeScript base configuration, or workflow changes are detected. It also runs for pull requests targeting those branches.

The build process installs dependencies with the frozen lockfile option and builds the API package through the workspace package filter. The configured path filters include a shared packages directory that is not present in the inspected tree, so that filter may be anticipatory or stale.

### Versioning and tagging

The workflow reads the base version from the API version file. On the primary branch, it increments the major, minor, or patch component according to commit message rules. On the development branch, it creates a prerelease version containing the base version, a timestamp, and a shortened commit identifier.

Releases use the `api-v` prefix followed by the computed version. The primary branch workflow writes the new version back to the version file, commits it, and pushes the change.

### Docker publishing and releases

The workflow publishes a container image to the GitHub Container Registry under the API image name. Published tags include the exact version, `latest` on the primary branch, `dev-latest` on the development branch, and a commit-based tag.

The primary branch workflow also creates a GitHub Release named with the API version. The release body includes the published image reference.

### Deploy step status

The deploy job exists, but it does not perform a real deployment. The current workflow writes a deployment summary while the actual deployment commands remain placeholders.

<Callout kind="alert">

The CI pipeline includes release and deployment scaffolding, but deployment is not implemented. The deploy job is placeholder-only in the current workflow.

</Callout>

## Current limitations

The API now includes authentication, DTO validation, persistence, domain modules, Swagger documentation, payment workflows, integrations, and administrative authorization. The bootstrap also applies a global `/api` prefix and a global validation pipeline, while root-level health endpoints remain available for service checks.

Two delivery limitations remain:

- CI does not currently run an active test step.
- The deploy job is placeholder-only and does not deploy the published image.

The implementation can build, package, publish, and expose the current backend functionality through CI. The next operational work should align the fixed application port with the Docker port and resolve the likely compiled-entry path mismatch between package metadata and the start script.
