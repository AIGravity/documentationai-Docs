## Overview

AIGravity/core now defines validation models across both services. The NestJS API uses class-validator DTOs with a global ValidationPipe, while the FastAPI service uses Pydantic models to validate requests and responses across many routes.

The repository also contains named model-like definitions such as `SignUpDto`, `LoginDto`, `CompleteProfileDto`, `PublishAgentDto`, `CreateAutomationDto`, `CreateBountyDto`, `ChatRequest`, `InteractionResponse`, `ReviewWorkflowRequest`, and `ReviewWorkflowResponse`. These models define API contracts and validation behavior, but they are not necessarily persisted entities or database schemas.

<Callout kind="info">

This reference inventories the model and validation definitions present in the checked-in repository today. It distinguishes API contract models from persistence schemas and migration infrastructure.

</Callout>

<Callout kind="danger">

DTOs and Pydantic models define API contracts and validation rules. They should not be interpreted as database tables, persisted entities, or migration-managed schemas unless a separate persistence definition establishes that mapping.

</Callout>

## Persistence and migration status

The services interact with data stores, including Supabase for authentication and related application data. The analyzed controllers do not identify a traditional ORM schema based on Prisma, TypeORM, Drizzle, Mongoose, SQLAlchemy, Sequelize, or Knex.

Migration infrastructure is also not identifiable at the application layer. No application-level migration directories, ORM-managed migration history, or SQL migration files were identified in the analyzed controllers. The repository may rely on Supabase's built-in schema management rather than migrations managed by the application services.

### Repository-level signals

- The NestJS API exposes controllers for authentication, agents, marketplace operations, bounties, payments, and other application capabilities.
- NestJS endpoints use named DTOs and class-validator decorators for request validation.
- A global ValidationPipe is configured with `whitelist`, `forbidNonWhitelisted`, and `transform`.
- The FastAPI service exposes endpoints for chat, guardrails, verification, agent review, embeddings, and requested agents in addition to health.
- FastAPI routes use Pydantic request and response models.
- Supabase is used by the API for authentication and data-store interactions.
- No traditional application-level ORM schema or migration history was identified in the analyzed controllers.

## Validation schema and DTO status

Both services now implement named validation layers for API contracts. NestJS uses DTO classes with decorator-based validation, while FastAPI uses Pydantic `BaseModel` classes and route annotations.

### NestJS API

- DTO classes are defined for authentication, profiles, agents, automations, bounties, payments, and related operations.
- Named DTOs include `SignUpDto`, `LoginDto`, `CompleteProfileDto`, `PublishAgentDto`, `CreateAutomationDto`, and `CreateBountyDto`.
- `class-validator` decorators define field-level validation rules.
- A global `ValidationPipe` is configured with `whitelist`, `forbidNonWhitelisted`, and `transform`.
- Request body validation is applied through DTO annotations.

### FastAPI service

- Pydantic `BaseModel` classes are defined for request and response contracts.
- Named models include `ChatRequest`, `InteractionResponse`, `ReviewWorkflowRequest`, and `ReviewWorkflowResponse`.
- Request model annotations are present on route handlers.
- Response model annotations are present on route handlers.
- Pydantic validates typed fields and rejects payloads that do not satisfy the declared model contracts.

<Callout kind="success">

Both services now have implemented validation layers. NestJS centralizes request validation through DTOs and a global ValidationPipe, while FastAPI uses Pydantic models for route request and response contracts.

</Callout>

## Gaps and implications

The current codebase defines substantial API contracts, but several areas remain separate from the DTO and validation layers.

- **No explicit application ORM schema**: The analyzed controllers do not identify traditional ORM entities or table mappings.
- **No application-level migration history**: The repository does not expose a conventional migration workflow in the analyzed controllers.
- **No shared cross-service contract package**: NestJS DTOs and FastAPI Pydantic models are defined within their respective services rather than clearly published as a shared schema layer.
- **Mixed response modeling**: Some health responses remain inline shapes while many request and response contracts use named models.
- **Persistence boundary remains external**: Supabase and other data-store interactions are not represented as a unified application-level model catalog.

<Callout kind="info">

Treat DTOs and Pydantic models as API validation contracts. Treat persistence mappings and schema history as separate concerns unless the repository provides an explicit entity, table, or migration definition.

</Callout>
