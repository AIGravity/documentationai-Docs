## Overview

The frontend is now a full Remix application with product-specific routes for the builder dashboard, agent customization, publishing, leaderboard, bounties, admin review, settings, and public landing pages. It includes an auth context that supports both user and builder account types, an API client for backend integration, and a builder sidebar that remains visible on builder routes even when you are signed out.

## App purpose and current scope

The frontend now serves as the primary application surface for both users and builders. It supports two account types, with builder-specific flows for agent creation, publishing, review submission, and dashboard management, while keeping public discovery pages available without authentication.

The auth modal can open on either the user or builder side depending on context. API integration now drives agent publishing, leaderboard data, bounty listings, and AI-powered content generation used during agent customization.

## Route map

The route surface now spans public discovery pages, builder workflows, account management, and admin review tooling.

### Public routes

- **`/`** — Landing page
- **`/leaderboard`** — Competition leaderboard with ranked workflows, quality-based scoring, locked, live, and ended states, and a countdown timer
- **`/how-it-works`** — Static explainer page for the builder competition
- **`/its-real`** — Static trust page covering prizes and payouts
- **`/bounties`** — Bounties listing with difficulty filters for All, Easy, Medium, and Difficult, plus shuffled bounty cards
- **`/bounties/:bountyId`** — Bounty detail page with difficulty indicator and submission count

### Builder routes

Builder routes support agent management and publishing flows. The builder sidebar remains visible on these routes even when the current visitor is signed out.

- **`/builder-dashboard`** — Builder dashboard with published agents and an empty state
- **`/customize-agent`** — Agent customization page with AI-powered category autofill, AI-assisted content improvement, and AI edit tracking
- **`/publish-agent`** — Agent publishing flow
- **`/requested-agents`** — Requested agents listing

### User and auth routes

Authentication is modal-driven rather than isolated to a single sign-in page. The modal supports an `initialAccountType` input so the UI opens on the user or builder side that matches the current flow.

- **Auth modal** — Opens in user or builder mode based on context
- **Settings** — Account management with side-aware post-logout redirect behavior

### Admin routes

Admin review pages now expose review state directly in the frontend rather than relying on placeholder screens.

- **Admin pending review detail** — Shows review details with quality scores formatted to 2 decimal places
- **Admin pending review cards** — Displays review queue cards with score output

A previous experimental `/leaderboard2` route is no longer part of the app. Its design work has been merged into the main `/leaderboard` experience.

## Root layout

`apps/web/app/root.tsx` still defines the application document shell, imports global CSS, registers font-related links, and renders the route outlet. The root now also provides auth state to the rest of the app so routes can react to the current session and account type.

### Global style import and linked assets

The root file imports the shared stylesheet directly and exposes font-related link tags through Remix `links()`.

<CodeGroup tabs="Style import,Links function">

```tsx
import "./app.css";
```

```tsx
export const links: LinksFunction = () => [
  { rel: "preconnect", href: "https://fonts.googleapis.com" },
  {
    rel: "preconnect",
    href: "https://fonts.gstatic.com",
    crossOrigin: "anonymous",
  },
  {
    rel: "stylesheet",
    href: "https://fonts.googleapis.com/css2?family=Inter:ital,opsz,wght@0,14..32,100..900;1,14..32,100..900&display=swap",
  },
];
```

</CodeGroup>

This is the only font configuration currently present. The shell preconnects to Google Fonts and loads Inter for the global sans stack.

### Document structure and auth providers

The `Layout` export still defines the outer document and includes the standard Remix primitives used by the app shell. The `App` export now wraps the route tree in auth-aware providers before rendering the outlet.

<CodeGroup tabs="Layout,App shell">

```tsx
export function Layout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en">
      <head>
        <meta charSet="utf-8" />
        <meta name="viewport" content="width=device-width, initial-scale=1" />
        <Meta />
        <Links />
      </head>
      <body>
        {children}
        <ScrollRestoration />
        <Scripts />
      </body>
    </html>
  );
}
```

```tsx
export default function App() {
  return (
    <AuthProvider>
      <Outlet />
    </AuthProvider>
  );
}
```

</CodeGroup>

A few points matter here:

- `Meta` renders route-level metadata such as the title and description exported by route modules.
- `Links` injects the stylesheet and font links registered through Remix.
- The auth provider manages authentication state for both user and builder flows.
- The auth context exposes `openAuthModal`, including support for an optional account type input when a route needs to open the modal on a specific side.
- The auth context also tracks the active account type so session-expired and post-logout flows can redirect to the correct side of the app.
- Builder routes render shared chrome, including the builder sidebar, above route content rather than leaving every route fully unframed.
- `ScrollRestoration` and `Scripts` are included at the document level, which is the expected baseline for Remix apps.

## Error handling

The root file also defines the current error boundary. It distinguishes route error responses from runtime errors and exposes more detail during development.

### Error boundary logic

The implementation starts with fallback values, then refines the message based on the error type.

<CodeGroup tabs="Boundary logic,Fallback UI">

```tsx
export function ErrorBoundary() {
  const error = useRouteError();
  let message = "Oops!";
  let details = "An unexpected error occurred.";
  let stack: string | undefined;

  if (isRouteErrorResponse(error)) {
    message = error.status === 404 ? "404" : "Error";
    details =
      error.status === 404
        ? "The requested page could not be found."
        : error.statusText || details;
  } else if (import.meta.env.DEV && error && error instanceof Error) {
    details = error.message;
    stack = error.stack;
  }
```

```tsx
  return (
    <main className="pt-16 p-4 container mx-auto">
      <h1>{message}</h1>
      <p>{details}</p>
      {stack && (
        <pre className="w-full p-4 overflow-x-auto">
          <code>{stack}</code>
        </pre>
      )}
    </main>
  );
}
```

</CodeGroup>

### Current behavior

The boundary currently behaves as follows:

- **404 route errors** render `404` with the message `The requested page could not be found.`
- **Other route error responses** render `Error` and use `error.statusText` when present
- **Development runtime errors** render the thrown error message and stack trace
- **Fallback cases** render `Oops!` and `An unexpected error occurred.`

This is a practical starter boundary. It is useful for local development, but it does not yet include branded error pages, structured logging, or recovery flows.

## Styling pipeline

The styling stack is intentionally small. Global styles live in `app.css`, and Vite is configured with only the plugins required for Tailwind, Remix, and TypeScript path resolution.

### Global CSS in `app.css`

The stylesheet imports Tailwind, defines the sans font theme variable, and sets the document background for light and dark mode.

<CodeGroup tabs="app.css">

```css
@import "tailwindcss";

@theme {
    --font-sans:
        "Inter", ui-sans-serif, system-ui, sans-serif, "Apple Color Emoji",
        "Segoe UI Emoji", "Segoe UI Symbol", "Noto Color Emoji";
}

html,
body {
    background-color: var(--color-white);

    @media (prefers-color-scheme: dark) {
        background-color: var(--color-gray-950);
        color-scheme: dark;
    }
}
```

</CodeGroup>

From this file alone, the shell currently guarantees:

- Tailwind CSS is loaded globally
- Inter is first in the sans font stack
- `html` and `body` default to a white background
- dark mode switches the background to `var(--color-gray-950)` and enables `color-scheme: dark`

The stylesheet has also expanded beyond the initial shell baseline. Current product styling includes custom presentation for leaderboard medals, incentive cards, bounty difficulty indicators, and locked leaderboard states.

### Vite and Remix configuration

The build configuration is defined in `apps/web/vite.config.ts`.

<CodeGroup tabs="vite.config.ts">

```ts
import { vitePlugin as remix } from "@remix-run/dev";
import tailwindcss from "@tailwindcss/vite";
import { defineConfig } from "vite";
import tsconfigPaths from "vite-tsconfig-paths";

export default defineConfig({
  plugins: [tailwindcss(), remix(), tsconfigPaths()],
});
```

</CodeGroup>

No additional server settings, proxy behavior, environment-specific overrides, or custom build options are configured here. The shell uses the default behavior provided by these plugins.

## Product UI overview

The starter welcome screen has been replaced by product pages that support public discovery, builder workflows, and admin review.

### Builder dashboard

The builder dashboard shows published agents and provides a true empty state instead of a generic placeholder. When no agents are published yet, the empty state narrows the next action to a single `How it works` call to action.

The builder sidebar remains visible even when the current visitor is signed out. In that state, the sidebar presents a sign-in action that opens the auth modal directly on the builder side rather than sending the visitor through a generic user flow.

### Customize-agent page

The customize-agent page now supports AI-powered category autofill. The app can analyze workflow context and prefill marketplace categories so builders do not need to classify every agent manually from scratch.

The `Improve with AI` flow can generate or polish the agent name, description, and problem statement. When AI-generated content appears in the form, the page also shows a hint so builders can distinguish generated text from manual edits.

The page tracks manual edits against the AI baseline for analytics. That tracking makes it possible to measure where builders accept, reject, or revise generated suggestions.

### Leaderboard

The leaderboard ranks published workflows by quality score and formats those scores to 2 decimal places. It now represents the competition lifecycle directly in the UI instead of acting as a static ranking screen.

The board supports three distinct phases:

- **Locked** — Before the competition opens, the board stays visible but locked
- **Live** — During the competition, rankings update and the countdown timer remains active
- **Ended** — After the competition ends, the board serves frozen final standings

The top of the page also highlights the top 5 positions with podium treatment and prize information. Once the competition has ended, the leaderboard remains available as a final record rather than resetting to a new live state.

### Bounties

The bounties page lists available opportunities with a difficulty filter for All, Easy, Medium, and Difficult. Cards are shuffled so the listing does not always privilege the same items by position.

Each bounty card displays difficulty using color-coded indicators:

- **Green** — Easy
- **Yellow** — Medium
- **Red** — Difficult

Bounty detail pages now emphasize difficulty and submission count instead of reward amount. That shift makes the page better aligned with competition participation and review activity.

### Admin review surfaces

Admin review UI now includes both queue cards and detail views. Score displays are formatted consistently, with quality scores shown to 2 decimal places in both summary and review-detail contexts.

### Tool name display

The product UI now preserves brand-specific capitalization for services that were previously rendered with incorrect title casing. Corrected examples include SerpAPI, VLM Run, LinkupAPI, Fireflies.ai, TickTick, and PostHog.

These commands map directly to the current shell lifecycle:

- `npm run dev` starts the Remix Vite development server
- `npm run build` creates the production build
- `npm run start` serves the built app from `./build/server/index.js`
- `npm run typecheck` runs TypeScript without a separate lint or test command in this package

Other relevant package facts currently visible in `package.json`:

- package name is `@repo/web`
- module type is `module`

## Container packaging

The frontend can also be built and run as a container. The Dockerfile uses a two-stage Node 20 Alpine build and serves the production Remix bundle on port `3000`.

### Docker build and runtime flow

<CodeGroup tabs="Dockerfile,Version file">

```dockerfile
FROM node:20-alpine AS build
WORKDIR /app
COPY package.json ./
RUN npm install --include=dev
COPY . .
# tsconfig.json extends ../../tsconfig.base.json — place it at the expected path
COPY tsconfig.base.json /tsconfig.base.json
RUN npm run build

FROM node:20-alpine
WORKDIR /app
COPY package.json ./
RUN npm install --omit=dev
COPY --from=build /app/build ./build
EXPOSE 3000
CMD ["npm", "run", "start"]
```

```text
0.1.0
```

</CodeGroup>

A few implementation details matter:

- the build stage installs development dependencies and runs `npm run build`
- the runtime stage installs production dependencies only
- the built `./build` output is copied into the final image
- the container exposes port `3000`
- the startup command is `npm run start`, which resolves to `remix-serve ./build/server/index.js`
- `apps/web/VERSION` is currently `0.1.0`
