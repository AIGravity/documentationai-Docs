## API overview

The NestJS API uses bearer-token authentication for protected routes. The public marketplace workflow-detail route, the OAuth callback, and the health probe are exceptions to the general authentication rule.

<Callout kind="info">

Send protected requests with an `Authorization` header using the `Bearer` scheme. Do not treat one public route as evidence that the entire API is unauthenticated.

</Callout>

### Endpoint families

- **Marketplace:** Start marketplace runs, retrieve public workflow details, and poll run status through `POST /api/marketplace/run-result`.
- **Credits:** Create custom credit orders and verify provider orders. Verification accepts `providerOrderId` and `razorpayOrderId`; when both are present, `razorpayOrderId` takes precedence.
- **Payouts:** Create payouts as an administrator, look up FX rates, synchronize payout data, and refresh payout state.
- **Subscriptions:** Manage plans, the current subscription, entitlements, history, checkout, cancellation, and plan activation.
- **OAuth:** Handle the OAuth callback without bearer-token authentication.
- **Health:** Check local API availability with `GET /health`.

A marketplace run can return a successful `running` result rather than a completed result. Poll `POST /api/marketplace/run-result` until the run reaches its terminal state.

Workflow validation and import failures can return `422 Unprocessable Entity`. Subscription routes return `404 Not Found` when billing is disabled, so clients should treat a missing subscription route as a feature-state response rather than assuming the route was removed.

## Authentication

Protected endpoint families require a bearer token.

<ParamField header="Authorization" param-type="string" required="true">

Use the format `Bearer access-token` for authenticated routes.

</ParamField>

The marketplace workflow-detail route and OAuth callback are public exceptions. The health endpoint is documented separately because it is an operational probe, not a representative authentication example for the rest of the API.

## Common error responses

The API returns sanitized error bodies with a consistent set of fields.

<ResponseField name="statusCode" field-type="integer" required="true">

HTTP status code for the failure.

</ResponseField>

<ResponseField name="error" field-type="string" required="true">

Short HTTP error name, such as `Unprocessable Entity`.

</ResponseField>

<ResponseField name="message" field-type="string" required="true">

Human-readable description of the failure.

</ResponseField>

<ResponseField name="path" field-type="string" required="true">

Request path that produced the error.

</ResponseField>

<ResponseField name="timestamp" field-type="string" required="true">

Timestamp for the error response.

</ResponseField>

<ResponseField name="requestId" field-type="string" required="false">

Request identifier when the server assigns one.

</ResponseField>

For unexpected server failures, the API uses `InternalError` as the error name and `Internal server error` as the message. Subscription failure bodies may include endpoint-specific condition codes only when those codes survive the error filter. Do not assume that every error response contains a code field.

### Workflow validation error

```json
{
  "statusCode": 422,
  "error": "Unprocessable Entity",
  "message": "Workflow validation failed",
  "path": "/api/marketplace/run",
  "timestamp": "2025-02-14T10:30:00.000Z",
  "requestId": "req_7f3c9a21"
}
```

## Credit order examples

Create a custom credit order at `POST /api/credits/orders/custom` with a bearer token.

<CodeGroup tabs="cURL">

```bash
curl -X POST http://localhost:3001/api/credits/orders/custom \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.example" \
  -H "Content-Type: application/json" \
  --data '{
    "amountUsdMinor": 2500,
    "currency": "INR"
  }'
```

</CodeGroup>

When verifying a credit order, send `providerOrderId` when that is the provider identifier available to your client.

<CodeGroup tabs="JSON">

```json
{
  "providerOrderId": "order_N8m4Q2r7Kp1L",
  "razorpayOrderId": "order_Rz9c3Vt6Lm2A"
}
```

</CodeGroup>

If both identifiers are present, the API uses `razorpayOrderId` for verification.

## Marketplace run behavior

A successful marketplace run request can report `running` while processing continues. Poll `POST /api/marketplace/run-result` to retrieve the current result instead of treating the initial response as terminal.

Workflow validation and import failures use HTTP status `422`. Clients should surface the returned `message` and preserve the `requestId` when present so support teams can trace the failed request.

## Subscription behavior

Subscription endpoints cover plans, the current subscription, entitlements, history, checkout, cancellation, and plan activation. When billing is disabled, these routes are hidden behind `404 Not Found`.

Handle the `404` response as a billing-availability condition when calling subscription routes. Do not retry the request as though it were a transient server failure.

## Health endpoint

### GET `/health`

Use this endpoint to verify that the NestJS backend is running and responding.

<ParamField body="method" param-type="string" required="true" show-location="false">

`GET`

</ParamField>

<ParamField body="path" param-type="string" required="true" show-location="false">

`/health`

</ParamField>

### Request details

The endpoint does not accept request-specific inputs beyond a standard `GET` request to the route.

#### Path parameters

<ParamField body="path parameters" param-type="none" required="false" show-location="false">

None. The route is fixed at `GET /health`.

</ParamField>

#### Query parameters

<ParamField body="query parameters" param-type="none" required="false" show-location="false">

None. The handler does not define or consume query string values.

</ParamField>

#### Headers

<ParamField body="custom headers" param-type="none" required="false" show-location="false">

None. No custom request headers are required for the health probe.

</ParamField>

#### Request body

<ParamField body="request body" param-type="none" required="false" show-location="false">

None. `GET /health` does not accept a request body.

</ParamField>

### Example request

<CodeGroup tabs="cURL">

```bash
curl -i http://localhost:3001/health
```

</CodeGroup>

## Health response

A successful request returns a JSON object that identifies the service and reports its status.

<CodeGroup tabs="JSON">

```json
{
  "status": "ok",
  "service": "api"
}
```

</CodeGroup>

### Response fields

<ResponseField name="status" field-type="string" required="true">

Health state returned by the endpoint. The implemented handler returns `ok`.

</ResponseField>

<ResponseField name="service" field-type="string" required="true">

Service identifier returned by the endpoint. The implemented handler returns `api`.

</ResponseField>

### Likely error responses

The health route does not define custom error responses. A `404` response indicates that the requested path or HTTP method does not match the route, such as `GET /api/health` or `POST /health`.

An unexpected runtime or framework failure can return a `500` response using the common sanitized error format.

The application listens on port `3001` in the current local configuration, so the health endpoint is available at `http://localhost:3001/health`.
