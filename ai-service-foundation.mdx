## Overview

The AI service is a FastAPI application that exposes a health check endpoint and a conversational `POST /chat` endpoint for agent search and recommendation. The chat endpoint orchestrates guardrail checks, LLM-based extraction, and a ranking engine that soft-blends vector similarity with platform, agent type, and tool matches. The service uses uv for dependency management and ships a container build path for deployment.

<Callout kind="info">

The service includes a `POST /chat` endpoint that handles conversational agent search, guardrail validation, LLM orchestration, session persistence, and a soft-blend ranking algorithm. See the [AI Service API reference](/api-reference/ai-service) for endpoint details.


</Callout>

## Current scope

The service exposes two HTTP endpoints: `GET /health` for liveness checks and `POST /chat` for conversational agent search. The `/chat` endpoint accepts a user message along with selected tools, orchestrates guardrail validation and LLM-based extraction, and returns ranked agent recommendations. Ranking uses a soft-blend formula that combines vector similarity with platform, agent type, and tool match signals.

Beyond the endpoints, the service includes Python 3.14 tooling, uv-based dependency management, and automation for linting, versioning, tagging, and container publishing.

## Bootstrap in main.py

The application starts directly in `apps/ai-service/main.py`. App creation happens at module import time, and route registration happens inline with a decorator on the FastAPI app instance.

<CodeGroup tabs="main.py,Notes">

```python
from fastapi import FastAPI

app = FastAPI()


@app.get("/health")
def health():
    return {"status": "ok"}
```

```text
Grounded bootstrap details:

- app = FastAPI() is defined at the top level
- /health is registered with @app.get("/health")
- the handler is synchronous: def health()
- /chat is registered with @app.post("/chat") and delegates to a service layer
- middleware enriches Sentry scope for /chat requests
- routes are registered inline — no APIRouter composition is used
```

</CodeGroup>

The startup path is straightforward: app creation and route registration happen inline. The `/chat` route delegates to a service layer that handles guardrail checks, LLM orchestration, session persistence, and agent ranking.

## Health endpoint

The `GET /health` endpoint is a lightweight liveness check that returns a plain JSON object with one field. The service also exposes `POST /chat` for conversational agent search — see the [AI Service API reference](/api-reference/ai-service) for full details.

<CodeGroup tabs="Route,Response">

```python
@app.get("/health")
def health():
    return {"status": "ok"}
```

```json
{
  "status": "ok"
}
```

</CodeGroup>

The endpoint does not define a response model, custom status code, tags, auth requirement, or explicit error handling. It is a basic process liveness check and does not probe downstream dependencies used by the `/chat` endpoint.

## Python environment and dependency management

Python and package management are consistent across local tooling, project metadata, and the lockfile. The service requires Python `>=3.14`, uses uv for dependency resolution, and pins resolved package versions in `uv.lock`.

<CodeGroup tabs="pyproject.toml,uv.lock,.python-version">

```toml
[project]
name = "ai-service"
version = "0.1.0"
requires-python = ">=3.14"
dependencies = [
    "fastapi>=0.135.0",
    "pydantic>=2.12.5",
    "uvicorn>=0.41.0",
]

[dependency-groups]
dev = [
    "ruff>=0.11.0",
    "pytest>=8.0.0",
]
```

```toml
version = 1
revision = 3
requires-python = ">=3.14"

[[package]]
name = "ai-service"
version = "0.1.0"
source = { virtual = "." }
dependencies = [
    { name = "fastapi" },
    { name = "pydantic" },
    { name = "uvicorn" },
]

[[package]]
name = "fastapi"
version = "0.135.0"

[[package]]
name = "pydantic"
version = "2.12.5"

[[package]]
name = "uvicorn"

```

</CodeGroup>

The declared runtime dependencies are FastAPI, Pydantic, and Uvicorn. The dev dependency group adds Ruff and pytest, while the lockfile confirms uv-based locking and resolved versions for FastAPI `0.135.0`, Pydantic `2.12.5`, and Uvicorn `0.41.0`.

The declared runtime dependencies listed here are the base FastAPI stack. The `/chat` endpoint's service layer integrates with external systems at runtime, including LLM providers, search engines, and session storage.

## Run locally

The repository does not include a substantive local guide for this service, so the usable commands are implied by the CI workflow and Docker runtime command. Run these commands from `apps/ai-service`.

<CodeGroup tabs="Install and start,Quality checks">

```bash
uv python install
uv sync
uv run uvicorn main:app --host 0.0.0.0 --port 8001
```

```bash
uv run ruff format --check .
uv run ruff check .
```

</CodeGroup>

If startup succeeds, Uvicorn listens on port `8001`. A successful request to `GET /health` returns `{"status": "ok"}`.

Tests are not part of the active CI path today. The workflow includes a commented-out pytest step, so pytest is declared as a dev dependency but is not currently enforced in automation.

## Docker packaging

The service image uses a multi-stage Docker build based on `python:3.14-slim`. The builder stage installs production dependencies with uv, and the runtime stage copies the virtual environment and application source before starting Uvicorn.

<CodeGroup tabs="Dockerfile">

```dockerfile
FROM python:3.14-slim AS builder
WORKDIR /app
COPY --from=ghcr.io/astral-sh/uv:latest /uv /uvx /bin/
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev

FROM python:3.14-slim
WORKDIR /app
COPY --from=builder /app/.venv /app/.venv
COPY . .
ENV PATH="/app/.venv/bin:$PATH"
EXPOSE 8001
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8001"]
```

</CodeGroup>

A few runtime details are explicit in the Dockerfile. The image exposes port `8001`, prepends `/app/.venv/bin` to `PATH`, and starts the app with `uvicorn main:app --host 0.0.0.0 --port 8001`.

The Dockerfile does not define a non-root user, healthcheck instruction, environment-specific configuration, or deployment-time setup. It packages and runs the service as-is.

## CI workflow

The GitHub workflow runs when changes affect `apps/ai-service/**` or `.github/workflows/ai-service.yml` on pushes and pull requests targeting `main` or `dev`. Its build job works from `apps/ai-service`, installs uv, installs Python, syncs dependencies, and runs Ruff formatting and lint checks.

Publishing happens only on push events. On `main`, the workflow reads `apps/ai-service/VERSION`, bumps the version according to commit message rules, creates a Git tag in the format `ai-service-v<version>`, publishes `ghcr.io/<owner>/gravity-ai-service`, applies the generated version tag and `latest`, and creates a GitHub Release.

On `dev`, the workflow generates a development version using the base version, timestamp, and short SHA. It tags the repository, publishes the same image with the generated version tag and `dev-latest`, and also adds a SHA tag.
