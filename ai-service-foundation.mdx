## Overview

The AI service is a FastAPI application that handles chat, guardrail checks, embeddings, agent indexing, requested agents, workflow verification, and agent review analysis. It uses uv for dependency management and has a container build path for deployment.

<Callout kind="info">

The service integrates with LLM providers for chat and workflow verification, and with embedding providers for agent indexing. Some verification routes fail open when providers are unavailable, returning empty results or safe defaults instead of erroring.

</Callout>

## Current scope

The AI service is a multi-router application that handles chat, verification generation, alignment judgment, embeddings, agent indexing, requested agents, and evidence-based review analysis. Routes are split across core routes, verification routes under `/verification/*`, and review routes under `/agent-review/*`.

The service uses Pydantic models for request validation, integrates with LLM providers for chat and verification, and uses embedding providers for agent indexing. Some verification routes fail open when providers are unavailable, returning empty results or safe defaults rather than blocking the request.

## Bootstrap in main.py

The application starts directly in `apps/ai-service/main.py`. App creation happens at module import time, and the application now assembles multiple `APIRouter` modules for verification and review, in addition to core routes defined directly on the FastAPI app instance.

<CodeGroup tabs="main.py,Notes">

```python
from fastapi import FastAPI

app = FastAPI()

# Core routes (chat, health, guardrail, embed, indexing, requested agents)
# are registered on the app instance or included via routers.

# Verification router
# app.include_router(verification_router, prefix="/verification")

# Agent review router
# app.include_router(review_router, prefix="/agent-review")
```

```text
Bootstrap details:

- app = FastAPI() is defined at the top level
- APIRouter modules are used for /verification and /agent-review prefixes
- Pydantic models validate request bodies across routes
- the service integrates with LLM and embedding providers via environment configuration
- admin routes use x-admin-token header authorization
```

</CodeGroup>

The startup path assembles the application with core routes, verification routes, and review routes. Service classes handle domain-specific logic for each route group.

## Health endpoint

The `GET /health` endpoint is one of many routes in the AI service. It returns a JSON object with the service status, version, and chat availability.

<CodeGroup tabs="Route,Response">

```python
@app.get("/health")
def health():
    return {
        "status": "healthy",
        "service": "ai-service",
        "version": "...",
        "chat_available": True
    }
```

```json
{
  "status": "healthy",
  "service": "ai-service",
  "version": "1.0.0",
  "chat_available": true
}
```

</CodeGroup>

The `chat_available` field indicates whether the chat route can currently reach a configured language model provider.

## Route groups

The AI service exposes three groups of routes:

- **Core routes:** `POST /chat`, `POST /internal/guardrail/check`, `POST /admin/pricing`, `POST /internal/embed`, `POST /internal/agents/index`, `DELETE /internal/agents/{agent_id}`, and requested-agent CRUD routes under `/internal/requested-agents/*`.
- **Verification routes (under `/verification/*`):** warmup, guardrail-health, url-verdict, generate-description, generate-workflow-steps, generate-categories, generate-fillable-fields, check-setup-fields, judge-request-alignment, prewarm, and verify-ap-stream.
- **Review routes (under `/agent-review/*`):** `POST /agent-review/analyze`.

<Callout kind="info">

Verification routes use a fail-open policy: `generate-categories`, `check-setup-fields`, `judge-request-alignment`, and `prewarm` return empty results or safe defaults when the AI provider is unavailable. The chat route returns `503` when no LLM key is configured, embedding routes return `503` for missing keys and `502` for provider failures, `url-verdict` returns `422` for invalid input, and `admin/pricing` returns `403` for invalid tokens.

</Callout>

For full endpoint details, parameters, and response shapes, see the [AI Service API reference](/api-reference/ai-service).

## Python environment and dependency management

Python and package management are consistent across local tooling, project metadata, and the lockfile. The service requires Python `>=3.14`, uses uv for dependency resolution, and pins resolved package versions in `uv.lock`.

<CodeGroup tabs="pyproject.toml,uv.lock,.python-version">

```toml
[project]
name = "ai-service"
version = "0.1.0"
requires-python = ">=3.14"
dependencies = [
    "fastapi>=0.135.0",
    "pydantic>=2.12.5",
    "uvicorn>=0.41.0",
]

[dependency-groups]
dev = [
    "ruff>=0.11.0",
    "pytest>=8.0.0",
]
```

```toml
version = 1
revision = 3
requires-python = ">=3.14"

[[package]]
name = "ai-service"
version = "0.1.0"
source = { virtual = "." }
dependencies = [
    { name = "fastapi" },
    { name = "pydantic" },
    { name = "uvicorn" },
]

[[package]]
name = "fastapi"
version = "0.135.0"

[[package]]
name = "pydantic"
version = "2.12.5"

[[package]]
name = "uvicorn"
version = "0.41.0"
```

```text
3.14
```

</CodeGroup>

The declared runtime dependencies are FastAPI, Pydantic, and Uvicorn. The dev dependency group adds Ruff and pytest, while the lockfile confirms uv-based locking and resolved versions for FastAPI `0.135.0`, Pydantic `2.12.5`, and Uvicorn `0.41.0`.

The service integrates with LLM and embedding providers configured through environment variables. Specific provider SDKs and credentials are managed externally rather than declared in the project dependencies.

## Run locally

The repository does not include a substantive local guide for this service, so the usable commands are implied by the CI workflow and Docker runtime command. Run these commands from `apps/ai-service`.

<CodeGroup tabs="Install and start,Quality checks">

```bash
uv python install
uv sync
uv run uvicorn main:app --host 0.0.0.0 --port 8001
```

```bash
uv run ruff format --check .
uv run ruff check .
```

</CodeGroup>

If startup succeeds, Uvicorn listens on port `8001`. A successful request to `GET /health` returns `{"status": "healthy", "service": "ai-service", "version": "...", "chat_available": true}`.

Tests are not part of the active CI path today. The workflow includes a commented-out pytest step, so pytest is declared as a dev dependency but is not currently enforced in automation.

## Docker packaging

The service image uses a multi-stage Docker build based on `python:3.14-slim`. The builder stage installs production dependencies with uv, and the runtime stage copies the virtual environment and application source before starting Uvicorn.

<CodeGroup tabs="Dockerfile">

```dockerfile
FROM python:3.14-slim AS builder
WORKDIR /app
COPY --from=ghcr.io/astral-sh/uv:latest /uv /uvx /bin/
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev

FROM python:3.14-slim
WORKDIR /app
COPY --from=builder /app/.venv /app/.venv
COPY . .
ENV PATH="/app/.venv/bin:$PATH"
EXPOSE 8001
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8001"]
```

</CodeGroup>

A few runtime details are explicit in the Dockerfile. The image exposes port `8001`, prepends `/app/.venv/bin` to `PATH`, and starts the app with `uvicorn main:app --host 0.0.0.0 --port 8001`.

The Dockerfile does not define a non-root user, healthcheck instruction, environment-specific configuration, or deployment-time setup. It packages and runs the current minimal service as-is.

## CI workflow

The GitHub workflow runs when changes affect `apps/ai-service/**` or `.github/workflows/ai-service.yml` on pushes and pull requests targeting `main` or `dev`. Its build job works from `apps/ai-service`, installs uv, installs Python, syncs dependencies, and runs Ruff formatting and lint checks.

Publishing happens only on push events. On `main`, the workflow reads `apps/ai-service/VERSION`, bumps the version according to commit message rules, creates a Git tag in the format `ai-service-v<version>`, publishes `ghcr.io/<owner>/gravity-ai-service`, applies the generated version tag and `latest`, and creates a GitHub Release.

On `dev`, the workflow generates a development version using the base version, timestamp, and short SHA. It tags the repository, publishes the same image with the generated version tag and `dev-latest`, and also adds a SHA tag.
