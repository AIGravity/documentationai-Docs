## Overview

The repository defines a working data layer across the API and AI services. Database tables are created and evolved with SQL migrations, request validation uses decorated DTO schemas with field-level constraints, and health endpoints still return small inline response shapes.

The current schema work centers on three areas: bounty funding, the agent review lifecycle for publishing, and app connection management. Those structures now provide persisted entities, validation contracts for incoming requests, and migration history for schema changes.

<Callout kind="info">

This reference inventories the data structures that are implemented in the checked-in repository today. It covers persisted tables, request validation schemas, and endpoint-local response shapes.


</Callout>

## Persistence and migration status

The repository uses SQL migrations to define and evolve the database schema. Instead of relying on a generated model layer, schema changes are expressed directly in migrations that add new tables, extend existing tables, and preserve lifecycle state as product features expand.

Recent migration work covers three concrete changes. Migrations create a `bounty_orders` table for payment order tracking, extend the agent review lifecycle with additional statuses and state-carrying columns, and add payment tracking fields to the `bounties` table so funding can be confirmed and timestamped.

## Database tables

### bounty_orders

Tracks payment orders created to fund bounties. Each row represents one funding attempt for a bounty.

| Column | Type | Description |
| --- | --- | --- |
| id | UUID | Primary key |
| bounty_id | UUID | Foreign key to the bounties table |
| user_id | UUID | The bounty creator who initiated the payment |
| razorpay_order_id | string | Gateway order identifier |
| amount | number | Payment amount in minor currency units |
| currency | string | ISO currency code |
| status | string | Order lifecycle state |
| created_at | timestamp | Row creation time |

### pending_agent_reviews

Tracks the review lifecycle for agents submitted for publishing. The table now supports a full lifecycle instead of a single pending-only state.

| Column | Type | Description |
| --- | --- | --- |
| id | UUID | Primary key |
| status | string | One of: checking, pending, approved, rejected |
| published_workflow_id | UUID | Links to the live published agent after approval |
| resume_state | JSON | E2E test run handle for resuming interrupted publish flows |
| checks | JSON | Complete verification gate results for rehydration |
| updated_at | timestamp | Last modification time, used for real-time updates |

### bounties

The bounties table now includes payment-tracking fields for funded work.

| Column | Type | Description |
| --- | --- | --- |
| payment_status | string | One of: unpaid, paid. Existing rows were backfilled as paid. |
| funded_at | timestamp | When the bounty payment was confirmed |

## NestJS API response shape

The NestJS API currently returns one structured object from the health endpoint. This object is an inline response shape, not a named DTO or persisted entity.

### Implemented shape

<CodeGroup tabs="TypeScript">

```ts
@Controller("health")
export class HealthController {
  @Get()
  getHealth() {
    return { status: "ok", service: "api" };
  }
}
```

</CodeGroup>

### Classification

- **Kind** — Inline response shape
- **Named entity or DTO** — None for this endpoint response
- **Persistence-backed** — No
- **Relationships** — None
- **Validation rules** — None on the response object

### Response fields

<ResponseField name="status" field-type="string" required="true">

Health state returned by the endpoint. The implemented handler returns `ok`.


</ResponseField>

<ResponseField name="service" field-type="string" required="true">

Service identifier returned by the endpoint. The implemented handler returns `api`.


</ResponseField>

### Notes

This response shape is defined inline inside the controller method. No DTO class, serializer, or schema definition backs the response.

## Migration status

SQL migrations now manage schema evolution for the repository. They capture both new tables and incremental changes to existing tables so the application can introduce funding workflows and a richer publishing review lifecycle without breaking earlier data.

Recent migrations added the `bounty_orders` table, introduced `payment_status` and `funded_at` on the `bounties` table, and backfilled existing bounty rows as paid. The same migration stream also extended `pending_agent_reviews` with the statuses `checking`, `approved`, and `rejected`, plus `published_workflow_id`, `resume_state`, and `checks` to support resumable verification and publish state.

## Gaps and implications

The data layer continues to evolve as new product features are added. The `bounty_orders` table and the expanded agent review lifecycle are the most recent additions, and they establish the current direction for funding, publishing, and operational state management.
