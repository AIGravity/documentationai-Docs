## Overview

Use the NestJS API on port `3001` to authenticate users, manage apps and connections, run chats and agents, configure automations, access marketplace resources, manage bounties, and process credits, payouts, subscriptions, and provider webhooks.

Swagger is available at `/api/docs`. Controllers define the `/api` prefix themselves, so the API does not apply a separate global prefix.

<Callout kind="info">

The endpoint summaries below provide route groups, authentication requirements, and common status codes. Use the OpenAPI specification at `/api/docs` for complete request parameters, schemas, and response definitions.

</Callout>

## Authentication

Most protected routes require a Supabase access token in the `Authorization` header. The `SupabaseAuthGuard` validates the bearer JWT before the controller handles the request.

<CodeGroup tabs="cURL,JavaScript">

```bash
curl -i http://localhost:3001/api/apps \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.example"
```

```javascript
const response = await fetch("http://localhost:3001/api/apps", {
  headers: {
    Authorization: "Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.example"
  }
});

const apps = await response.json();
console.log(apps);
```

</CodeGroup>

`@Public()` bypasses the Supabase authentication guard for routes that must be reachable without a user JWT. Public routes can still apply their own authentication, such as webhook signature verification.

<Callout kind="info">

Routes protected by `AdminGuard` require both a valid Supabase JWT and the `admin` role. A missing or invalid token returns `401 Unauthorized`; an authenticated user without the required role returns `403 Forbidden`.

</Callout>

### Authentication parameters

<ParamField header="Authorization" param-type="string" required="true">

Bearer JWT for routes protected by `SupabaseAuthGuard`. Use the format `Bearer token`.

</ParamField>

<ParamField body="role" param-type="string" required="false" show-location="false">

The authenticated user's role is read from the validated identity for routes protected by `AdminGuard`. The required administrator role is `admin`.

</ParamField>

## Error response format

The API uses one normalized error shape for client errors and server errors.

```json
{
  "statusCode": 401,
  "error": "Unauthorized",
  "message": "Invalid or missing bearer token",
  "path": "/api/apps",
  "timestamp": "2026-10-05T12:34:56.789Z"
}
```

<ResponseField name="statusCode" field-type="integer" required="true">

HTTP status code for the error.

</ResponseField>

<ResponseField name="error" field-type="string" required="true">

HTTP error name, such as `Unauthorized`, `Forbidden`, `Bad Request`, or `Internal Server Error`.

</ResponseField>

<ResponseField name="message" field-type="string" required="true">

Human-readable explanation of the failure. Validation failures may contain multiple messages.

</ResponseField>

<ResponseField name="path" field-type="string" required="true">

Request path that produced the error.

</ResponseField>

<ResponseField name="timestamp" field-type="string" required="true">

ISO 8601 timestamp generated when the error is handled.

</ResponseField>

<Callout kind="info">

Validation uses `ValidationPipe` with whitelist, forbidden non-whitelisted fields, and type transformation enabled. Fields that are not declared by the request DTO are rejected, and invalid input commonly returns `400 Bad Request`.

</Callout>

## Health endpoints

Health routes are unauthenticated and return the current status of the NestJS API service. The service listens on port `3001` in the current configuration.

### GET `/`

Use the root route for a minimal liveness check.

<ParamField body="path" param-type="string" required="true" show-location="false">

</ParamField>

<ParamField body="request body" param-type="none" required="false" show-location="false">

</ParamField>

#### Example request

<CodeGroup tabs="cURL,JavaScript">

## Payments endpoints

Payment operations cover credits, payouts, subscriptions, and provider webhooks. The payment controllers use different authentication models depending on whether a request originates from an authenticated application user or an external payment provider.

<Expandable title="View payments endpoint inventory">

| Method | Path | Auth | Description | Status codes |
|---|---|---|---|---|
| `GET`, `POST`, `PATCH`, `DELETE` | Payment credits routes | Supabase JWT | Credit balance and credit transaction operations | `200`, `201`, `400`, `401`, `404`, `500` |
| `GET`, `POST`, `PATCH`, `DELETE` | Payment payouts routes | Supabase JWT | Payout account and payout lifecycle operations | `200`, `201`, `400`, `401`, `404`, `500` |
| `GET`, `POST`, `PATCH`, `DELETE` | Payment subscriptions routes | Supabase JWT | Subscription creation and management operations | `200`, `201`, `400`, `401`, `404`, `500` |
| `POST` | Payment webhook routes | Provider signature | External payment provider callbacks | `200`, `400`, `401`, `500` |

</Expandable>

<Callout kind="info">

Payment webhooks are public provider callbacks authenticated with request signatures, not Supabase JWTs. Preserve the raw request data and provider signature handling required by the payment integration when forwarding webhook requests.

</Callout>
