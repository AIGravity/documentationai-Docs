## Overview

The codebase defines data models and persistence across both the NestJS API and the FastAPI AI service. The API uses Supabase and Postgres for identity, catalog, billing, chat, reviews, referrals, and marketplace metadata, with ActivePieces Postgres for flows, runs, and connections. The AI service uses Pydantic models for request and response validation, SQLAlchemy for database access, Redis for session caching, and Typesense for agent search indexing.

## Persistence and migration status

The API service uses Supabase as its primary database, with SQL migrations managed under `apps/api/supabase/migrations/`. Migrations cover identity, agent catalog, marketplace, billing, subscriptions, credits, payouts, referrals, bounties, candidates, chat, reviews, and notifications. ActivePieces uses its own Postgres database for flow metadata, runs, and connections. The AI service connects to Supabase via SQLAlchemy for execution tracking and usage data, uses Redis for session and conversation caching, and indexes agents in Typesense for search.

### Repository-level signals

- The NestJS API exposes domain modules backed by Supabase and Postgres data models.
- The FastAPI service uses Pydantic models for request and response validation.
- ActivePieces maintains a separate Postgres database for workflow data.
- Redis stores session and conversation cache data.
- Typesense indexes agents for search.

## NestJS API response shape

The NestJS API currently returns one structured object from the health endpoint. This object is an inline response shape, not a named DTO or persisted entity.

## Key data models

The platform data model spans identity, agent publishing, marketplace workflows, billing, collaboration, and operational tracking.

- **Identity:** Users, profiles, sessions, and user types including creators, business users, candidates, and admins
- **Agents:** Agent submissions, review submissions, builder reports, and published agents
- **Marketplace:** Workflows, consumer clones, run results, and draft events
- **Billing:** Credit packages, credit orders, credit charges, subscription plans, subscription cycles, payout accounts, and payouts
- **Earnings and referrals:** Creator earnings balances, referral links, and referral earnings
- **Bounties:** Bounty records, submissions, and assignments
- **Chat:** Sessions, messages, and flow state
- **Agent review:** Review findings, evidence scores, and builder feedback
- **ActivePieces:** Flows, runs, connections, and waitpoints

## Validation schema and DTO status

The API uses NestJS DTOs with class-validator decorators, enforced through a global ValidationPipe with whitelist mode. Non-whitelisted properties are rejected, so request DTOs define the exact fields controllers accept. The AI service uses Pydantic models for request and response validation on the `/chat` endpoint, verification routes, agent review routes, and internal APIs.

## Migration status

Supabase SQL migrations are managed under `apps/api/supabase/migrations/`. Recent migrations include builder report edits and feedback, referral earnings, and other schema changes supporting new features. The AI service does not manage its own migrations but writes execution and usage data to the shared Supabase database.

## Gaps and implications

The data model covers identity, marketplace, billing, chat, agent review, and operational data. DTOs and Pydantic models provide validation contracts at the API boundary. The main consideration for contributors is that schema changes require Supabase migrations, and the ActivePieces database is managed separately from the platform database.
