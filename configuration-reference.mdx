## Overview

The codebase uses environment-driven configuration across all three services. Each service, API, AI service, and web, has its own `.env.example` file documenting required and optional variables. The API uses NestJS ConfigModule with `isGlobal: true` to load `.env` at runtime. The AI service reads environment variables via Python's `os.getenv`. The web app uses Vite's `import.meta.env` for browser-exposed variables.

Use this page to answer three practical questions:

- Which settings affect local runtime, builds, and deployment
- Where each setting is defined
- Which environment variables each service requires or supports

## Configuration surface summary

Configuration is spread across several concrete surfaces:

- **`.env` files per service** define runtime configuration. The API loads variables through NestJS ConfigModule, the AI service reads them with `os.getenv`, and the web app reads browser-exposed variables through Vite's `import.meta.env`.
- **Static config files** define TypeScript, workspace, Turbo, Nest, and Python tool settings.
- **Dockerfiles** define container base images, exposed ports, commands, and runtime environment defaults.
- **GitHub Actions workflows** define service names, image names, branch filters, concurrency behavior, setup versions, and release gating logic.

## Environment variables

Each service provides a `.env.example` file. Copy the relevant file to `.env` for local development, then replace example values with credentials and service URLs for your environment.

### API service

The API loads `.env` through NestJS ConfigModule with `isGlobal: true`. These variables control HTTP behavior, integrations, payments, notifications, analytics, and AI-backed features.

| Variable | Purpose | Required |
| --- | --- | --- |
| `CORS_ORIGINS` | Comma-separated allowed CORS origins. | No. Defaults to `localhost:3000`, `localhost:5173`, and `localhost:5174`. |
| `PORT` | HTTP listening port. | No. Defaults to `3001`. |
| `FRONTEND_URL` | Public web app URL for OAuth callbacks. | No. Defaults to `localhost:5173`. |
| `AI_SERVICE_URL` | Base URL for the AI service. | Yes for AI-backed features. |
| `SUPABASE_URL` | Supabase project URL. | Yes for normal operation. |
| `SUPABASE_ANON_KEY` | Supabase anonymous or public key. | Yes for normal operation. |
| `SUPABASE_SERVICE_ROLE_KEY` | Server-side Supabase key for privileged operations. | Yes for privileged functionality. |
| `ACTIVEPIECES_INSTANCE_URL` | Self-hosted ActivePieces instance URL. | Yes for ActivePieces integration. |
| `AP_JWT_SECRET` | Shared HS256 secret for ActivePieces user JWTs. | Yes for user provisioning. |
| `AP_POSTGRES_HOST` | ActivePieces PostgreSQL host. | Yes for ActivePieces PostgreSQL integration. |
| `SENTRY_DSN` | Sentry DSN. | No. |
| `POSTHOG_API_KEY` | PostHog server-side key. | No. |
| `POSTHOG_ENVIRONMENT` | Enables PostHog only when set to production. | No. |
| `RAZORPAY_KEY_ID` / `RAZORPAY_KEY_SECRET` | Razorpay payment credentials. | Required for Razorpay payments. |
| `STRIPE_SECRET_KEY` | Stripe server-side API key. | Conditional. Stripe is disabled when absent. |
| `PAYPAL_CLIENT_ID` / `PAYPAL_CLIENT_SECRET` | PayPal REST credentials. | Conditional for PayPal payouts. |
| `OPENROUTER_API_KEY` | LLM API key for chat and recommendations. | Yes unless `OPENAI_API_KEY` is supplied. |
| `SMTP_HOST` / `SMTP_USER` / `SMTP_PASS` | Email notification credentials. | Required when email notifications are enabled. |
| `NOTIFICATIONS_ENABLED` | Global notification sender switch. | No. Defaults to `true`. |
| `GRAVITY_CHECKPOINT_INJECTION` | Enables or disables checkpoint injection. | No. Defaults to off. |

| `BEDROCK_GUARDRAIL_ID` | AWS Bedrock guardrail ID. | Required for guardrail operation. |
| `AWS_REGION` | AWS region. | Required for Bedrock. |
| `TYPESENSE_API_KEY` / `TYPESENSE_HOST` | Typesense search credentials. | Required for agent search. |
| `GEMINI_API_KEY` | Gemini API key for embeddings. | Required for embedding features. |
| `SENTRY_DSN` | Sentry DSN. | No. |
| `POSTHOG_API_KEY` / `POSTHOG_ENVIRONMENT` | PostHog analytics configuration. | No. |

### Web app

The web app reads browser-exposed variables through Vite's `import.meta.env`. Variables intended for browser access use the `VITE_` prefix.

| Variable | Purpose | Required |
| --- | --- | --- |
| `VITE_SUPABASE_URL` | Supabase URL exposed to the browser. | Yes for authentication. |
| `VITE_SUPABASE_ANON_KEY` | Supabase public key exposed to the browser. | Yes for authentication. |
| `VITE_API_URL` | API base URL. | Yes for API-backed functionality. |
| `VITE_APP_ENVIRONMENT` | App environment. Production hides development-only UI. | No. |
| `VITE_SENTRY_DSN` | Browser Sentry DSN. | No. |
| `VITE_POSTHOG_KEY` | Browser PostHog project key. | No. |
| `VITE_CRISP_WEBSITE_ID` | Crisp support widget ID. | No. |
| `VITE_BUGFEED_PROJECT_ID` | Bugfeed feedback widget project ID. | No. |

<Callout kind="info">

Variables with the `VITE_` prefix are bundled into browser code. Non-`VITE_` Sentry and PostHog variables are server or build-time values and should not contain secrets exposed to clients.

</Callout>

## Application runtime settings

Application runtime behavior is configured through service environment variables, with defaults applied when optional variables are absent.

### API service runtime settings

The API reads CORS origins from `CORS_ORIGINS` and the listening port from `PORT`.

<CodeGroup tabs="main.ts,Behavior summary">

```ts
const corsOrigins = configService
  .get<string>("CORS_ORIGINS", "http://localhost:3000,http://localhost:5173,http://localhost:5174")
  .split(",")
  .map((origin) => origin.trim());

app.enableCors({
  origin: corsOrigins,
  methods: ["GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS"],
  allowedHeaders: [
    "Content-Type",
    "Authorization",
    "Accept",
    "sentry-trace",
    "baggage",
  ],
  credentials: true,
});

await app.listen(configService.get<number>("PORT", 3001));
```

```ts
// Effective runtime behavior:
// - CORS origins come from CORS_ORIGINS
// - Defaults include localhost ports 3000, 5173, and 5174
// - GET, POST, PUT, PATCH, DELETE, and OPTIONS are allowed
// - Content-Type, Authorization, Accept, sentry-trace, and baggage are allowed
// - Credentialed requests are enabled
// - PORT defaults to 3001
```

</CodeGroup>

## Notable mismatches

The API Dockerfile exposes port `3000`, while the API application defaults to listening on port `3001`. Set `PORT` during deployment to reconcile the container configuration with the application runtime.

<Callout kind="alert">

The API deployment must use a consistent port value. Either configure `PORT` to match the container's exposed port or update the Dockerfile and deployment configuration to expose the application's default port, `3001`.

</Callout>
