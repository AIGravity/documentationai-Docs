## Overview

The API service is now a full NestJS application in `apps/api` with more than 20 feature modules spanning agent publishing, review workflows, leaderboard, bounties, marketplace, chat, authentication, payments, telemetry, and supporting platform services. It still boots as a single Nest application, but the runtime surface is no longer limited to one controller or one route.

The service uses `ConfigModule` for environment-driven configuration, `SupabaseModule` for PostgreSQL persistence, and guard-based authentication for protected endpoints. JWT-protected routes use `SupabaseAuthGuard`, while public routes remain available without authentication where appropriate.

<Callout kind="info">

The current implementation includes agent, leaderboard, bounties, marketplace, chat, auth, and health endpoints, with JWT-guarded routes across protected controller actions.


</Callout>

## Bootstrap flow

`apps/api/src/main.ts` still creates the Nest application from `AppModule`, enables CORS, and starts the HTTP server on a fixed port. The bootstrap remains small, but it now runs against an application graph that includes global configuration, authentication, persistence, and multiple feature modules.

<CodeGroup tabs="main.ts,Behavior summary">

```ts
const app = await NestFactory.create(AppModule);

app.enableCors({
  origin: ["http://localhost:3000"],
  credentials: true,
});

await app.listen(3001);
```

### Application creation

The service starts by calling `NestFactory.create(AppModule)`. That makes `AppModule` the root of the application graph and defines the full set of controllers, providers, and imported modules available at runtime.

Because the module graph is now broad, bootstrap initializes a full feature-oriented API rather than a single-controller foundation app. The entrypoint is still lean, with no global pipes, interceptors, guards, filters, or prefixes configured directly in `main.ts`.

### Configuration loading

The service now relies on `ConfigModule` for environment-driven configuration. `ConfigModule` is registered globally and loads from `.env`, so feature modules can resolve configuration values without re-importing configuration support in every module.

That moves environment access into the Nest dependency graph instead of leaving runtime configuration entirely hardcoded. CORS and port binding in `main.ts` still remain explicit in the bootstrap file.

### CORS configuration

CORS is enabled with `app.enableCors(...)` and allows exactly one origin: `http://localhost:3000`. The configuration also sets `credentials: true`, so browsers can include credentials on cross-origin requests from that origin.

That setup is enough for local frontend-to-API development, but it is not dynamic. The service does not read allowed origins from environment variables in the inspected bootstrap file.

### Port binding

The service binds to port `3001` with `app.listen(3001)`. There is no `process.env.PORT` handling in the inspected source, so the listening port is fixed in code.

<Callout kind="alert">

The runtime port is not aligned across the implementation. `main.ts` listens on `3001`, while the Dockerfile exposes `3000`. A container built from the current files advertises one port and binds another.


</Callout>

`HealthController` is still registered directly on `AppModule`. That keeps the liveness endpoint available at the root application level while the rest of the API surface is organized into feature modules.

## Health endpoint

`GET /health` remains the simplest endpoint in the service, but it is now one route among many rather than the only implemented API path. It still returns a plain inline object and does not use a DTO, schema, or health-check integration package.

<CodeGroup tabs="health.controller.ts,Response example">

```ts
@Controller("health")
export class HealthController {
  @Get()
  getHealth() {
    return { status: "ok", service: "api" };
  }
}
```

```json
{
  "status": "ok",
  "service": "api"
}
```

</CodeGroup>

### Route behavior

The route path is `/health` because the controller is decorated with `@Controller("health")` and there is no global prefix configured in `main.ts`. The method is `GET`, and the handler returns a literal object directly from the controller method.

Because there is no API versioning or prefix configuration in the bootstrap file, clients call the endpoint at `/health`, not `/api/health` or `/v1/health`.

### Response shape

The response is a small JSON object with two fields.

<ResponseField name="status" field-type="string" required="true">

Returns `ok` in the current implementation.

</ResponseField>

<ResponseField name="service" field-type="string" required="true">

Returns `api` in the current implementation.

</ResponseField>

### What the endpoint does not include

The health endpoint is intentionally bare. It does not check downstream dependencies, validate output through a schema, or map through a response DTO.

There is also no health library integration in the inspected files. The endpoint reports service availability by returning a static object from the controller.

## Authentication and authorization

Protected endpoints use `SupabaseAuthGuard` to validate JWT bearer tokens before controller handlers run. That guard establishes the authenticated request context used by feature modules such as agents, bounties, builder flows, and other user-scoped operations.

Admin-only endpoints add `AdminGuard` on top of JWT authentication. Those routes require both a valid authenticated user and an authorization check that verifies admin access.

### Auth context

The authenticated request context exposes the current user identity to downstream handlers. At minimum, that context includes the authenticated user ID and email, which feature controllers use to scope reads, writes, reviews, and ownership checks.

That keeps user identity resolution in the auth layer instead of repeating token parsing logic inside controller methods. Public routes can skip that guard chain entirely when no authenticated context is required.

### Public and protected surfaces

Not every route requires authentication. Leaderboard endpoints and the health endpoint are public, while protected feature modules require JWT authentication through `SupabaseAuthGuard`.

Admin review workflows are stricter. Those routes require both JWT authentication and admin role verification before allowing review or moderation actions.

## Agent and leaderboard endpoints

The service now exposes a substantial API surface across agent publishing and public leaderboard access. These endpoints sit in dedicated feature modules rather than being attached directly to the root application module.

### Agents controller surface

`AgentsController` exposes 27 endpoints under `/api/agents`. That surface covers publishing flows, review submission, AI-powered previews for categories and descriptions, workflow-step generation, verification streaming, and admin review management.

All agent endpoints require JWT authentication. Admin review endpoints add role-based enforcement, so they require both authenticated access and admin verification.

### Leaderboard controller surface

`LeaderboardController` exposes public endpoints under `/api/leaderboard` for workflow rankings and frozen seasonal results. Those routes are intentionally public-facing, which makes them available without JWT authentication.

That separation reflects the service's access model. Builder and submission workflows are identity-aware, while read-only leaderboard views remain open.

## Runtime and build

Local development and runtime execution are defined in `apps/api/package.json`, while Nest and TypeScript build behavior is split across `nest-cli.json`, `tsconfig.json`, and `tsconfig.build.json`. The setup is workable as a foundation, but several paths and module settings do not line up cleanly.

```json

    "dev": "bun --watch src/main.ts",
    "build": "tsc -p tsconfig.build.json",
    "start": "bun dist/main.js",
    "start:prod": "bun ."
  }
}
```

```json
{
  "main": "dist/src/main",
  "type": "commonjs"
}
```

</CodeGroup>

### Runtime scripts

The service defines four runtime and build scripts:

- **`dev`** — runs `bun --watch src/main.ts`
- **`build`** — runs `tsc -p tsconfig.build.json`
- **`start`** — runs `bun dist/main.js`
- **`start:prod`** — runs `bun .`

The `dev` command runs the TypeScript entrypoint directly in Bun watch mode. The `build` command compiles with TypeScript rather than `nest build`.

### Likely dist path mismatch

The package metadata and runtime scripts point to different built entrypoints. `package.json` declares `main` as `dist/src/main`, while the `start` script runs `dist/main.js`.

<Callout kind="alert">

The compiled output path is likely inconsistent with the `start` script. With `rootDir` set to `./` and the source entrypoint at `src/main.ts`, emitted files likely land under `dist/src/`, which makes `bun dist/main.js` a probable mismatch.


</Callout>

## Docker and runtime packaging

The Dockerfile builds the service in one Bun-based stage and runs it in a second Bun-based stage. It copies the built `dist/` directory into the runtime image and starts the service with the production script.

<CodeGroup tabs="Dockerfile build stage,Dockerfile runtime stage">

```dockerfile
FROM oven/bun:1-alpine AS build
WORKDIR /app
COPY package.json bun.lock ./
RUN bun install --frozen-lockfile
COPY . .
RUN bun run build
```

```dockerfile
FROM oven/bun:1-alpine
WORKDIR /app
COPY package.json bun.lock ./
RUN bun install --frozen-lockfile --production
COPY --from=build /app/dist ./dist
EXPOSE 3000
CMD ["bun", "run", "start:prod"]
```

</CodeGroup>

### Build flow inside the image

The build stage installs dependencies from `package.json` and `bun.lock`, copies the application files, and runs `bun run build`. The runtime stage installs production dependencies only, copies `dist/` from the build stage, and starts the container with `bun run start:prod`.

That keeps the final image smaller than a single-stage build and matches the Bun-based local runtime approach used in the package scripts.

### Runtime behavior in the container

The runtime image exposes port `3000` and starts the service with `bun run start:prod`. That command resolves to `bun .`, so the container depends on package metadata to find the entrypoint rather than using an explicit file path.

This is one more place where the current packaging is functional but indirect. Between the `main` value, the `start` script path, and the hardcoded port in `main.ts`, the implementation has multiple runtime assumptions that do not fully agree.

## CI integration

The API workflow in `.github/workflows/api.yml` already covers build, versioning, image publishing, release creation, and a placeholder deploy job. It is more complete than the service implementation itself, but several parts are still scaffolding.

### Trigger and build behavior

The workflow runs on pushes to `main` and `dev` for changes under selected paths, and on pull requests targeting those branches. The build section installs dependencies with `pnpm install --frozen-lockfile` and builds the API with `pnpm --filter @repo/api build`.

The workflow path filters include `apps/api/**`, `packages/**`, `pnpm-lock.yaml`, `tsconfig.base.json`, and the workflow file itself. The inspected tree does not show a `packages/` directory, so that filter currently looks anticipatory or stale.

<CodeGroup tabs="Workflow trigger,Build step">

```yaml
on:
  push:
    branches: [main, dev]
    paths:
      - "apps/api/**"
      - "packages/**"
      - "pnpm-lock.yaml"
      - "tsconfig.base.json"
      - ".github/workflows/api.yml"
  pull_request:
    branches: [main, dev]
```

```yaml
- name: Install dependencies
  run: pnpm install --frozen-lockfile

- name: Build
  run: pnpm --filter @repo/api build
```

</CodeGroup>

### Versioning and tagging

The workflow reads the base version from `apps/api/VERSION`, which currently contains `0.1.0`. On `main`, it bumps major, minor, or patch based on commit message rules. On `dev`, it creates a prerelease version in the form `base-dev.timestamp.shortsha`.

It then tags releases as `api-v<version>`. On `main`, the workflow also writes the bumped version back to `apps/api/VERSION`, commits it, and pushes the change.

### Docker publishing and releases

The workflow publishes a container image to `ghcr.io/<owner>/gravity-api`. Tags include the exact version, `latest` on `main`, `dev-latest` on `dev`, and a SHA-based tag.

On `main`, the workflow also creates a GitHub Release named `API v<version>`. The release body includes the published image reference.

### Deploy step status

The deploy job exists, but it does not perform a real deployment yet. The inspected workflow only writes a deployment summary, and the actual deploy commands are commented placeholders.

<Callout kind="alert">

The CI pipeline includes release and deployment scaffolding, but deployment is not implemented. The deploy job is placeholder-only in the current workflow.


</Callout>
