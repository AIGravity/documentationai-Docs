## Overview

Gravity is a polyglot monorepo with three independently runnable applications under `apps/`: a Remix frontend at `apps/web`, a NestJS API at `apps/api`, and a FastAPI service at `apps/ai-service`. The repository has workspace orchestration, per-service Dockerfiles, semantic version files, and GitHub Actions pipelines.

The API is the primary backend, exposing endpoints for agent publishing, marketplace workflow execution, subscription billing, credits, earnings, referrals, payouts, and admin review. It uses Supabase for PostgreSQL persistence and authentication. The AI service provides agent verification, quality review, and AI-assisted content generation. The web app provides the user-facing interface for builders and consumers.

<Callout kind="info">

`pnpm-workspace.yaml` includes `packages/*`, and the README describes planned shared packages. Shared contracts are currently defined as TypeScript types within the API rather than as separate workspace packages.

</Callout>

## Top-level repository structure

The repository root contains the orchestration, build, and operational layers that tie the three applications together.

- `.github/`
  - `.github/workflows/web.yml`
  - `.github/workflows/api.yml`
  - `.github/workflows/ai-service.yml`
- `apps/`
  - `apps/web`
  - `apps/api`
  - `apps/ai-service`
- `scripts/`
  - `scripts/bootstrap.sh`
  - `scripts/version-bump.sh`
- `README.md`
- `package.json`
- `pnpm-lock.yaml`
- `pnpm-workspace.yaml`
- `tsconfig.base.json`
- `turbo.json`

A few root files define the monorepo shape directly:

- `pnpm-workspace.yaml` registers `apps/*` and `packages/*` as workspaces.
- `turbo.json` configures a minimal task graph for `dev` and `build`.
- `package.json` defines root development commands that delegate into the app workspaces.
- `scripts/bootstrap.sh` installs toolchains and service dependencies across JavaScript, Bun, and Python environments.

## Monorepo orchestration layer

The repo uses `pnpm` workspaces for package coordination and Turborepo primarily as a process orchestrator. At the current maturity level, Turborepo is not modeling a deep dependency graph because there are no shared internal packages yet.

The root `package.json` defines workspace-level commands such as `dev:web`, `dev:api`, and `dev`. Those commands establish the intended local development pattern: run services independently when needed, or run them in parallel through Turbo.

<Callout kind="alert">

The root script `dev:py` points to `apps/py-service`, but the actual Python service lives at `apps/ai-service`. That script is stale relative to the repository tree.

</Callout>

## Service architecture

### `apps/web`: Remix frontend

`apps/web` is the user-facing frontend. It provides builder tools for agent creation and testing, a marketplace for browsing and running agents, subscription and billing UI, admin review dashboards, and payout management. The app communicates with the API through an API client layer and uses Supabase for browser-side authentication.

The main entry file is `apps/web/app/root.tsx`. That file defines the document shell, global styles, font links, an `ErrorBoundary`, and the route outlet. The exported app component returns an `Outlet`, so request handling follows standard Remix nested routing.

Current route files are minimal:

- `apps/web/app/routes/_index.tsx`
- `apps/web/app/routes/home.tsx`

Both routes render the same component from `apps/web/app/welcome/welcome.tsx`.

`apps/web/vite.config.ts` shows the active frontend stack:

- Remix
- Vite
- Tailwind CSS
- TypeScript path support

The relationship to the rest of the repo is mostly implicit. The API service enables CORS for `http://localhost:3000`, which indicates the frontend is expected to call the API, but no such calls are implemented in the frontend code today.

### `apps/api`: NestJS API on Bun

`apps/api` is the TypeScript backend boundary. It uses NestJS for the HTTP framework, Bun as the runtime for local development and execution, and TypeScript compilation to `dist/` for builds.

The service boots from `apps/api/src/main.ts`. It creates the Nest application, enables CORS through the `CORS_ORIGINS` environment variable, applies a global validation pipe that strips unknown properties and transforms input types, and listens on the `PORT` environment variable, which defaults to `3001`.

The root module imports feature modules for agents, marketplace, payments, subscriptions, credits, payouts, earnings, referrals, and health. Authentication uses Supabase JWT bearer tokens through an auth guard. Admin endpoints require an additional admin role guard.

The API exposes dozens of endpoints across its feature modules, with DTO classes for request validation, service layers for business logic, and database access through the Supabase client and `pg` library. See the API reference for the full endpoint inventory.

### `apps/ai-service`: FastAPI Python service

`apps/ai-service` is the Python service for agent verification, quality review, and AI-assisted content generation. It uses OpenRouter or OpenAI for language model access, Bedrock for guardrail checks, Gemini for embeddings and search, and Redis for session caching.

The service exposes endpoints for agent verification with SSE streaming, description and category generation, setup field validation, URL safety screening, and quality review workflows. It uses Pydantic models for request and response validation.

The entry point is `apps/ai-service/main.py`. The Python project configuration lives in `apps/ai-service/pyproject.toml`. Dependencies include `fastapi`, `pydantic`, and `uvicorn`, with `ruff` and `pytest` declared for development.

## Entry points and request handling

Each application has a clear entry point, with request handling distributed across the web routes and backend feature modules.

### Web routes

The frontend entry point is `apps/web/app/root.tsx`, with route modules under `apps/web/app/routes/`.

Current route behavior:

- `/` is defined by `apps/web/app/routes/_index.tsx`
- `/home` is defined by `apps/web/app/routes/home.tsx`

Both route modules render the same welcome component. There are no loaders, actions, or backend requests in those routes.

### API routes

The API entry point is `apps/api/src/main.ts`. Controllers define their own `/api/...` route prefixes. The API exposes endpoints for agents, marketplace, subscriptions, credits, earnings, referrals, payouts, and webhooks. See the API reference for the full endpoint inventory.

### AI service routes

The AI service entry point is `apps/ai-service/main.py`. The service exposes endpoints for agent verification, content generation, setup validation, URL safety, and quality review.

## Module relationships and service boundaries

The repository has strong top-level separation and layered internal modules. The Nest application organizes domain behavior through feature modules, controllers, DTOs, services, guards, and database access. The FastAPI application separates its endpoint workflows and uses Pydantic models for request and response validation.

The clearest boundaries today are folder boundaries:

- `apps/web` for the frontend
- `apps/api` for the TypeScript backend
- `apps/ai-service` for the Python backend

### Current cross-service wiring

The API communicates with the AI service over HTTP for verification, review, and content generation. The web app communicates with the API through an API client layer. Both the API and web app use Supabase for authentication and database access.

## Persistence, middleware, auth, and external services

### Database and persistence

The platform uses Supabase-hosted PostgreSQL as its primary database. The persistence layer is schema-first and SQL-first: tables, constraints, triggers, and stored procedures are defined in raw SQL migrations. The API accesses the database through the Supabase client and the `pg` library. No ORM entity layer is used.

The database schema covers billing and credits, marketplace workflows, agent review and verification, earnings and payouts, referrals, user profiles, bounty systems, notifications, and telemetry. See the Data Models Reference for the full table inventory.

A separate Activepieces PostgreSQL database stores workflow execution state, including flows, runs, and connections. Activepieces manages this schema, which is intentionally separate from the Gravity application database.

### Middleware

The API uses a global validation pipe that strips unknown properties and transforms input types. CORS is configured through the `CORS_ORIGINS` environment variable. Sentry and PostHog integrations provide error tracking and analytics.

### Authentication and authorization

Authentication uses Supabase JWT bearer tokens. Most API endpoints require a valid token through an auth guard. Admin endpoints additionally require an administrator role. Public endpoints include health checks, public workflow detail, share-link resolution, file proxy downloads, and webhook receivers. Webhooks authenticate through provider signature verification.

### External services and integrations

Present integrations:

- Supabase for database, authentication, and row-level security
- Activepieces for workflow execution
- OpenRouter and OpenAI for language model access
- Bedrock for guardrail checks
- Gemini for embeddings and search
- Redis for session caching
- Razorpay and Stripe for pay-ins
- RazorpayX, PayPal, and Stripe Connect for payouts
- SMTP for email notifications
- Sentry for error tracking
- PostHog for product analytics
- Crisp for support chat, when enabled

See the Integrations page for details on each integration.

## Build, release, and deployment tooling

The operational layer is more mature than the application layer. Each app has enough tooling to build, version, containerize, and publish independently.

### Local setup

`scripts/bootstrap.sh` checks for `pnpm`, `bun`, and `uv`, then installs dependencies for the JavaScript and Python services. That script reflects the repo's polyglot design: each app uses the native tooling expected for its runtime.

### Versioning

Each app has a local `VERSION` file:

- `apps/web/VERSION`
- `apps/api/VERSION`
- `apps/ai-service/VERSION`

`scripts/version-bump.sh` updates those version files, establishing per-service version management rather than one monorepo-wide application version.

### Containers and CI/CD

Each service has its own Dockerfile:

- `apps/web/Dockerfile`
- `apps/api/Dockerfile`
- `apps/ai-service/Dockerfile`

Each service also has its own GitHub Actions workflow:

- `.github/workflows/web.yml`
- `.github/workflows/api.yml`
- `.github/workflows/ai-service.yml`

Those workflows handle build and verification steps, version generation, Docker image publishing to GitHub Container Registry, and GitHub release creation. The deployment sections are present as placeholders, which means release automation is implemented further than environment deployment.

## Notable gaps and inconsistencies

A few repo details can mislead an architectural review unless they are called out directly.

### Script and naming drift around the Python service

The repository uses `apps/ai-service` as the actual Python service path, but some root-level references still point to `py-service`. The most concrete example is the root `package.json` script that targets `apps/py-service`.

This inconsistency affects local development expectations and is a sign that repo documentation and scripts have not fully caught up with the current directory structure.

<Callout kind="info">

The architecture has matured from its initial scaffold into a feature-complete platform. The strongest aspects remain the operational structure: service boundaries, runtime separation, containerization, and release automation. The application layer now includes domain modules, persistence, authentication, and cross-service integration.

</Callout>

## What this architecture means today

Gravity has a stable foundation with clear service boundaries, mature operational tooling, and a feature-complete application layer. The API, web, and AI services are integrated through authentication, database access, and HTTP communication. Domain modules cover agents, marketplace, billing, earnings, payouts, and referrals.
