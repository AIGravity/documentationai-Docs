## Implementation notes

The FastAPI application registers the `GET /health` handler directly and also exposes verification endpoints under the `/verification` path. The health route does not define a response model, while the verification endpoints use typed request and response schemas.

## Likely error responses

The current implementation is minimal, so likely error behavior is limited to framework defaults and unexpected runtime failures.

- **`404 Not Found`** — Returned when you request a path that is not defined.
- **`404 Not Found`** — Returned when you use a path or method combination that does not match the implemented route, based on the available code analysis.
- **`500 Internal Server Error`** — Possible only if the service encounters an unexpected runtime failure while handling the request.

## Verification warmup

### POST `/verification/warmup`

Primes the verification pipeline components so that subsequent verification requests avoid cold-start delays. The endpoint warms LLM clients, initialises content safety guardrails, and loads URL safety feeds into memory.

<ParamField body="method" param-type="string" required="true" show-location="false">

`POST`


</ParamField>

<ParamField body="path" param-type="string" required="true" show-location="false">

`/verification/warmup`


</ParamField>

<ParamField body="request body" param-type="none" required="false" show-location="false">

None. This endpoint does not accept a request body.


</ParamField>

### Example request

<CodeGroup tabs="cURL">

```bash
curl -i -X POST http://localhost:8000/verification/warmup
```

</CodeGroup>

### Response

Returns a JSON object indicating whether the warmup completed and how long it took.

<CodeGroup tabs="JSON">

```json
  "warmed": true,
  "elapsed_ms": 3200,
  "status": "ok"
}
```

</CodeGroup>

<ResponseField name="warmed" field-type="boolean" required="true">

</ResponseField>

<ResponseField name="elapsed_ms" field-type="integer" required="false">

</ResponseField>

<ResponseField name="status" field-type="string" required="true">

</ResponseField>

## Verification prewarm

### POST `/verification/prewarm`

Pre-runs the behaviour analysis stage of the verification pipeline on a submitted workflow and caches the result under the workflow's content hash. When the caller later submits the same workflow for full verification, the cached analysis is reused instead of re-running from scratch.

The cache expires after 30 minutes and holds up to 500 entries.

<ParamField body="method" param-type="string" required="true" show-location="false">

`POST`


</ParamField>

<ParamField body="path" param-type="string" required="true" show-location="false">

`/verification/prewarm`


</ParamField>

### Request body

<ParamField body="workflowJson" param-type="string" required="true">

The workflow JSON to pre-analyse. This should match the workflow that will be submitted during the full verification step.


</ParamField>

### Example request

<CodeGroup tabs="cURL">

```bash
curl -i -X POST http://localhost:8000/verification/prewarm \
  -H "Content-Type: application/json" \
  -d '{"workflowJson": "{\"trigger\": {}, \"steps\": []}"}'
```

</CodeGroup>

### Response

Returns a JSON object indicating whether the result was cached and the overall status.

<CodeGroup tabs="JSON">

```json
{
  "cached": true,
  "status": "ok",
  "reason": "prewarm completed"
}
```

</CodeGroup>

<ResponseField name="cached" field-type="boolean" required="true">

Returns `true` when the analysis result was successfully cached for later reuse.


</ResponseField>

<ResponseField name="status" field-type="string" required="true">

Status of the prewarm operation. Returns `ok` on success.


</ResponseField>

<ResponseField name="reason" field-type="string" required="false">

Human-readable detail about the prewarm result, such as whether the result was newly cached or already present from a previous call.


</ResponseField>
